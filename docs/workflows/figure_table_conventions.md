# Figure and table conventions — what the MTD literature does, and what this dissertation adopts

**Status:** durable. The visual-artefact counterpart to [`voice.md`](voice.md): load it **before generating or revising any dissertation figure or table**, and before writing a new figure generator in `tools/`. Distilled from a page-level visual survey (2026-08-20) of the lit-review corpus in `docs/sources/lit_review/original/` — the papers this dissertation cites, across the five house styles the field publishes in (IEEE journal, IEEE conference, Elsevier, ACM, USENIX/MDPI). The aim is that our figures and tables read as native to the MTD literature.

Two prior rulings sit **above** this file and are not overridden by anything in it:

- the figure-pipeline ruling: figures are generated by `tools/` scripts into `docs/thesis/figures/` as 12pt standalone TikZ, greys + one accent (RGB 31,84,140 / `accentlight` 200,214,232), shared tactic axis across the L1/L3 family (the canonical style block moved to `tools/gap_appendix_figures.py` when `l1_attack_graph.{tex,py}` was deleted on 2026-08-20 — same `accent`/`accentlight` definitions, same grey grammar, and it does §h's type-size arithmetic in the generator);
- the no-accentuation ruling for *diagnostic* visualisation (no arrows/circles/highlights on evidence viz; accentuation is reserved for dissertation chapter figures, used sparingly).

## b) The rules every house style agrees on

These held in **every** paper surveyed; treat them as hard conventions.

1. **Table captions above the table; figure captions below the figure.** No exceptions in the corpus. The dissertation follows this.
2. **The caption decodes every visual encoding.** Colour semantics (cho2020 Fig. 2: "a blue vertical line represents a proactive MTD … an orange line … reactive"), cell shading (he2025 TABLE III: "Successful attacks … are shaded in grey" as a table footnote), letter callouts (jalowski2026 Figure 3 decodes A/B/C one by one), and abbreviation keys (brown2023 Figs. 4–5: "Key - I: IP Shuffle, H: Host Topology Shuffle…"). A reader who sees only the float must be able to read it completely.
3. **Multi-panel results use lettered panels** — (a), (b), (c), one overall caption carrying the shared message and decoding each panel in turn, and the series encoding held constant across panels with the legend/key shown once (hong2018 Fig. 5 gives the key its own panel cell; brown2023 stacks (a)–(c) with one caption). *Mechanism:* the letters are drawn by the generator inside the picture, not set by `subcaption` — see the §i ruling.
4. **Table footnotes carry provenance and marks.** Where a value's origin or a symbol needs explaining, it goes in a footnote row under the table, not in body text (outkin2023 TABLE 1's inferred-from-literature note; rahman2024 TABLE 6's `*`/`**` agreement levels).
5. **ATT&CK-derived (or any versioned-corpus) data is date/version-stamped in the caption** (sadlek2022: "The most common data sources in MITRE ATT&CK (22nd March 2022)"). Ours: any figure or table built from the pinned ATT&CK bundle or a frozen artefact family states the pin (bundle version / `v4_failure_only` etc.) in the caption or footnote. The general (prose-side) ATT&CK referencing and version-pinning rules live in [`literature_conventions.md`](literature_conventions.md) §a–b.
6. **Kill-chain / tactic order is the universal organising axis.** Stage pipelines run left→right in lifecycle order (alshamrani2019 Fig. 1); attack trees band their stages (Figs. 2–5); mapping tables key rows by stage (TABLE V); matrices column by tactic (al-sada2024 Fig. 2). Our shared-tactic-axis ruling is the same convention — never reorder tactics between figures.

## c) Caption label typography — venue-specific, so the thesis picks one and holds it

The corpus splits: IEEE journals use "Fig. 1." + small-caps `TABLE I` above; the IEEE conference template renders "Fig. 1: …" / "TABLE I: …"; Elsevier uses "Fig. 1. …" ("Fig. 1 – …" in older C&S) and a two-line "Table 1 ⏎ Description."; ACM uses "Table 1. Title Case". What transfers is **position and completeness (§b), not the label form**. The dissertation uses the `cshonours` class defaults ("Figure N: …", "Table N: …") — do not imitate IEEE small caps or roman numerals. Caption text: sentence case, ends with a full stop; multi-sentence captions are normal and expected when decoding encodings (§b2).

**Every float carries a short caption.** `\listoffigures` and `\listoftables` are both live in the preamble, and the decoding captions §b2 mandates are long enough to flood them — a twelve-line caption becomes a twelve-line List of Tables entry. So every float is written `\caption[short]{long…}`, where the short form is a noun phrase naming what the float shows, no decode, no full stop, one line in the list. Ruled at the appendix-wiring pass (2026-08-20) and demonstrated on `tab:experiment-one`, the first wired float.

## d) Diagram genres, with the exemplar to imitate

For each genre the literature has a settled visual grammar. New figures should be recognisably of their genre — deviate in palette (ours is greyer), not in grammar.

1. **Stage/lifecycle pipeline** — plain rectangles, left→right arrows, stage labels beneath the boxes (alshamrani2019 Fig. 1). Same grammar at framework scale: labelled stage lozenges with per-stage content boxes (rodriguez2024 Figure 1, minus the icons).
2. **Attack tree / attack graph** — rectangles for goals/non-leaf nodes, ellipses for leaf actions, AND/OR gate symbols where logic matters, dashed bands separating lifecycle stages, and a symbol legend *inside* the figure (alshamrani2019 Figs. 2–5). brown2023 Fig. 1 colour-codes node types in pastel; our equivalent is grey fills + the accent for the one node class that matters.
3. **Taxonomy / classification tree** — shallow tree, fill tone per depth level, straight connectors without arrowheads (cho2020 Fig. 3; hong2018 Fig. 1).
4. **Attacker-procedure flowchart** — rounded rectangles, numbered steps, decision edges labelled Success/Failure, loop-back edges labelled in words (brown2023 Fig. 3 — the direct ancestor of our movement-model figures).
5. **Petri net** — circles = places, rectangles = transitions, IDs on the nodes (`cP1`, `cT3`), meanings in companion **ledger tables** (ID | description | rate), colour used only to single out special transitions (bland2020 Fig. 8 + Tables 7–8). This is the published precedent for the L3 net figure and its appendix ledgers.
6. **Network topology** — surveys use 3D icon clip-art (cho2020 Fig. 13); evaluation papers use abstract node-link drawings coloured by layer/level (brown2023 Fig. 2). Ours are always the abstract kind.
7. **Tactic-keyed matrix / heatmap** — the ATT&CK-navigator genre: tactic columns, technique cells, fill marking membership or weight (al-sada2024 Fig. 2). Our weight matrices (`fig_4-2-4b_failure_weight_matrix.tex`) are this genre with a numeric fill; keep every cell printed (the corpus prints values in cells wherever cells are few enough to read — tay2024 Fig. 6, cho2020 pies).
8. **Timeline** — event marks as vertical lines colour-coded by kind on a labelled time axis (cho2020 Fig. 2), or phase spans annotated with braces and per-phase symbols (kim2026 Fig. 7).
9. **Icon/scenario cartoon** (alshamrani2019 Figs. 6–7; jalowski2026) — a survey-register genre. **Do not use**: it collides with the greys ruling and dates quickly.

## e) Table genres

1. **Comparison / feature matrix** — rows = works or techniques with the citation in the row label ("Carbanak [16]"), columns = capabilities, ✓ for present, **empty cell** (not ✗) for absent (alshamrani2019 TABLE II). Used for related-work positioning tables.
2. **Pros/cons or approach-comparison table** — prose cells, one row per approach, Ref(s). column collecting citations (cho2020 TABLES IV/VI).
3. **Parameter table** — the experiment-setup genre: Type | Symbol | Description | Value, math symbols italic, units bracketed, ranges as `[a, b]`, distributions as math (`Uniform(1000, 5000)` ms) (kim2026 Table 4; brown2023 TABLE I). Ch5's setup tables are this genre.
4. **Stage→methods mapping table** — rows in kill-chain order (alshamrani2019 TABLE V).
5. **Results table** — booktabs; grouped column headers with spanning rules under the group label (he2025 TABLE III's per-device ADR|RI pairs; buechel2025 Table 5's per-dataset Prec|Rec|F1); numerals right-aligned at fixed decimals; best-in-column marked bold or underlined; cell shading allowed only with a decoding footnote (§b2, §b4).
6. **Ledger table** — companion to an ID-labelled diagram: ID | meaning (| rate) (bland2020 Tables 7–8). The L3 appendix ledgers follow this.

**Rule style:** the 2019–2020 IEEE surveys use fully boxed grids with bold header rows; everything 2024+ (rahman, he, buechel, kim, al-sada) is booktabs — top/mid/bottom rules, **no vertical rules**. The dissertation is booktabs throughout (`\usepackage{booktabs}` is already loaded); never emit `\hline` grids from a generator.

## f) Results-chart conventions

- **Chart type by question:** grouped bars for technique × scenario comparison (brown2023 Figs. 4–5); marker-per-series line charts for parameter sweeps (hong2018 Fig. 5; kim2026 Fig. 8); log-axis scatter for two-metric outcome spaces (he2025 Fig. 4); stacked bars only when segment values are printed in the segments (tay2024 Fig. 6). Pair an overview with a zoom when one regime hides another (bland2020 Fig. 12).
- **Series encoding is an experiment-wide contract:** one colour/marker per condition, identical in every panel and every figure of that experiment (hong2018 holds four series across five panels). Name series in domain terms ("No MTD", "Shuffle only"), or declared math symbols (kim2026's $S_{vIP}+D_{SW}$) — never raw code identifiers.
- **Legend inside the axes** where space allows (every charted paper), or as a once-shown key panel for multi-panel figures (hong2018).
- **No title above the axes** — the caption is the title. (bland2020 and tay2024 keep matplotlib's default titles; that is the tool leaking, not a convention.)
- Axis labels spelled out with units; when axis categories abbreviate, the caption carries the key (brown2023).
- Palette: the corpus's saturated defaults (cho2020 pies, bland2020 tab10) are **not** the model; ours is greys + accent. For multi-series charts needing more hues, the `dataviz` skill's palette rules apply within that constraint.

## g) Anti-patterns in the corpus (named, so they are recognised and refused)

The examiner stake: Tim French's lit-review feedback (missing images/examples cost marks) makes figures a marked surface. These are the corpus's failures — the things a reader notices:

- **Illegible tick labels** — brown2023 Figs. 4(b)/(c), 5(b)/(c): double/triple-MTD combination labels render at ~3pt. Rule: after inclusion scaling, no glyph below ~8pt equivalent; if categories don't fit, rotate, thin, or split the panel.
- **Raw code identifiers in figures** — tay2024 Fig. 6's `sensitivity_1.0` tick labels; the figure exposes the config file. Rule: presentation names are part of the figure spec, mapped in the generator, never hard-coded corpus facts (the mechanism-not-exception ruling applies to figure tooling too).
- **Tool-default chart junk** — matplotlib titles (bland2020, tay2024), default palettes, unstyled legends. Generators emit deliberate style or none.
- **3D/gradient clip-art** — cho2020 Figs. 1/13. Dated on publication; excluded by the greys ruling.
- **Screenshot-as-figure** — rodriguez2024's ProM output (Figure 4) is legitimate *tool-evidence* in a mining paper, but unreadable at print size; for our own models we draw the figure, we do not screenshot the tool.
- **Encoding without a decode** — any colour, shading, or letter that the caption does not explain violates §b2 (the corpus almost never does this — which is exactly why a violation stands out).

## h) Sizing and typography for the thesis build

- The papers set figures at `\columnwidth` (~8.4 cm) with 8–9pt label text. The thesis is single-column: default to `\textwidth` inclusion, and prefer two panels side by side only when they share a y-axis.
- **The printed size is the invariant, not the size macro** (measured 2026-08-20, at the controller-mapping figure). A standalone's fonts are set in its own coordinate space and then *scaled by the inclusion*, so a macro name guarantees nothing: `\textwidth` is **411.4pt (14.51 cm)** in `cshonours`, and a figure whose natural width is 16 cm is scaled to ~0.87, which puts `\scriptsize` (8pt) on the page at ~7pt and `\tiny` (6pt) at ~5.2pt — under §g's own ~8pt floor. The arithmetic every generator owes:

  > printed pt = natural pt × (411.4 ÷ natural width in pt)

  So **choose the type scale and the inclusion width together**, not by habit. A text-dense figure at ~16–17 cm natural needs `\footnotesize`/`\small` as its two sizes to clear the floor; only a figure narrow enough to be scaled *up* can afford `\scriptsize`/`\tiny`. The floor has a ceiling to match: a narrow figure included at full `\textwidth` is scaled up, and its labels then print *larger* than the prose around them, which reads as amateurish. Set the inclusion width so figure labels land near or just below body size — `fig:controller-mapping` is 11.6 cm natural at `0.78\textwidth`, printing at ~9.8–10.7pt against 12pt body. Where the widest element sets the width — a reason or label column — cap its length in the generator and enforce the cap, so a later edit cannot quietly push the whole figure under the floor. Measure after any change to width, type scale, or inclusion width; `gs -sDEVICE=bbox` gives the natural size, and the check belongs in the generator's own output.
- Grey grammar (from `tools/gap_appendix_figures.py`, the canonical block since 2026-08-20): hairlines/gridlines `black!12`, secondary text `black!60`, structure in blacks/greys, `accent`/`accentlight` for the one thing the figure is about.
- **The landscape typeblock, measured (2026-08-20, at the appendix attack graphs).** Inside `pdflscape`'s `landscape` environment the typeblock is the portrait one rotated: **702.78pt (24.79 cm) wide by 455.24pt (16.06 cm) tall**. (`\the\textwidth` read inside the environment still reports the portrait 455.24pt — it is the shipped page that swaps, so measure the printed page, not the macro.) A full-page landscape figure therefore has ~23.5 cm to work in with a decoding caption under it. Flagged for reconciliation: §h's arithmetic above quotes `\textwidth` as 411.4pt, but `dissertation.tex` loads `geometry` with `margin=2.5cm`, which makes it **455.24pt** — the two numbers disagree, and the second is what the document actually compiles with.
- **Including at natural size sidesteps the scaling trap entirely.** If the generator packs the figure to the page box itself and the float includes it with a bare `\includegraphics{...}` — no width macro — then 8pt in the generator is 8pt on the page, and no later inclusion-width edit can quietly push it under the floor. `tools/gap_appendix_figures.py` works this way and prints the effective type size of every figure it writes.
- Tables are typeset in the document (booktabs), not generated as images. Generators may *emit* LaTeX table bodies; values always flow from tracked artefacts, never typed (the L3 no-value-typed rule generalises: any number in a figure or table is read from a tracked artefact or generated by the tool).

## j) File naming — floats are keyed to where they land in the dissertation (ruled 2026-08-27)

Every file in `docs/thesis/figures/` and `docs/thesis/tables/` is named for the
dissertation position it is included at, so the folder can be scanned by
section and the right file found for an Overleaf paste without opening the tex:

```
<kind>_<chapter>-<section>-<subsection><order>_<name>.<ext>
fig_4-2-4b_failure_weight_decomposition.pdf
tab_B-6a_outcome_overlay_weights.tex
```

- `kind` is `fig` or `tab`. Tables are the `\input` fragments; a fragment
  holding several `table` environments is one file (`tab_B-6a_…` carries three).
- The position is the numbered heading the float is included under, to the
  depth that exists: `2-2` (§2.2), `4-2-4` (§4.2.4), `4-0` (chapter 4 before
  its first section), `D-0` (appendix D, chapter-level). Appendices use their
  letter. Subsubsections are not encoded (nothing yet needs them). Separators
  are **hyphens**, never dots — a dot in a graphics stem breaks
  `\includegraphics`'s extension parsing.
- `order` is a letter giving order of appearance within that heading, counted
  separately for figures and tables (`fig_B-1a` … `fig_B-1d`; `tab_4-2-4a`).
- `name` is the descriptive stem the generator has always used.
- A generated file with no float in `dissertation.tex` yet takes `unplaced`
  in the position slot (e.g. `fig_unplaced_success_weight_matrix`, if the
  success verdict were ever drawn), so it sorts apart and cannot be mistaken
  for a wired one.
- **Labels do not follow the file name.** `\label{fig:controller-mapping}`
  stays semantic; the file prefix is a location index, not an identity, and
  it is **re-keyed when a float moves or a heading is renumbered** — moving a
  float is a rename of its file, its generator's `STEM`, and the tex
  `\includegraphics`/`\input` line, in one commit. The generator's STEM is the
  single point of truth for the name; the tex and the manifest follow it.
- The manifest at [`../thesis/FLOATS.md`](../thesis/FLOATS.md) lists every
  float with its position, file, label and generator; update it in the same
  commit as any rename or new float.
