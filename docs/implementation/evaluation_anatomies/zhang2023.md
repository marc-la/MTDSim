## B. Setup — what is declared before any result

- Network configuration(s): FOUR networks, Table 2 "Network Properties" (p.33): columns Network | Nodes | Density | Endpoints | Layers; rows 1: 25/0.093/3/4; 2: 50/0.052/5/4; 3: 75/0.040/7/4; 4: 100/0.043/10/4. Chosen as a size sweep: "four networks with different sizes, ranging from 25 to 100 nodes. The number of nodes in the network is denoted as Network Size" (p.33). Generation: 3-layer HARM; Barabási–Albert for the host graph, Watts–Strogatz for service connections (p.20); four OS types (Ubuntu, CentOS, Windows, FreeBSD), five users per host with some credential reuse (p.21); service versions 1–99, half cross-platform (p.21). How density was set: not stated (it is reported as a property, then invoked post hoc in 5.1.3).
- Attacker model / scenarios: ONE. "only the first attack scenario is selected to be refactored and simulated in MTDSimTime" — compromise as many hosts as possible (p.28, 4.4.1.1); the target scenario is explicitly dropped "Due to the limited amount of time". Profile given as four bold-run-in features (4.4.1.1–4.4.1.4, p.28–29): objectives; exploiting vulnerabilities; C2/pivoting with "compromised hosts will always stay compromised and can be recognised by the adversary immediately upon regaining access, regardless of any network changes made by MTD techniques" (p.29); credential stuffing. Attack flow = Cyber Kill Chain-ordered flowchart, Figure 7 (p.30), three phases (Scan Port & Exploit User Credential; Exploit Vulnerabilities; Brute Force) (p.29). Interruption rule: "a limited number of attempts will be allowed for each attack action. If the number of interruptions caused by application layer MTD techniques reaches a certain threshold, the attack event will fail" (p.30) — threshold value: not stated. Attacker timing: Phase 2 duration by Equation 2 with an exponential T_exploit and per-vulnerability attack complexity in [0,1]; learning halves time on previously exploited vulnerabilities; "time penalty" per MTD interruption (p.31) — penalty value: not stated.
- Defence conditions: FIVE techniques (4.3.1, p.22–24): CompleteTopologyShuffle, IPShuffle (shuffle, network layer); ServiceDiversity, OSDiversity, DAP_OSDiversity (diversity, application layer; the last "newly implemented", p.22). Combinations: all pairwise = 10 (Fig. 10 legend, p.37). Schedulers: THREE execution schemes — Random, Alternative, Simultaneous (4.3.2, p.24–25), with a resource-occupation/suspension queue (4.3.3, p.26–27). Interval distribution: exponential (replacing the uniform of "the previous simulator", p.27). No-defence baseline: YES — "NoMTD" is the first bar in every panel of Figures 8, 10, 11, 12 (p.35, 37, 38 renders) and is named in prose: "as compared to the case where no MTDs are employed" (p.34).
- Parameter tables: TWO. Table 2 Network Properties (p.33, 4×5 as above). Table 3 "MTD Execution Time" (p.34): MTD technique | Average Duration (s) | Standard Deviation; CompleteTopologyShuffle 110/0.5; IPShuffle 100/0.5; OSDiversity 80/0.5; DAP_OSDiversity 80/0.5; ServiceDiversity 70/0.5. Distributions: exponential for MTD interval and action durations, stated in prose with PDF/CDF equations (p.27, p.32, Eq. 3–4); Table 3 implies a normal-like duration (mean + SD) but the distribution is not named. Basis: "there is currently a lack of research measuring the time spent by specific MTD techniques … the proposed solution selects various time values for each MTD technique within a reasonable range based on existing empirical data and conducts sensitivity analysis to determine the appropriate value" (p.27–28) — no such sensitivity analysis is reported. Factor levels declared in prose: "four MTD Intervals, ranging from 50 to 200 seconds" (p.33) = 50/100/150/200 (panel titles, p.35). No table lists the attacker's constants.
- Replications: "we set the terminating condition for the simulation as the NCR reaching 0.8 and run the simulation 100 times for each variable set to obtain statistically significant results" (p.33). Horizon: none other than the NCR=0.8 checkpoint; seeds: not stated; whether the network is regenerated per run: not stated. Cell count: single = 4 intervals × 4 sizes × 6 conditions (5 MTD + NoMTD); multiple = "16 scenarios" (p.36) × 3 schemes × (10 pairs + NoMTD).
- Statistics: means only — "Mean Time to Compromise on 0.8 NCR" (Fig. 8/10 captions). No SD/CI/min–max on any results figure (no error bars in renders p.35/37/38); no significance test despite the phrase "statistically significant results" (p.33). Derived statistic: "Percentage Improvement %" histograms (Fig. 9, Fig. 13) and a "Max Count" tally (Fig. 14).
- Anything else: SimPy as the DES engine (p.31, "MTDSimTime utilises the SimPy framework"); Python implied. Hardware, versions, run-time, code link: not stated.

  - Figure 13 (p.39): histogram; x = Percentage Improvement % (range ≈ −50 to 170), y = Frequency; caption "Distribution of Percentage Improvement: Combining Multiple Category MTDs over Combining Shuffle MTDs".

- Tables: Table 2 (4 rows × 5 cols) — the four networks; Table 3 (5 rows × 3 cols) — per-technique execution time. No results table; every number in the text comes from a figure.
- Baseline appearance: "NoMTD" is the leftmost bar in every panel of Figs. 8, 10, 11, 12 (renders). In prose the baseline is invoked once, qualitatively (p.34).
- Comparison prose: MAGNITUDE via percentage improvement — "a significant improvement of over 130% (Figure 9) compared to the other techniques on average" (p.34); "an average improvement of approximately 20% (Figure 13)" (p.38); abstract: "consistently outperform diversity-based techniques by more than 130% on average" (p.5). ORDERING — "consistently outperform"; "the top 2 MTD techniques, namely CompleteTopologyShuffle and IPShuffle … did not have the same dominant position when they were used in combination" (p.38); "consistent superiority of the Alternative and Simultaneous schemes over the Random scheme in most scenarios" (p.40). RECOMMENDATION, conditional — "in certain scenarios, it may be advantageous to utilise a single shuffle-based MTD technique instead of combining them" (p.39); "the Alternative scheme is more effective for shorter intervals (50, 100), while the Simultaneous scheme performs better for longer intervals (150, 200)" (p.40); "when selecting an MTD execution scheme, careful consideration of the specific scenario and available resources is crucial" (p.40). No absolute MTTC values are quoted in text.

## D. Narrative — the claims, in order

1. MTD raises time-to-compromise vs no MTD: "employing MTD techniques can significantly increase the time it takes for an adversary to achieve their objective, as compared to the case where no MTDs are employed" (p.34).
2. Shuffle > diversity: "network shuffle-based MTD techniques, including IPShuffle and CompleteTopologyShuffle, consistently outperform other MTD techniques … over 130% (Figure 9)" (p.34); mechanism offered: "disruption of connections … require the adversary to spend extra time relocating their targets … diversity-based MTD techniques only reconfigure components within each host, allowing the adversary to resume the attack after interruption" (p.34).
3. Interval: "MTD techniques are more effective on shorter intervals in most scenarios", with an exception at 100 vs 150 for shuffle techniques attributed to Table 3 execution times exceeding the interval: "the mean execution times for these MTDs are longer than the triggering interval, which may cause issues related to suspension actions" (p.36).
4. Size: "MTD techniques are generally more effective on networks with more nodes", with a 75 vs 100 exception attributed to density: "it is assumed that MTD techniques are more effective on networks with more nodes and lower densities. However, to establish this relationship with greater certainty, further research and evidence may be necessary" (p.36).
5. Combinations follow the single trend across intervals/sizes (p.36–38); the two best singles lose dominance in combination because "both of these MTD techniques occupy resources in the network layer, which means they cannot be deployed concurrently" (p.38); cross-category pairs "demonstrated better performance with an average improvement of approximately 20% (Figure 13)" (p.38).
6. Single shuffle ≈ shuffle combinations: "network shuffle-based MTD techniques exhibit similar effectiveness when used in combination compared to when used individually. Therefore, in certain scenarios, it may be advantageous to utilise a single shuffle-based MTD technique" (p.38–39), with a resource-model caveat (p.39).
7. Schemes: Alternative and Simultaneous beat Random "in most scenarios" (p.40); no node correlation; Alternative for short intervals, Simultaneous for long, with a mechanism ("registers all MTD techniques simultaneously", p.40) and a resource caveat.

Claims about the ATTACKER from the data: none. Attacker properties appear only as mechanism explanations for defence results (claim 2: the adversary must "relocate their targets" vs "resume the attack"; claim 5: static application layer "can make it easier for adversaries to exploit"). The adversary's own behaviour (target selection by distance, fixed action list) is characterised as a limitation in 6.3 (p.42–43), not measured.

## E. Sensitivity / parameter analysis

Present, as a FULL-FACTORIAL GRID embedded in the results rather than a separate section: two factors, MTD Interval ∈ {50, 100, 150, 200} s and Network Size ∈ {25, 50, 75, 100} nodes, crossed to "16 scenarios" (p.36), with the single-MTD condition (6 levels) and, for the pairwise block, the execution scheme (3 levels) added as further crossed factors. Reported as 4×4 small-multiple grids (Figs. 8, 10) with two zoom-ins (Figs. 11, 12) and a tally chart (Fig. 14). Range justification: "ranging from 50 to 200 seconds" and "ranging from 25 to 100 nodes" (p.33) — no rationale given for either range; the interval range straddles the Table 3 execution times (70–110 s), which is later used explanatorily (p.36). Located: 5.1.2 "Impact of MTD Interval" and 5.1.3 "Impact of Network Size" are dedicated sub-sections inside the single-MTD results (p.36); for combinations the factor effects are read off Figs. 11/12/14 inside 5.2. Claims supported: shorter interval → more effective (with exception); larger network → more effective (with exception, density hypothesised); scheme choice conditional on interval (p.40). Declared-but-absent: "conducts sensitivity analysis to determine the appropriate value" for MTD execution times (p.28) and "µ … can be determined via empirical study and sensitivity analysis" (p.32) — neither is reported. No one-at-a-time sweeps of attacker constants; no appendix.

## F. Discussion / limitations

No section titled Discussion. Interpretation is folded into the results sub-sections (each ends with a mechanism hypothesis and, twice, a resource caveat: p.39, p.40). The limitations chapter is titled "6 Scope for Future Work" (p.41) and frames each limitation as a future-work item; its opening is a mini-summary of findings. Threats-to-validity language is absent; comparability against other simulators/papers is not discussed (the only cross-reference is that the target scenario and three techniques from "previous work [17]" were dropped, p.22, p.28).

Verbatim sentences worth quoting:
- Chapter framing: "While the study has yielded important findings, it is important to acknowledge that certain limitations may have impacted the results in some aspects. In order to ensure the robustness of future research, this section aims to outline these limitations and suggest potential directions for further investigation." (p.41)
- Interval/frequency confound (6.1): "due to resource occupation and suspension mechanisms, the frequency of deployment for MTD techniques does not necessarily increase with shorter triggering intervals. Notably, it is hypothesized that a higher frequency of deployment could lead to better MTD technique performance, but this hypothesis could not be confirmed in this work due to the time limitation." (p.41)
- Network-size confound (6.1): "Given the multitude of factors influencing a network, it is impossible to maintain uniformity while exploring how varying node numbers can affect MTD performance across different networks. As mentioned in Section 5, the Network Density may also play a pivotal role, but conclusive evidence is required to validate this hypothesis." (p.41–42)
- Random vulnerabilities as uncontrolled factor (6.1): "as the vulnerabilities in each host of the simulated network were randomly generated and assigned, it was challenging to measure and control their impact during experimentation. Unfortunately, this work did not consider these factors, nor did it examine the extent to which they impact the effectiveness of MTD techniques." (p.42)
- Generalisability (6.2): "only one to two defenses were explored per layer, with just two shuffle and three diversity techniques examined. As a result, the findings may not be generalisable to other MTD techniques or combinations that were not tested in this study. Therefore, it is important to acknowledge the limitations of the current research and to exercise caution when applying the results to real-world scenarios" (p.42)
- Adversary realism (6.3): "The current attack operation in this work consists of a fixed list of actions that can be optimised in various ways. For example, in the target selection phase, the adversary's current decision is based on the distance to each discovered host, which may not be the most efficient approach as different hosts can have varying levels of vulnerability complexities." … "introducing a more intelligent attack profile will make it more comprehensive and sophisticated, enabling future works to evaluate the effectiveness of MTD techniques against a more advanced adversary." (p.42–43)
- Scope concession on the attacker (4.4.1.1): "Due to the limited amount of time in developing the simulator on a new simulation framework, only the first attack scenario is selected to be refactored and simulated in MTDSimTime." (p.28)
- Resource-model caveat inside results (5.2.1): "the two network shuffle-based MTD techniques employed in this experiment assume the same resource utilisation (specifically, network layer resources) within the simulation environment, while not considering the computational resource consumption associated with executing MTD techniques." (p.39)
- Reconfiguration scope (6.4): "MTD techniques were modelled to execute on all nodes in the simulated network … we did not incorporate this mechanism in our simulation due to time constraints and a lack of data on user profiles and network interactions, making it difficult to measure how MTD techniques affect the quality of service (QoS)." (p.43)
- Conclusion's strongest claim: "network shuffle-based MTD techniques consistently outperform diversity-based MTD techniques. However, it is noteworthy that the combination of both approaches, specifically Shuffle + Diversity, emerged as the most effective strategy for enhancing network security." (p.44)

## G. Transferable vs purpose-specific

Transfers to an honours dissertation evaluating existing MTD mechanisms against a new attacker model on a simulator:
- An untitled experimental-design paragraph at the head of the Evaluation chapter that states, in one place: the two parts of the evaluation and why the first is a "baseline" for the second; the factors and their level ranges; the checkpoint metric (NCR) and termination rule; the replication count with its purpose (p.33).
- Small parameter tables placed at the point of use (Table 2 networks, Table 3 execution times) rather than one omnibus table (p.33–34).
- Full-factorial small-multiple grids with rows = one factor, columns = the other, a fixed series order and NoMTD leftmost in every panel; zoom-in figures for the two panels the prose leans on (Figs. 8/10 → 11/12).
- Naming the factor-effect sub-sections by the factor ("Impact of MTD Interval", "Impact of Network Size") and stating the exception to each trend in the same paragraph as the trend (p.36).
- Deriving a distribution of percentage improvements across cells (Figs. 9, 13) so that a "by more than 130% on average" magnitude claim has a visible spread behind it.
- Each mechanism hypothesis marked as such ("It is assumed that …", "This may be because …") and the confounded factors (interval vs deployment frequency; size vs density) named explicitly in the limitations (p.41–42).
- Reusing the predecessor simulator's terms and declaring which of its scenarios/techniques were dropped and why (p.22, p.28).

Purpose-specific artefacts (GENG5512 report; simulator-rebuild project):
- The limitations chapter titled "Scope for Future Work" and its "due to time constraints" register (p.28, p.41, p.43) — a coursework-deadline convention.
- Means without dispersion despite 100 runs; "statistically significant" used without a test (p.33).
- The adversary reduced to one scenario, and attacker realism treated purely as future work (6.3).
- Execution-scheme comparison (Random/Alternative/Simultaneous) and the "Max Count" tally chart are artefacts of this report's scheduler contribution.
- The DAP_OSDiversity technique and the SimPy/DES exposition (Eq. 3–4) are contributions of the rebuild, not evaluation conventions.
- Two declared-but-unreported sensitivity analyses (p.28, p.32).
