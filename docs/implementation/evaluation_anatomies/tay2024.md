Structural facts worth naming:
- The experimental portion is **three chapters**, split by function rather than by experiment: §5 = design-of-experiment + numbers, §6 = interpretation, §7 = limitations. §6 and §7 both back-reference §5 by section number ("In Section 5.3, we explored…", p.26; "As discussed in Sections 6.1 and 6.2", p.27).
- Each §5 subsection has an identical internal shape: (i) a paragraph defining the hyperparameter and what it trades off, (ii) a sentence declaring the range tested *and its justification*, (iii) the figure, (iv) one to three paragraphs of numeric readout, deferring the "why" to §6.
- §5 opens with a roadmap paragraph naming every subsection in order ("Section 5.1 describes the baseline scenario … In section 5.2, various hyperparameters are adjusted … In section 5.3, attacker detection rate is studied … Finally in section 5.4, ablation studies are performed", p.19). §3 (p.10) and §4 (p.13) open the same way — a house pattern.

## B. Setup — what is declared before any result

- **Network configuration(s): NOT STATED.** No host count, no layer/subnet count, no topology generator, no service or vulnerability parameters, no network size of any kind appears anywhere in the document. The network is described only qualitatively: "The network module is a graph comprised of nodes and edges, which symbolise hosts and the connections between. Each node has IP addresses, operating systems, services, vulnerabilities, and user access credentials" (p.13). How many configurations were run: not stated (the text implies one, via "the specific simulation conducted in MTDSimTime and the parameters chosen for that context", p.25, but the parameters are never given).
- **Attacker model / scenarios: NOT STATED as a model.** The attacker is one sentence of inherited machinery: "The attacker module conducts attack operations, executing a sequence of attack actions on hosts within the network with the aim to compromise hosts" (p.13). No scenario names, no goals, no skill levels, no give-up rule, no bold-defined scenarios, no count of scenarios. There is exactly **one** attacker-side experimental knob, and it is a *defender-observability* knob rather than an attacker-behaviour knob: the attacker detection rate of §5.3 ("feeding information about the actions the attacker is taking to the model during the training process", p.23), varied "from 0% (no knowledge of the attacker's actions) to 100% (full knowledge of the attacker's actions)" (p.23) and appearing in Figure 6 as eleven levels (sensitivity_0 through sensitivity_1.0 in steps of 0.1, p.23 render).
- **Defence conditions:** five actions, listed once in prose: "The proposed model features five key MTD actions: IP shuffle, OS diversity, Service diversity, Complete topology shuffle, and the option not to deploy MTD" (p.14). The *scheduler* is the contribution: the inherited simulator is characterised as "time-based, deploying MTD into the network on a fixed schedule with no regard for the network security posture", and MTDShield converts it "from a time-based simulator to a reactive one" (p.13). **The fixed-interval scheduler is never run as a comparison condition** — MTDShield is never compared against the time-based baseline it replaces. Trigger interval / MTD frequency for any comparator: not stated.
- **"No defence" baseline: YES, but as a normaliser, not as a plotted condition.** §5.1 verbatim: "The goal is to explore a method that will allow us to easily compare sets of scores between models. The approach that we chose was to run the simulation with no MTD applied, simply running the Network and Attacker modules to get baseline scores for each of the five metrics. We will then normalize subsequent scores against these baseline values by dividing them, the obtain a value that represents a multiple of this baseline value. This allows for easy comparison between different models." (p.19). The no-MTD run is therefore the unit of the y-axis (every value is a multiple of it) and appears in no figure as a bar. Its absolute metric values are not reported. How many no-MTD runs were averaged to fix the baseline: not stated.
- **Metrics:** five, declared once at the head of §5.1 — "The performance of each model will be assessed using five key metrics: Attack Success Rate (ASR), Mean Time to Compromise (MTTC), Attack Path Exposure (APE), Return on Attack (ROA), and Risk" (p.19). Each is prose-defined in the §4.1 module descriptions rather than in §5 (HCR p.14; Number of Vulnerabilities and Number of Exposed Vulnerabilities p.15; Attack Path Exposure Score p.15; MTTC p.16; Downtime and Operational Impact for Node Replacement p.16; Time since last MTD p.16). No formulae are given for ASR, ROA or Risk. The metric *direction* (whether a higher normalised value is better for each of the five) is not stated. Note MTTC is spelled "MTCC" in the Figure 3 caption (p.20) and in the §4.1.2 body ("MTCC is a security metric that measures the average duration…", p.16) and "MTTC" elsewhere (p.16, p.19, p.28).
- **Composite score:** every bar carries a bold total (e.g. "10.77", p.20) and the prose treats that total as "model performance" ("The best performing model was gamma_0.85 (10.77)", p.20). That total is the arithmetic sum of the five normalised segment values (verifiable from the printed segment labels: 0.99+1.01+3.87+1.91+1.69 ≈ 9.46 for gamma_0.5, p.20). **The document never states that the five metrics are summed, never names the composite, and never states weights** — the additive convention is legible only from the stacked-bar figures.
- **Parameter table: NO.** The document contains **no tables at all** — there is no List of Tables in the front matter (p.5–6, which lists only a List of Figures), no "Table N" reference anywhere in the body, and pdfplumber finds no table regions on any of the 32 pages. Every parameter that is declared is declared in running prose.
- **Parameters that ARE declared (all in prose, all model-side):**
  - gamma: "vary gamma values from 0.50 to 0.99" (p.20); Figure 3 shows ten levels — 0.5, 0.6, 0.7, 0.75, 0.8, 0.85, 0.9, 0.95, 0.98, 0.99 (p.20 render), and the prose says "the 10 models tested" (p.20).
  - epsilon: "testing various epsilon values (ranging from 0.5 to 1.0)" (p.21); Figure 4 shows six levels (0.5–1.0 in 0.1 steps) × four decay rates.
  - epsilon decay: "Different gradual decay rates (from 0.980 to 0.998)" (p.21); Figure 4 panels are 0.98, 0.99, 0.995, 0.998 (p.21 render). §6.2 states the grid size: "Figure 4 in Section 5.2.2 showed 24 different models with varying combinations of epsilon and epsilon decay values" (p.25).
  - train start: "vary train start values (500 to 2000 experiences)" (p.22); Figure 5 shows four levels — 500, 1000, 1500, 2000 (p.22 render).
  - attacker detection rate ("sensitivity"): 0% to 100% (p.23); eleven levels in Figure 6 (p.23 render).
  - network architecture: dense 128 → ReLU → batch-norm → dense 64 → ReLU → batch-norm → 30% dropout (feature extraction, p.14–15); LSTM 64 (return sequences) → ReLU → batch-norm → LSTM 32 → ReLU → batch-norm → 30% dropout (time series, p.15–16); concatenate → dense 64 → ReLU → batch-norm → 30% dropout (fusion, p.16); dense output of five Q-values (p.16).
  - Not stated: learning rate, optimiser, minibatch size, replay-memory capacity, target-network update period n ("only copying the weights from the Main Network every n steps", p.18 — n itself is never given), the reward function, epsilon floor, number of training steps or episodes, state-vector length, time-series window length.
- **Replications: NOT STATED.** No run count, no seed, no seed convention, no episode count, no repetition of any configuration, no averaging statement. A grep of the full text for "seed", "run(s)", "trial(s)", "episode", "repeat", "iteration", "timestep" returns nothing declaring replication; the only near-mentions are "the limited run-time of the simulation" (p.25), "more studies need to be conducted to determine their performance in extended trials" (p.26) and "Increased Runtime and Simulation Space" (p.27) — all of them limitations, all about the length of a run rather than the number of runs. Each bar in every figure is one number with no stated provenance.
- **Horizon / termination rule: NOT STATED.** Simulation length is referred to only obliquely and only as a limitation: "due to the limited run-time of the simulation, placing too much importance on future rewards with high gamma values, which often delay beneficial short-term rewards, led to a scenario where these long-term benefits never fully materialised" (p.25).
- **Statistics: NONE.** No mean, no standard deviation, no confidence interval, no min–max, no significance test, no error bars on any of the five results figures (p.20–24 renders). Every comparison is a point-estimate percentage difference between two single numbers.
- **Anything else declared:** no hardware, no OS, no Python/TensorFlow/PyTorch version, no library, no code link for the author's own MTDShield (the only repository cited is the inherited MTDSimTime, ref [23], p.30), no wall-clock training time. AI-tool declaration on p.2: "I have used AI tools in the preparation of this report: Yes … Use of AI tools to check English."

## C. Results — how the numbers are shown

- **Order:** experiment-major, and inside that, model-hyperparameter first and threat-side second. §5.1 fixes the yardstick (baseline normalisation), then §5.2 tunes the agent (gamma → epsilon → train start), then §5.3 varies the one environment-facing knob (attacker detection rate), then §5.4 ablates the architecture. The ordering tracks the pipeline of *building* the controller — tune it, then stress it, then justify its parts — and §5.4 explicitly consumes §5.2's winner: "Figure 7 compares the best performing model from the previous sections with one that only has a time series or static feature extraction module" (p.24); the "complete" bar in Figure 7 is 11.00 (p.24 render), the same value as the §5.2.2 winner epsilon_0.5/decay 0.99 (p.21 render).
- **Every figure in the evaluation portion.** All five results figures are the **same chart**: a five-segment stacked vertical bar chart, one bar per trained model, y-axis labelled "Values" (no units, no axis title elsewhere), x-axis unlabelled with rotated model-name tick labels of the form `<parameter>_<value>`, every segment annotated with its numeric value inside the segment, and the bar total printed in bold above the bar. No legend on any of them — the segment key exists only in the Figure 3 caption. No error bars anywhere. Bars are **sorted in descending order of total score, not by parameter value**, in Figures 4, 5, 6 and 7; Figure 3 alone is ordered by parameter value (0.5 → 0.99).
  - **Figure 1** (p.13): block diagram, "Overview of MTDShield System Architecture" — two coloured containers, "System" (green: (a) Attacker Operations → (b) Network, (c) MTD Operations, with labelled edges "Compromise Hosts", "Interrupt Attack Actions", "Reconfigure Network") and "MTDShield" (orange: (d) Feature Extraction Module, (e) Time-Series Analysis Module, (f) Feature Fusion Module, (g) Q-Network Output Layer, (h) Action Selection), joined by "Network Security Metrics"/"Static Features"/"Temporal Features" in and "Selected MTD Action" out. Setup, not results. The green/orange split is the inherited-vs-contributed boundary and is stated in the prose ("highlighted in green", "highlighted in orange", p.13).
  - **Figure 2** (p.17): diagram, "Double DQN Model Training". Setup, not results.
  - **Figure 3** (p.20): stacked bars, caption "Impact of Gamma on model performance (Top- down: Risk, ROA, APE, MTCC, ASR)". x = ten models, gamma_0.5 … gamma_0.99 (parameter order); y = "Values"; series = the five normalised metrics as stack segments, keyed top-down in the caption; totals 9.46 … 10.77.
  - **Figure 4** (p.21): 2×2 grid of the same stacked-bar chart, caption "Impact of Epsilon and Epsilon Decay on Model Performance". Facets = epsilon decay, sub-captioned "(a) Epsilon Decay 0.98", "(b) Epsilon Decay 0.99", "(c) Epsilon Decay 0.995", "(d) Epsilon Decay 0.998". x within each panel = six models, epsilon_0.5 … epsilon_1.0, **sorted by descending total** so the x-order differs panel to panel (panel (a) runs 0.6, 0.7, 0.9, 0.5, 0.8, 1.0; panel (b) runs 0.5, 0.6, 1.0, 0.8, 0.7, 0.9); y = "Values"; totals 9.48 … 11.00. 24 bars total.
  - **Figure 5** (p.22): stacked bars, caption "Impact of Train Start on Model Performance". x = four models, train_start_2000, _1500, _1000, _500 (descending total, which here coincides with descending parameter value); y = "Values"; totals 10.39, 9.77, 9.70, 9.63.
  - **Figure 6** (p.23): stacked bars, caption "Impact of Attacker Detection Rate on Model Performance". x = eleven models, sensitivity_1.0, _0.9, _0.8, _0.7, _0.6, _0.4, _0, _0.2, _0.3, _0.1, _0.5 (descending total — so the parameter order is scrambled after the fourth bar, which is itself the visual form of the paper's "cutoff" claim); y = "Values"; totals 10.78 … 9.48.
  - **Figure 7** (p.24): stacked bars, caption "Impact of Removing Modules on Model Performance". x = three models, `complete`, `time_series`, `static`; y = "Values"; totals 11.00, 10.30, 10.11.
- **Tables:** none in the evaluation portion or anywhere in the document.
- **How the baseline appears in each:** it does not appear as a bar in any figure. It is the denominator of every plotted number ("a value that represents a multiple of this baseline value", p.19), so the no-MTD condition is the implicit y = 1.0 per metric, un-drawn and never labelled. No reference line is drawn at the baseline.
- **How comparisons are stated in prose:** **magnitude-first, always as a percentage difference between two single models**, and always paired with the named winner and loser. The template recurs verbatim across all five subsections:
  - "The best performing model was gamma_0.85 (10.77) while the worst performing model was gamma_0.5 (9.46) which is a 12.16% difference." (p.20)
  - "The best performing model was epsilon_0.5 with a decay of 0.99 (11.00) in Figure 4b while the worse performing model was epsilon_1.0 with a decay of 9.48 in Figure 4a which is a 13.82% difference." (p.22) [reproduced verbatim; the decay value is replaced by the score in the second clause]
  - "Figure 5 above shows that having a train start of 2000 (10.39) was the best performing model of the 4 tested. This model outperformed the next closest model by 5.97% and the worst performing model by 7.31%." (p.23)
  - "The best performing model outperformed the other 2 models by 6.36% and 8.09% respectively." (p.24)
  - Per-metric spreads are then reported as ranges across the whole set: "Risk and ROA affected the overall score of the models the most with the range being as much as 41.78% and 40.26%. While the difference in APE was less than the top 2 at 10.62% … ASR and MTTC had less influence on the overall performance throughout the 10 models tested, with only a 3.53% and 6.57% difference respectively" (p.20); "Risk and ROA once again had the greatest difference with a percentage change of 41.61% and 49.48%. APE, MTCC and ASR had swings of 11.66%, 9.85% and 5.75% respectively" (p.22).
  - **Recommendation form is absent from §5 and appears only in §8**: "Models with gamma (between 0.75 and 0.90) and epsilon (favouring early exploitation) values exhibited the best performance." (p.28)
  - Shape claims are made about the chart itself: "In general, the chart follows a bell-shaped pattern, with model performance increasing as gamma grows from 0.5 to 0.85 before dropping as gamma approaches 0.99." (p.20)

## D. Narrative — the claims, in order

1. Baseline convention (§5.1, p.19): normalising every metric by a no-MTD run makes model scores commensurable — "This allows for easy comparison between different models."
2. Gamma is unimodal (§5.2.1, p.20): "the chart follows a bell-shaped pattern"; best gamma_0.85 (10.77), worst gamma_0.5 (9.46), 12.16% apart.
3. The composite is driven by two metrics (§5.2.1, p.20): "Risk and ROA affected the overall score of the models the most"; ASR and MTTC move least (3.53%, 6.57%). Restated for epsilon (p.22) and again for train start ("most of the gains that this model made were in the Risk and ROA metrics", p.23) — the same claim is made three times from three experiments.
4. Low epsilon wins (§5.2.2, p.22): "the lower values of epsilon (0.5, 0.6 and 0.7) outperformed the higher values of epsilon (0.8, 0.9 and 1.0)"; and a cross-panel regularity — "the best performing model in each subplot had the highest score in Risk". Epsilon moves the metrics more than gamma does ("the variance was higher compared to gamma", p.22).
5. Larger train start wins mildly (§5.2.3, p.23): 2000 best, +5.97% over the next.
6. Detection rate has a threshold (§5.3, p.23): "The first 4 models' sensitivity_1.0 – sensitivity_0.7 demonstrate a trend where performance decreases marginally as detection rate decreases (2.60%). However, it can be observed that there is a cutoff after sensitivity_0.7 where the performance drops by 5.33% from sensitity_0.7 – sensitivity_0.6. From there on, the performance of the models no longer seems correlated with their attacker detection rate."
7. Ablation is small (§5.4, p.24): complete model beats the two reduced models by 6.36% and 8.09%; but it "under performed in the APE metric by 13.14% and 4.6% compared to the two incomplete models" — the one place a result is reported against the paper's own contribution.
8. Then §6 supplies the mechanism for each of 2, 4, 5, 6, 7 in turn (see §F below), and §8 lifts 2 and 4 into the conclusion's recommendation (p.28).

**Claims about the ATTACKER's properties from the data:** none. The attacker is never measured. Every data claim is about the controller (the defence). Attacker-side language appears only in three roles: (i) as an unmeasured design assumption ("executing a sequence of attack actions on hosts", p.13); (ii) as a *defender-side observability* variable — §5.3 varies how much of the attacker the defender sees, not what the attacker does, and its finding is about the model's ability to use information ("This suggests that these models were able to integrate the information they received about the attacker's actions into their strategies", p.26); (iii) as an aspiration in the introduction and conclusion ("Demonstrates how continuous system changes through MTD disrupt attackers' reconnaissance and exploitation efforts, reducing the risk of advanced persistent threats (APTs)", p.8; "MTD introduces unpredictability by continuously altering system configurations", p.28) — neither is evidenced by any figure. The word "APT" appears once (p.8) and never in §5–§7.

## E. Sensitivity / parameter analysis

Sensitivity analysis is not an adjunct here — **it is the entire evaluation**. §5.2 and §5.3 are nothing but parameter sweeps, and §5.4 is an architecture sweep.

- Parameters swept: gamma (10 levels, 0.5–0.99, uneven spacing: 0.5, 0.6, 0.7, 0.75, 0.8, 0.85, 0.9, 0.95, 0.98, 0.99); epsilon (6 levels, 0.5–1.0) × epsilon decay (4 levels, 0.98–0.998); train start (4 levels, 500–2000); attacker detection rate (11 levels, 0–1.0); module presence (3 conditions: complete / time_series only / static only).
- Design: **one-at-a-time for gamma, train start, detection rate and ablation; a full 6×4 = 24-cell factorial grid for epsilon × epsilon decay** (§6.2 calls it "24 different models", p.25). Whether the non-swept hyperparameters are held at the previous section's winner is not stated (§5.4 says only "the best performing model from the previous sections", p.24).
- **Range justification is given for every sweep**, and it is the document's most consistent convention. Verbatim:
  - gamma: "The most common values of gamma used in other experiments range from 0.9 to 0.99 as they focus on long term strategies. This experiment will instead vary gamma values from 0.50 to 0.99 to observe how the agent's focus on short-term versus long-term rewards affects its ability to learn an optimal policy. The lower values are used to study the trade-off between immediate and future rewards in faster-changing environments [33, 35]." (p.19–20) — i.e. the range is justified *against the literature's default*, with the deviation argued.
  - epsilon: "The rationale for not testing below 0.5 is that the model would lean towards exploitation too early on, which may lead to premature convergence and suboptimal policies due to insufficient exploration [28]. Different gradual decay rates (from 0.980 to 0.998) allow us to view the impact of changing epsilon without compromising model performance too significantly [34]." (p.21) — a justification for the *lower bound*, with a citation.
  - train start: "This experiment will vary train start values (500 to 2000 experiences) to explore the trade-off between early training speed and long-term stability." (p.22) — the trade-off is named; the endpoints themselves are not justified.
  - detection rate: the range is the natural 0–100% and the framing is a real-world artefact — "Most traditional network systems will have some form of an Intrusion Detection System (IDS) … However, as attacker evasion techniques and zero-day attacks become more and more sophisticated, the ability of an IDS to offer credible and timely information becomes less impactful." (p.23)
- Reporting: one figure per sweep, inside the results section; no appendix, no separate sensitivity section, no table of the swept grid.
- Claim supported: for §5.2, an operating range for the controller ("Models with gamma (between 0.75 and 0.90) and epsilon (favouring early exploitation) values exhibited the best performance", p.28); for §5.3, a robustness threshold; for §5.4, the necessity of the contributed modules.
- **Not swept:** anything about the network, the attacker, the MTD techniques, the MTD interval, or the reward function.

## F. Discussion / limitations

**Discussion is a separate chapter (§6, p.25–26), and limitations are a third separate chapter (§7 Future Works, p.27).** Neither is folded into results. §6 mirrors §5 one-for-one — five subsections, same names, same order — and contains no new numbers; it re-reads each §5 result and supplies a mechanism. There is no "threats to validity" heading, no comparability caveat against any other paper or simulator (no cross-paper comparison is attempted anywhere in the document), and no ethics/reproducibility statement.

The §6 scoping paragraph is the document's central caveat, verbatim:
> "The results obtained in Section 5 align with the specific simulation conducted in MTDSimTime and the parameters chosen for that context. However, these results may vary for networks with different configurations or when using other MTD techniques. By applying the evaluation methods described, we can analyse how each parameter impacts the relevant metrics. This, in turn, allows us to identify suitable parameter ranges for different types of network environments." (p.25) — note the move: the *numbers* are conceded to be configuration-specific, and the *method* is claimed as the transferable object.

Mechanism claims in §6, verbatim where the phrasing matters:
- Gamma (§6.1, p.25): "For models with higher gamma values (>0.9), we observe an increased APE score compared to models with lower gamma values (<0.75). A higher gamma in reinforcement learning encourages the agent to prioritize long-term strategies … On the other hand, models with lower gamma values show proportionally higher Risk and ROA scores." And the horizon concession: "due to the limited run-time of the simulation, placing too much importance on future rewards with high gamma values, which often delay beneficial short-term rewards, led to a scenario where these long-term benefits never fully materialised."
- Epsilon (§6.2, p.25–26): the result is flagged as contrarian — "the best performing models were the ones that started with low epsilon values (0.5 – 0.7) which runs contrary to the epsilon-greedy policies that other reinforcement learning models tend to favour [28]" — and then bounded by the simulator: "This strategy works well in the simulated environment due to the limited runtime, but more studies need to be conducted to determine their performance in extended trials." (p.26)
- Train start (§6.3, p.26): "While there was a small improvement by increasing the train start due to improved quality of experiences stored in the memory buffer, this value shouldn't be pushed too far due to the increased computational burden it imposes on the system when training."
- Detection rate (§6.4, p.26), hypothesis explicitly flagged as such: "We hypothesize that this is due to the model receiving incomplete information about the attacker's actions. Once the detection sensitivity falls below 0.7, the model can only acquire attacker information sporadically, resulting in performance levels like those of models with no information at all."
- Ablation (§6.5, p.26), a concession against the paper's own contribution: "While the complete model outperformed both incomplete ones, the difference in performance was not as large as expected. It seems that despite losing one of the critical elements of the model, it is still able to make sound judgements on when and what MTD techniques to deploy."

§7 Future Works carries the external-validity limitations, each stated as a limitation and then converted to a work item:
- Simulator realism (§7.1, p.27): "The results discussed in Sections 5 and 6 are all specific to the MTDSimTime simulator which is a representation of a network. Therefore, the findings made in the simulator may not necessarily be applicable to real networks. Integrating external intrusion datasets into the simulator would provide a valuable opportunity to test the robustness and generalisability of the MTDShield in real-world scenarios."
- Network size / runtime as a confound for the headline finding (§7.2, p.27): "As discussed in Sections 6.1 and 6.2, certain values of gamma and epsilon have stood out as leaders in this study which run contrary to the values used in many other RL studies. One of the reasons could be the size of the network resulting in smaller runtime. The models need to be tested on larger, more realistic networks to determine if these parameters can still come out on top."

## G. Transferable vs purpose-specific

**Transfers to an honours dissertation evaluating existing MTD mechanisms against a new attacker model on a simulator:**
- The **three-chapter split by function**: §5 numbers → §6 mechanism, subsection-mirrored one-for-one → §7 limitations-as-future-work. The mirroring is mechanical and cheap to execute, and it keeps interpretation out of the results narration entirely. It also means every result gets a "why" paragraph by construction — none is left un-interpreted.
- The **roadmap paragraph** opening every numbered chapter, naming each subsection in order (p.10, p.13, p.19). A house convention of this supervisor's students; low cost, high navigability.
- **Justifying every swept range against the literature's default, and arguing the deviation** (gamma p.19–20 is the model case: "The most common values … range from 0.9 to 0.99 … This experiment will instead vary gamma values from 0.50 to 0.99 … The lower values are used to study …"). Also justifying a *bound* rather than only a range (epsilon's floor, p.21). This is the single most reusable convention in the document.
- **Normalising every metric by an explicit no-defence run** so heterogeneous metrics become commensurable multiples (§5.1, p.19), with the normalisation scheme declared before any result and the reason given ("This allows for easy comparison between different models").
- Naming each configuration with a **`<parameter>_<value>` model id** and then using that id as the subject of every sentence about it ("The best performing model was gamma_0.85 (10.77)", p.20) — figure tick labels and prose share one vocabulary.
- **Per-experiment magnitude reporting** — winner, loser, and the percentage between them, in one sentence, every time (p.20, p.22, p.23, p.24) — plus a second sentence decomposing the spread per metric. Contrast with brown2023, which reports only orderings and no magnitudes.
- Flagging a result as **contrary to the literature** and then bounding it with the confound that could explain it (§6.2 + §7.2, p.26–27: low epsilon wins, *but* "One of the reasons could be the size of the network resulting in smaller runtime").
- Reporting a result **against your own contribution** and keeping it (the APE under-performance of the complete model, p.24; the "not as large as expected" ablation, p.26).
- Conceding the numbers and claiming the method (p.25).

**Purpose-specific artefacts (RL-controller thesis; 8000-word GENG5512 report):**
- The sweep axes are all **hyperparameters of a learner** — gamma, epsilon, epsilon decay, train start — which exist only because the contribution is an RL agent. An evaluation of MTD mechanisms against an attacker model has no analogue for these; its sweep axes would be network, attacker and defence parameters, none of which are swept here.
- **The ablation study** is an ML-paper convention (remove a module, re-measure) and presupposes a modular learned architecture.
- **The absence of any network or attacker configuration** is an artefact of the contribution being the plugin rather than the substrate: the substrate is cited (ref [23], p.30) and inherited wholesale, so its parameters are treated as out of scope. A dissertation whose object *is* the substrate's behaviour cannot inherit that silence.
- **The single chart type for all five results figures** (stacked bar, sorted by total, values printed in-segment) is efficient here because every experiment produces the same five-metric vector; it would not survive a results section with heterogeneous outcome shapes.
- **Sorting bars by score rather than by parameter value** (Figs 4–7) suits a "which configuration wins" question; it destroys the shape of a dose-response relationship, which is exactly the reading Figure 3 (parameter-ordered) supports and Figure 6 (score-ordered) does not.
- **Zero replication, zero dispersion, zero tables** — no run count, no seeds, no error bars, no parameter table anywhere in 32 pages. Recorded here as the local genre's floor, not as a target.
- **The composite score left undefined** (bar totals are the unstated sum of five normalised metrics, and metric direction is never declared) works only because every comparison in the document is within the same five-metric vector.
