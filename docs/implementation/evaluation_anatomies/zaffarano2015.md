## B. Setup — what is declared before any result

Read this as "what the paper declares it *will* configure", not "what was run".

- **Network configuration(s)**: **no concrete configuration is given** — no host count, no subnet count, no topology instance, no diagram of a test network. What is declared is a *generator*: "a range of varied network topologies containing a heterogeneous collection of hosts running versions of Linux and Microsoft Windows, along with associated routers and other network components" (md L167–171, p.6); a hierarchical structure "in line with observed power law distribution models" with node counts drawn from "a bounded Pareto distribution, roughly following the techniques suggested by Crovella et al." for a "Heavy-Tailed (skewed) distribution of nodes" (md L196–205, p.6). Chosen against an explicit alternative: "our approach differs from pure random topological generation approaches, such as the Waxman method … The disadvantage of this approach is that the network has an unnaturally even distribution of nodes, with less bottlenecks and other network elements that can affect performance behavior" (md L189–195, p.6). Topologies are organised by *mission template*: "each mission template represents a range of different possible topologies that would support such a mission, along with associated network mission characteristics" (md L186–188, p.6). Server roles are enumerated in Table 1 (6 rows × 2 cols: Application Server / User & database middleware; Message server / Chat server; File Server / Connection through FTP; Mail Server / Email transmission; Database Server / SQL, data retrieval; Web Server / Browser usage) (md L144–152, p.6). Clients: "a variable number of clients" (md L234, p.7) — count not stated.
- **Attacker model / scenarios**: **one attacker model, no named scenarios**. It is an *activity model* (§3.2.2), defined as a set of tasks drawn from Cyber Kill Chain stages, explicitly **not** as a sequential agent: "Our attacker model will aim to perform activities from several stages of the Cyber Kill Chain, and not necessarily in order" (md L272 + L209–210, p.7–8). Basis: "we consider the Cyber Kill Chain®" (md L256–259, p.7), citing Hutchins et al. [5]. The paper hedges the model in the same breath it adopts it: "While no single attacker model can perfectly capture the workflow of every attacker, the Cyber Kill Chain has been proven to be a useful model for describing the high-level process that most serious attackers will follow" (md L260–263, p.7). The concrete attacker instrument is Table 2 "Attack (APT) Components" — 5 rows × 3 cols (Stage | Potential Sensor | Data Collected): Discovery / nmap / "assesses network visibility"; Delivery / ncrack / "dictionary attack success or failure"; C2, Exfiltration / ncat / "ability to successfully establish a backdoor"; Action / read, write, execute / "ability to run, modify, delete, create; illustrates the ability to perform desired actions (including privilege escalation)"; Propagation / Discovery and Delivery combination / "ability to maneuver within the network" (md L279–296, p.8; verified on the page render). **Note the mismatch worth recording**: Table 2's five stage names (Discovery, Delivery, C2/Exfiltration, Action, Propagation) are *not* the seven Cyber Kill Chain stage names the paper itself glosses (Reconnaissance, Weaponization, Delivery, Exploitation, Installation, Command and Control, Actions on Targets, md L229–271, p.7–8); the prose then refers to "The Discovery stage" (md L272, p.7) as if it were one of them. No attacker skill levels, no give-up rule, no attacker decision procedure, no ordering — by design.
- **Defence conditions**: **no MTD is named anywhere in the paper as the technology under test.** The condition set is binary and generic: "With MTD" vs "Without MTD" (Table 3, md L279–282, p.8). Related-work MTDs (IP hopping [10,11,12], game-theoretic platform selection [3], RL [13], control theory [1]) are cited in the introduction only (md L42–61, p.3) and never instantiated. No mechanisms, no schedulers, no MTD parameters, no trigger-time distribution. A **no-defence baseline is explicit and load-bearing**: "Runs with no MTD deployed represent a baseline run, which can be contrasted to effects measured during identically configured runs with a deployed MTD technology. This contrast drives our metrics" (md L293–297, p.8). Note *two* baselines exist, not one — Table 3 names "mission baseline" and "attacker baseline" separately.
- **Parameter table**: **NO.** There is no parameter table, no distribution table, no constant anywhere in the paper except two: the bounded Pareto for node counts (unparameterised, md L204, p.6) and a single illustrative task rate — "Each task will be repeated at timed intervals. For instance, the client will send 60 emails, one every second" (md L251–253, p.7). Tables 1–4 are all definitional (server roles, sensors, the 2×2 matrix, metric glosses), not parametric.
- **Replications**: **NOT STATED** — no run count, no seeds, no episodes, no horizon. Termination is stated only as a *policy*, and only for the outer experiment loop: "the process is repeated until the experiment stopping condition is reached (which may be in a time limit, or reaching certain pre-identified statistical significant measurements for certain metric measurements)" (md L98–102, p.4). Nothing states how many topologies, missions or MTDs constitute one experiment. §4 says only "Metrics process data gathered from multiple runs, where each run represents a combination of a mission, topology, adversary model, and MTD deployment. Some of the runs will have no adversary model and/or no MTD deployed" (md L289–293, p.8) — which implies a factorial design over {mission × topology × adversary × MTD} with empty levels for adversary and MTD, but the paper never says "factorial", never lists levels, and never gives a cell count.
- **Statistics**: **no test, no estimator, no interval is named.** Two statistical gestures only: "Metrics are derived from the statistical differences between these interactions during runs when an MTD is not deployed (the baseline) and when it is deployed" (md L76–80 right col, p.4) — "statistical differences" is left undefined; and the stopping-condition phrase "certain pre-identified statistical significant measurements" (md L101–102, p.4, sic). The only estimator actually written down is the **arithmetic mean over tasks**, which is the body of all four metric formulae (§4.1–4.4). The paper itself flags the mean as a weak choice (see F).
- **Anything else declared**: virtualisation stack — "currently VMware vSphere, but the workflow can be ported to other virtualization systems, or adapted to physical cyber-ranges" (md L94–97, p.4), plus ESXi and "the dynamic creation of linked clones" (md L172–175, p.6). Toolchain: Siege's **Cyber Quantification Framework (CQF)** with "a user-friendly interface for designing large-scale experiments … and a workbench for data analysis and visualization" (md L91–99, p.4), a browser-based drag-and-drop configuration UI (Figure 4, md L112, p.5) shown at `10.42.13.56:8080/cqf/cqf.html` with a software palette (Chrome, Apache, Samba, Easy FTP Server, PostgreSQL, Java, Adobe, chat, mail) and a per-VM parameter panel (Number of Copies, Target VM, Clones, Version, Admin/Root Username, Admin/Root Password, User Username, User Password). Attacker tooling: nmap, ncrack, ncat, and read/write/execute (Table 2, p.8). Data retention: "we preserve all data collected in a database which is dynamically linked to our metrics" (md L451–453, p.10). No hardware spec, no VM counts, no software versions, no code or data availability statement.

(md L216–221, p.8).

## D. Narrative — the claims, in order

There is no results narrative. The paper's argumentative sequence — the claims it actually makes, in order, all of them about *how to measure* rather than about *what was measured*:

1. **Static defence is brittle, but MTD is not deployed because it may cost the mission.** "flexible proactive defensive measures such as Moving Target Defense (MTD) have as much potential to interfere with a network's ability to support the mission as they do to defend the network" (abstract, md L14–17, p.3).
2. **Therefore both sides must be quantified together.** "it is important to be able to quantify the security benefits associated with each approach along with potential productivity costs that may be introduced (either through the overhead associated with deployment of the system, or potential interference such a system may introduce to legitimate network operations)" (md L22–29 right col, p.3).
3. **Of the four available methods, testbeds are the right instrument.** The methods are ranked as a cost/accuracy tradeoff — "pure analytical approaches based on mathematical analysis, coarse grained simulation, data gathered from testbeds or cyber ranges of representational networks with real missions, and experimentation and instrumentation of real operational networks. Each of these approaches represents a different tradeoff between analysis cost and accuracy of results" (md L29–35 right col, p.3) — and the paper takes a position: "The focus of this paper is on metrics and analysis approaches that utilize cyber testbeds, as it is our position that this represents the most realistic data that can be gathered short of operational deployment experiments, which are often implausible without having first gathered strong evidence that such experiments are worthwhile and will cause no harm to ongoing operations" (md L36–41 right col, p.3). *Note for our purposes: simulation is explicitly ranked below testbeds here, and the ranking is asserted, not evidenced.*
4. **No single tradeoff point is universally right, so publish multiple metrics and keep the raw data.** "Security, productivity, and the appropriate tradeoff between the two cannot be statically evaluated in way that is equally applicable to all parties considering the potential deployment of an MTD technology. As such, our approach is to define multiple metrics that measure different areas of potential interest, and to persist and maintain the raw data from which metric results are derived" (md L75–81, p.4, "in way" sic).
5. **The CIA triad is the traditional frame and it is insufficient.** Traditional design quantifies "Confidentiality, Integrity, and Availability of data [8]" (md L103–110, p.4); "Our approach is inspired by this approach, but is modified to address information operation issues that the traditional approach does not directly address. For example, there are conditions under which an MTD might fail to stop an attack, but is still able to monitor and log much more fine grained detail on attack operations that allow for improved attribution or post-attack characterization of the attacker. Such benefits are important, but not well represented in traditional information assurance metrics" (md L64–72 right col, p.4). *Availability is silently dropped and Productivity and Success added; the paper never says so explicitly.*
6. **Model both parties' objectives and difference them against a no-MTD baseline.** "In our approach, we explicitly model a range of potential attacker and defender (or mission) objectives, and then run multiple experiments to collect data on the interaction between these objectives and the MTD. Metrics are derived from the statistical differences between these interactions during runs when an MTD is not deployed (the baseline) and when it is deployed" (md L72–80 right col, p.4).
7. **Assess over a range of topologies, not one.** "To properly assess an MTD's applicability to a mission, a variety of mission relevant topologies should be assessed" (md L156–157, p.6), and generate them with realistic (heavy-tailed) rather than uniform-random structure (md L189–205, p.6).
8. **Prefer instrumentable synthetic activity to realistic traffic.** "Rather than using network traffic simulators, which are often based on mimicking the load and traffic behaviors of real networks, we are using the concept of activity models … The activity model approach is not intended to produce traffic with the most realistic dynamics, but rather to be instrumentable, reproduceable, and immediately sensitive to the characteristics of MTDs under consideration, namely, their effectiveness and their cost" (md L124–137, p.5). *An explicit realism-for-measurability trade, stated as a virtue.*
9. **Trade attacker realism for coverage of the kill chain.** Sampling stages out of order "makes the attacker model less realistic, in some sense, but improves the data that it provides" (md L210–212, p.8), because otherwise late-stage effectiveness is unobservable — "if a given MTD is particularly successful at preventing reconnaissance and delivery, it may be very difficult to obtain real-world data about the MTD's effectiveness against later Cyber Kill Chain stages" (md L212–216, p.8). **This is the paper's single most transferable methodological argument.**
10. **Do not read a per-stage failure as a verdict on the MTD.** "MTD defenses are not designed to provide complete security against actions at every stage of the Cyber Kill Chain. Instead, different MTD technologies provide varying degrees of protection against actions at each stage" (md L268–272, p.7); "it will be important to include representative tasks from a variety of the kill chain stages, but also to recognize that an MTD's inability to prevent certain types of activities is not necessarily an indictment of its intended effectiveness" (md L222–225, p.8).
11. **Separate collected data from computed metrics, so metrics can be revised without re-running.** (md L368–376, p.9 — quoted in F.)
12. **Blend the eight metrics only at the end, with customer-chosen weights.** (md L436–449, p.10 — quoted in H.)

**Does the paper make any claim about the ATTACKER's properties from data?** No — no data exists. It does, however, structurally *provide for* attacker-side claims in a way most MTD papers do not: four of the eight metrics (Attack Productivity, Attack Success, Attack Confidentiality, Attack Integrity) are properties of the attacker's task stream, and the argmax formula in §4.2 is explicitly designed to yield an attacker-side statement ("the kill chain phase against which the MTD appears to be most effective", md L372–375, p.9). The one attacker-side claim the paper does state is a **hypothesis, flagged as untested**: "We have an informal hypothesis that some MTDs that are beneficial in ensuring confidentiality of mission information may also help preserve the confidentiality of attacker information, at least if the attacker already has access to compromised hosts and can generate traffic on the network. Because we will test activities representative of different stages in the kill chain, we hope to be able to confirm or refute this hypothesis" (md L399–406, p.10).

## E. Sensitivity / parameter analysis

**Not present** — no parameter is varied, because no parameter is fixed and no run is reported. Three places nonetheless *declare an intent* to vary something, and are the closest the paper comes:

- **Scale**: "To ensure metrics can be effectively calculated that account for scalability effects, we need to be able to generate topologies of different scales and complexities" (md L182–184, p.6) — the intended axis is topology scale; no range, no levels, no justification of levels.
- **Mission type**: "each mission template represents a range of different possible topologies" and this "allows us to not only analyze data across all mission types, but also specify effectiveness for a subset of network characteristics and mission types of interest to a potential user of the MTD under test" (md L186–188 + L207 / p.6 right col) — i.e. an intended stratified re-analysis by mission type and network characteristic.
- **Post-hoc re-analysis instead of re-running**: the paper's substitute for a sensitivity section is the claim that the retained raw data permits new questions later — "This allows us to leverage our metrics to answer questions developed after our experiments. For example, if you wanted to determine if the effectiveness of the MTD was dependent on network policy, you could rerun metrics on the data with different network policies and measure the effects" (md L453–459, p.10). Note this only works for questions answerable by re-computation over existing data, not for questions requiring a different configuration — the paper does not distinguish the two cases.

No factorial design is declared; no ranges are justified; no sensitivity figure or table exists; there is no appendix.

## F. Discussion / limitations

**No discussion section and no limitations section exist.** §5 CONCLUSION (md L390 right col, p.10) is six sentences of restatement — "In this paper we presented an overall approach to metric design for Moving Target Defense technology for network defense. Our approach utilizes a cyber testbed which can be rapidly configured and reconfigured to run a series of tests such that large quantities of data can be gathered and analyzed. We also presented details on our test design, cyber testbed, and Siege's Cyber Quantification Framework." — and states no finding, no limitation and no future work.

The paper's self-criticism is instead **embedded in the metric definitions**, one caveat per metric. These are the only limitation sentences in the paper, and they are worth quoting because each pairs a definitional choice with the objection to it:

- **On the mean as an estimator, and on the data/metric separation (§4.1)**: "We have defined productivity in terms of the duration attribute. While there may be other measures that could also be rightly called productivity, we expect that it is uncontroversial to assume that decreased duration is typically a good result for mission tasks, and that increased duration of attacker tasks is typically a good result from a defensive standpoint. However, we recognize that the arithmetic mean of duration may not be the single best indicator of task time: a single outlier could change the average task time significantly, even though the majority of task durations actually change in the other direction. These types of considerations have led us to make a clean distinction between the data that we collect (that is, the task attributes), and the metrics that we define based on this data. If a flaw should be discovered in a metric definition, or an incremental improvement is proposed, it may not be necessary to rerun tests, but rather only to compute new values from the data. This is an important benefit of our approach." (md L357–376, p.9)
- **On the coarseness of the success attribute (§4.2)**: "At this early stage in our MTD experimentation, we are focusing simply on the success or failure of all tasks in a mission model, but we expect that by assigning additional attributes to tasks, we can characterize the behavior of MTDs much more specifically." (md L356–362, p.9)
- **On the operationalisation of exposure (§4.3)**: "In principle, there are many ways in which information could be exposed (e.g., being stored in a database in such a way that a web application presents it to users), but in these initial experiments, we simply refer to whether information is visible in plaintext in network traffic." (md L394–398, p.10)
- **On measuring corruption without weighting its consequence (§4.4)**: "Note that some types of information are much more sensitive to information corruption than others. In encrypted data, even a single bit of corruption may render a transmission useless, but in an analogue audio transmission, static is unpleasant, but may cause no significant loss of functionality. Our activity models are based on digital information where the amount of corruption can be easily measured, but we stress that we are measuring how much an MTD may corrupt data, not how significant that corruption would be in practice." (md L423–434, p.10) — *the sharpest comparability caveat in the paper: it measures a quantity, not its importance.*
- **On attacker-model realism (§3.2.2, the closest thing to Brown's V.A)**: "While no single attacker model can perfectly capture the workflow of every attacker, the Cyber Kill Chain has been proven to be a useful model for describing the high-level process that most serious attackers will follow." (md L260–263, p.7) and "This makes the attacker model less realistic, in some sense, but improves the data that it provides." (md L210–212, p.8)
- **On activity-model realism (§3)**: "The activity model approach is not intended to produce traffic with the most realistic dynamics, but rather to be instrumentable, reproduceable, and immediately sensitive to the characteristics of MTDs under consideration" (md L132–137, p.5).

**Two internal inconsistencies worth recording** (record, not judge):
1. The roadmap promises "we describe the intent for the rest of the effort in Section 4.5" (md L56–58, p.3), but §4.5 "Overall Metrics" (md L436–459, p.10) describes metric aggregation and data retention; it contains no work plan, no schedule and no statement of what remains to be done.
2. §4.1 defines `Productivity(M,ν)` as the **mean of the duration attribute** (md L318–319, p.8) but then glosses it twice as a **rate**: "Mission productivity is the rate at which mission tasks are completed" (md L322–323, p.9) and Table 4 "Mission Productivity can be measured by the rate at which mission tasks are completed" (md L333–334, p.9). A mean duration is not a rate, and it moves in the opposite direction (higher mean duration = lower productivity). The paper's own direction sentence — "decreased duration is typically a good result for mission tasks" (md L360–361, p.9) — is consistent with the *formula*, not with the *gloss*. Anyone citing "productivity" from this paper must say which of the two they mean.

## G. Transferable vs purpose-specific

**Transfers** to an honours dissertation evaluating existing MTD mechanisms against a new attacker model on a simulator:

- **The 2×2 experimental matrix (Table 3, p.8)** as a one-table statement of design: {mission model, attacker model} × {without MTD, with MTD} → {mission baseline, cost to mission; attacker baseline, effectiveness}. It makes "effectiveness" and "cost" *definitionally* the two off-diagonal differences rather than rhetorical labels, and it forces a no-MTD baseline into the design rather than leaving it as an optional extra series.
- **Defining a metric as the mean of one declared, per-task, observable attribute**, with the attribute list fixed *before* the metrics and the formula written out (`(1/|T|) Σ_{τ∈T} ν(τ, a)`). One formula shape, four attributes, eight metrics — cheap to state, impossible to misread.
- **The clean data/metric separation and its stated payoff**: collect attributes, define metrics over them, so that a metric flaw costs a recomputation and not a re-run (md L368–376, p.9). Directly applicable to a simulator with an event log — and it is the argument for logging per-action attributes rather than only end-of-run aggregates.
- **The both-sides framing**: every metric instantiated once for the defender/mission and once for the attacker, with the sign convention made explicit at aggregation ("the network mission is positively weighted, and the attacker mission is negatively weighted", md L447–449, p.10) rather than smuggled into the metric names.
- **The kill-chain-coverage argument (md L212–221, p.8)**: sampling attacker tasks across stages, out of order, precisely so that late-stage effectiveness remains observable when early-stage defence is strong — with the worked contrast between the assessment you can make ("good at stopping reconnaissance, but does little against Command and Control") and the one you are stuck with otherwise ("we don't know … because no attacker ever made it that far"). This is a **censoring argument**, and it applies to any run that terminates on attacker failure.
- **The paired caveat convention**: each metric definition immediately followed by one paragraph naming the objection to it (outlier sensitivity of the mean; plaintext-only as a proxy for exposure; corruption measured but not weighted by consequence). Cheap, honest, and it pre-empts the obvious examiner question at the point where the question arises.
- **The "not an indictment" sentence (md L222–225, p.8)**: an MTD failing to block a stage it was never designed to block is not evidence against the MTD. Useful when a new attacker model makes existing mechanisms look bad.
- **Naming the method-choice tradeoff explicitly** (analytical / simulation / testbed / operational, by cost vs accuracy, md L29–35, p.3) — the shape of a methodology justification, though the ranking itself cuts against a simulator (see below).

**Purpose-specific artefacts** (mid-contract framework paper, 8 pages, ACM workshop, DoD-funded, vendor testbed):

- **No results at all.** The whole paper is a promise; every experimental verb is future tense. A dissertation cannot borrow this posture — and, critically, **this paper cannot be cited as evidence that any MTD has any effect**, only as a source for metric *definitions* and *design conventions*.
- **Hardware-testbed apparatus** (vSphere/ESXi, linked clones, nmap/ncrack/ncat sensors, a drag-and-drop VM configurator) — the machinery of §3 does not transfer to a simulator; only its *design vocabulary* (activity model, task, attribute, run, valuation) does.
- **The explicit demotion of simulation** relative to testbeds (md L36–41, p.3) is a positioning move for a testbed-vendor paper; a simulator-based dissertation must answer it rather than cite it approvingly.
- **"tailored to the needs of an individual customer"** weighting (md L441–446, p.10) and the enterprise-customer framing throughout — a commercial-consultancy convention. In a dissertation the weights would need to be fixed and justified, not left to a customer.
- **Confidentiality and Integrity as MTD metrics at all** are specific to this paper's information-operations remit (attribution, post-attack characterisation, D5 effects, md L64–72 right col, p.4; md L320–327, p.8). Most MTD evaluations, including the MTDSim lineage, have no instrument for either.
- **The mission-activity apparatus** (mail/FTP/SQL/web clients transacting at fixed rates against activity servers) presumes a live network with legitimate traffic. A simulator with no benign-traffic model cannot compute the mission column of Table 3 at all — meaning the framework's central "cost to mission" cell is **out of reach for a simulator-based study**, and this must be said if the framework is invoked.
- **The Cyber Kill Chain as the stage taxonomy** (2011 Lockheed model, seven stages) rather than ATT&CK — a 2015 artefact; and the paper's own Table 2 already departs from it (Discovery, Propagation).

## H. The framework itself

### H.1 The four metric categories, and how each is defined

The paper names **four metric categories**, each instantiated **twice** — once over the mission activity model, once over the attacker activity model — giving eight metrics: "Examining four attributes over two activity models gives eight individual metrics that can be partitioned into two sets of four, or four sets of two, shown earlier in Figure 2, and described in more detail in Table 4" (md L306–309, p.8). Figure 2 (p.4) draws exactly this: a blue **Mission Metrics** panel and a red **Attack Metrics** panel, each stacking *Productivity, Success, Confidentiality, Integrity*.

The four categories are in one-to-one correspondence with the four **task attributes** declared earlier, in §3.2 (md L212–224, p.7):

| Attribute | Values | Metric built on it |
|---|---|---|
| `duration` | non-negative reals — "length of time to complete the task execution" | Productivity |
| `success` | 0 = "task did not complete successfully", 1 = "task completed successfully" | Success |
| `unexposed` | 0 = "information was exposed", 1 = "information was not exposed" | Confidentiality |
| `intact` | 0 = "information was corrupted", 1 = "information was not corrupted" | Integrity |

Attribute choice justified in one sentence: "Our attribute list was chosen to be representative enough of real network traffic, while providing concrete, quantifiable data to the metrics subsystem defined in Section 4" (md L226–228, p.7).

**All four metrics have the same functional form** — the arithmetic mean of one attribute over the task set of an activity model `M = ⟨T, A⟩` under a valuation `ν` (§3.2, md L160–167, p.6: `T = {τ₁,…,τₙ}` a set of n tasks, `A = {α₁,…,α_m}` a set of m attributes, and "A run of a model is a process that produces a dataset, which is simply a mapping function ν: T × A → V which takes a task τ and an attribute α to a value from the permissible values for the attribute α"):

- **Productivity** (§4.1, md L310–319, p.8): "Productivity is a measure of how quickly tasks in an activity model can be completed. Given an activity model M = ⟨T, A⟩, where A is the set of task attributes defined in Section 3.2 and a valuation ν, we define the productivity of M is defined as the average of the duration attribute over the tasks in M" (sic, "we define … is defined").
  `Productivity(M, ν) = (1/|T|) Σ_{τ∈T} ν(τ, duration)`
- **Success** (§4.2, md L379–386, p.9): "Success is computed similarly to productivity, but using the success attribute rather than duration. The success attribute is Boolean valued, taking on just 0 and 1, but the average over a number of tasks makes mission success and attacker success real-valued numbers in the range [0, 1]."
  `Success(M, ν) = (1/|T|) Σ_{τ∈T} ν(τ, success)`
- **Confidentiality** (§4.3, md L383–393, p.9–10): "Confidentiality is a measure of how much information is exposed by activity model tasks. For the mission model, exposing information is typically undesirable, whereas an attacker being exposed is desirable. Confidentiality is computed similarly to the metrics above, with the same type of costs and benefits derived from them."
  `Confidentiality(M, ν) = (1/|T|) Σ_{τ∈T} ν(τ, unexposed)`
  Operationalised narrowly: "in these initial experiments, we simply refer to whether information is visible in plaintext in network traffic" (md L396–398, p.10).
- **Integrity** (§4.4, md L407–421, p.10): "Integrity is a measure of how much information produced by the activity model tasks is preserved (not corrupted). For the mission model, corrupting information is typically undesirable … whereas an attacker's transmissions being corrupted is beneficial and will hinder their attacks. Integrity is computed in the now familiar fashion".
  `Integrity(M, ν) = (1/|T|) Σ_{τ∈T} ν(τ, intact)`

**Table 4: MTD Effectiveness Metrics** (p.9), the paper's own glosses, verbatim (md L331–349):

| Metric | Description |
|---|---|
| Productivity | "Mission Productivity can be measured by the rate at which mission tasks are completed" / "Attack Productivity is a measure of how quickly an attacker can perform and complete adversarial tasks" |
| Success | "Mission Success can be measured by the number of attempted mission tasks that are successfully completed" / "Attack Success is a measurement of how successful an attacker may be while attempting to attack a network" |
| Confidentiality | "Mission Confidentiality is a measure of how much mission information is exposed to eavesdroppers, whether information could be intercepted, etc." / "Attack Confidentiality is a measure of how much attacker activity may be visible by detection mechanisms" |
| Integrity | "Mission Integrity is a measure of how much mission information is transmitted without modification or corruption" / "Attack Integrity is a measurement of the accuracy of the information viewed by an attacker" |

**A fifth, optional metric** is defined in §4.2 — a per-kill-chain-phase effectiveness locator. Let `Φ = {Reconnaissance, Weaponization, …}` be the kill chain phases, `phase` a task attribute valued in `Φ`, and `T_φ = {τ | ν(τ, phase) = φ}`. Then, with `ν′` the with-MTD valuation and `ν` the without-MTD valuation, "the following is the kill chain phase against which the MTD appears to be most effective":
`argmax_{φ∈Φ} (1/|T_φ|) Σ_{τ∈T_φ} [ ν′(τ, success) − ν(τ, success) ]`
(md L363–375, p.9). Immediately hedged: "There are, of course, other measures that could be computed from the same attribute values. For instance, rather than looking at the absolute change in success values, it might be appropriate to look at the proportional change in success values" (md L376–382, p.9).

**Aggregation (§4.5)**: "Each metric is designed to be calculated independently such that overall metrics which blend the potential costs and benefits associated with deploying an MTD can be easily tailored to the needs of an individual customer. Our default configuration provides a simple weighted average of each metric, where the network mission is positively weighted, and the attacker mission is negatively weighted." (md L441–449, p.10). No weights are given.

### H.2 What the paper says an MTD evaluation must measure, and why

**The terms are indeed productivity / success / confidentiality / integrity** — and the "why" is a two-part argument.

*Part one: both sides, because MTD's obstacle is deployment cost, not efficacy alone.* The motivating claim is that MTD is undeployed because it may harm the mission as much as the attacker: "flexible proactive defensive measures such as Moving Target Defense (MTD) have as much potential to interfere with a network's ability to support the mission as they do to defend the network" (abstract, md L14–17, p.3). Therefore the evaluation must produce a *balance*: "help guide MTD deployment decisions that successfully balance the potential security benefits of MTD deployment against the potential productivity costs" (abstract, md L18–21, p.3), and "it is important to be able to quantify the security benefits associated with each approach along with potential productivity costs that may be introduced (either through the overhead associated with deployment of the system, or potential interference such a system may introduce to legitimate network operations)" (md L22–29 right col, p.3). This is why every metric is doubled: the mission column of Table 3 is the *cost*, the attacker column is the *benefit*.

*Part two: the four categories are a deliberate revision of the CIA triad.* The paper names the incumbent — "The traditional approach to cyber metric design is to try to quantify the effect the system under test has on three aspects of the mission data flowing through the system, Confidentiality, Integrity, and Availability of data [8]" (md L103–110, p.4, citing NIST SP 800-33) — and states the deficiency: "Our approach is inspired by this approach, but is modified to address information operation issues that the traditional approach does not directly address. For example, there are conditions under which an MTD might fail to stop an attack, but is still able to monitor and log much more fine grained detail on attack operations that allow for improved attribution or post-attack characterization of the attacker. Such benefits are important, but not well represented in traditional information assurance metrics" (md L64–72 right col, p.4). The net edit: Confidentiality and Integrity are kept, **Availability is dropped without comment**, and Productivity and Success are added — with Attack Confidentiality carrying the new "attribution / detectability" concern that motivated the revision in the first place.

*Why a difference, not a level.* Effectiveness is definitionally a contrast against a no-MTD baseline, stated three times: "Metrics are derived from the statistical differences between these interactions during runs when an MTD is not deployed (the baseline) and when it is deployed" (md L76–80 right col, p.4); "Runs with no MTD deployed represent a baseline run, which can be contrasted to effects measured during identically configured runs with a deployed MTD technology. This contrast drives our metrics" (md L293–297, p.8); and per metric, "The difference between attacker success with the MTD and without the MTD represents a benefit of deploying the MTD, and the effectiveness of the MTD at thwarting attacker activities" (md L350–356, p.9).

*Directions, as stated.* Mission side: lower duration good, higher success good, higher `unexposed` good, higher `intact` good. Attacker side, inverted: "we expect that it is uncontroversial to assume that decreased duration is typically a good result for mission tasks, and that increased duration of attacker tasks is typically a good result from a defensive standpoint" (md L357–363, p.9); "For the mission model, exposing information is typically undesirable, whereas an attacker being exposed is desirable" (md L383–387, p.9); "For the mission model, corrupting information is typically undesirable … whereas an attacker's transmissions being corrupted is beneficial and will hinder their attacks" (md L411–417, p.10). The inversion is *not* built into the formulae — all four are computed identically on both models — and is applied only at aggregation, by sign of weight (§4.5, md L447–449, p.10).

### H.3 How "mission" is operationalised alongside attacker success

"Mission" is operationalised in exactly the same object as the attacker: **an activity model**, `⟨T, A⟩`, with the *same four attributes*. "We now define two specific activity models whose tasks have the same set of attributes. The first is a mission activity model, whose activities correspond to legitimate network activities, such as sending email, and retrieving content from a database. The second is an attacker activity model, whose activities correspond to the types of actions an attacker would perform. Our two activity models use the same set of attributes (though the mechanisms for collecting attribute values may differ for the different types of tasks)" (md L200–209, p.6–7). **This symmetry is the framework's core design move**: mission and attack are not different kinds of measurement, they are the same measurement over two task sets, differing only in the sign of the weight applied at the end.

Concretely, the mission side is (§3.2.1, md L230–253, p.7):
- **Servers**: "Each test network will have a variable number of clients and an assortment of activity servers configured for use within the enclave, e.g.: Mail Server; File Server; Database Server; and Web Server. This list was chosen to represent multiple communication mechanisms sufficient to identify potential operational issues introduced by an MTD technology under test" (md L233–239, p.7); Table 1 (p.6) adds Application Server and Message server.
- **Why these**: MTDs interact differently with different protocol shapes — "some chat protocols are based on establishing peer-to-peer connections, while others route all messages through a central server; some servers depend on privileged ports, while others use unreserved high port numbers), and missions may make use of different selections of these services" (md L242–247, p.7, stray parenthesis sic).
- **Client tasks**: "sending and retrieving email, downloading files with FTP, querying a database with SQL, and retrieving web pages. Each task will be repeated at timed intervals. For instance, the client will send 60 emails, one every second" (md L248–253, p.7).
- **Mission → topology binding**: mission templates define which topologies count as supporting that mission (md L184–188, p.6), so "mission" is simultaneously the traffic model *and* the topology-selection criterion.

Mission is thus measured **per task, in the same units as the attack**, and the two meet only in Table 3 and in the §4.5 weighted average. Note the practical consequence for a simulator: the mission column of Table 3 requires a running benign-traffic workload with per-task instrumentation. Without one, "cost to mission" is not computable, and only the attacker column of the matrix is available.

### H.4 Experimental apparatus described

- **Testbed, not simulator**: "Siege utilizes an automated testbed for testing and measuring cyber effects as part of its workflow for designing cyber capabilities. In order to measure the effectiveness of MTD technologies, we have adapted and leveraged our Cyber Quantification Framework (CQF)" (md L82–86, p.4). The CQF "has been used for experimental quantitative assessment of various types of cyber-assets, including both hardware and software" and "combines a user-friendly interface for designing large-scale experiments, sophisticated integration with virtualization servers (currently VMware vSphere, but the workflow can be ported to other virtualization systems, or adapted to physical cyber-ranges), and a workbench for data analysis and visualization" (md L89–99, p.4).
- **CQF architecture** (Figure 3, p.5): Client nodes each carrying an MTD component, reporting to a *Control Server* ("Mission/Attack Activity Testing and Data Collection"), which feeds *MTD Characterization* → *Mission-Based MTD Assignment Engine*.
- **Configuration UI** (Figure 4, p.5): browser-based drag-and-drop; "Top level items represent (virtual) hardware elements such as routers or switches, and virtual machine templates. Other non-top level items are dragged into these, and encapsulate additional test parameters, such as software that can be installed on virtual machines, data collectors that can be deployed to virtual machines during experimentation, and virtual networks that can be established on virtual routers" (md L102–111, p.4).
- **Experimental loop** (Figure 1, p.4): configure → spawn a VM network with sensors → run missions with and without cyber-attacks → gather data → update analysis → generate a new topology → repeat. "Once an experiment is configured, it will automatically spawn a network of virtual machines configured with custom software to replicate mission oriented network activity, and a set of sensors to gather data. We will execute realistic missions with and without cyber-attacks, gather data, and then update our analysis of what pre-conditions make sense before launching the technology under test, and what post-launch conditions should be expected" (md L88–97, p.4).
- **Topology generation**: vSphere + ESXi, linked clones, Linux and Windows hosts plus routers (md L162–179, p.6); hierarchical structure with node counts from a bounded Pareto distribution for a heavy-tailed degree profile (md L196–205, p.6); contrasted with Waxman random generation (md L189–195, p.6).
- **Scenarios**: **none are defined**. There is no scenario list, no named attack campaign, no mission instance.
- **Runs**: **no count, no duration, no seeds, no repetitions.** The only structural statement is "each run represents a combination of a mission, topology, adversary model, and MTD deployment" (md L289–292, p.8) and the stopping-condition policy at md L98–102 (p.4).
- **Sensors / data collection**: per Table 2 (p.8) — nmap (network visibility), ncrack (dictionary attack success/failure), ncat (backdoor establishment), read/write/execute probes (D5 capability incl. privilege escalation), and a Discovery+Delivery combination for propagation. Plus TCP Dump and Java collectors visible in Figure 4. Storage: "we preserve all data collected in a database which is dynamically linked to our metrics" (md L451–453, p.10).
- **Scale**: "large-scale experiments" is asserted (md L92, p.4) and the prior work is characterised as "large scale in the sense that a large number of machines were created, configured, and run, all at once" (md L116–118, p.5) — but no number of VMs, hosts or runs appears anywhere in this paper.

### H.6 Citation caution

The paper is safely citable for: the four-category metric scheme and its formulae; the mission-vs-attack symmetry; the 2×2 experimental matrix; the baseline-difference definition of effectiveness/cost; the data-vs-metric separation argument; the kill-chain-coverage (censoring) argument; the caveats in F. It is **not** citable for any empirical claim about any MTD, for any measured value, or for any comparison between MTD mechanisms — the paper contains none. If the dissertation's metric table attributes a *result* to this source, that attribution is unsupported.
