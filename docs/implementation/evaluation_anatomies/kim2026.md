# kim2026 — evaluation-section anatomy

Source read: docs/sources/lit_review/3_2_kim2026mtdid.md (full text; locators "L<n>" = md line) and docs/sources/lit_review/original/3.2_kim2026mtdid.pdf (14 pp., text extracted per page with pypdf; locators "p<n>" = PDF page). Caution on the md: its §5–§6 text is column-scrambled (e.g. the "5.2 Attack model" and "5.3 Defense model" headings sit together at L278–280 while their bodies are at L266 and L282–284; the "6.2/6.3" headings at L442–444 are separated from their bodies at L446–466 and L422/L440), so the PDF page text was used for reading order and the md lines are cited for text only. Tables 4 and 5 are real text in both sources (cell values quoted below); Figs 7–10 are images, so chart types are inferred from captions and prose only.

Paper's own research question / purpose (one sentence, so its conventions are read against its purpose, not ours): propose "MTD in Depth (MTDID)", a conceptual framework that maps MTD sub-techniques to MITRE ATT&CK techniques and Cyber Kill Chain phases via digital artefacts, and demonstrate it with a case study on a physical SDN testbed that measures both the performance degradation and the per-CKC-phase security benefit of combinations of vIP shuffling, software diversity and redundancy against a single automated multi-phase attack (abstract L31–45; contributions L77–81; p1).

## B. Setup — what is declared before any result

- Network configuration(s): one physical SDN testbed (Fig. 4 "Architecture of our physical SDN testbed", p7): "5 HP Aruba switches (3x 2920F, 2x 2930M), which serve as a partial Fat-Tree network. The SDN controller operates on ONOS 2.4.0 with the OpenFlow 1.3 protocol" (L356; p8); "The servers and the attacker are deployed in each Raspberry Pi 4" (L372; p9); components "SDN-enabled switches, web servers, a legitimate client, and an attacker" (L264; p7). Described as "an entertainment network environment" (L260). Number of configurations: one topology; the varied axis is the MTD combination (five systems + baseline). How chosen: not stated beyond "designed to facilitate the testing and development of MTD operations" (L356).
- Attacker model / scenarios: §5.2 (p7). One scenario: "This work proposes a single attack scenario and follows sequential steps. The overlap in time between each phase is out of scope." (L276). Automated RCE exploit for CVE-2021-41773 on Apache 2.4.49 (T1059) (L282, L382). Phases bold-labelled once with an abbreviation and then used as metric subscripts: "Reconnaissance (REC)", "Delivery/Exploitation/Installation (DEI)", "C2/Actions on Objectives (C2A)" (L270–274; p7). Weaponization is dropped "because the exploit is open in the public database" (L266). Attacker parameters: scan range 4096 vIPs per trial × 5 repeats out of 65,535 (Table 4, L367–368; L386–388); attack arrivals Poisson at ATKλ = 0.2/min (L382; Table 4 L363). Attacker knowledge assumption: "an attacker has a lack of network information about a target" (L270); "only targeting an Apache web server because of its weapon" (L382). Assumptions about the environment that protect the attacker model: secure DNS accessible only to legitimate clients (L264, L380).
- Defence conditions: three sub-techniques, italic-labelled once with a symbol: "_Virtual IP Shuffling (S_vIP)_", "_Software Diversity (D_SW)_", "_Hardware & Software Redundancy (R_HSW)_" (L298, L348, L304; p8), each with an operating algorithm (Algorithm 1, 2) and a timeline figure (Fig. 6). Five MTD systems evaluated: S_vIP, D_SW, S_vIP+D_SW, S_vIP+R_HSW, S_vIP+D_SW+R_HSW (Table 5 rows, L460–464); redundancy alone is excluded by rule: "It is necessary for R_HSW to operate in conjunction with S_vIP, as a number of redundancy techniques do not work on their own" (L388). Scheduler: time-based, all techniques "triggered every MTD interval of T_MTD" (L388), "a naive configuration that triggers the operations of all MTD techniques at the same time on a regular basis" (L296). "No defence" baseline: yes — "No-MTD", defined operationally as ONOS built-in forwarding/DHCP apps: "As compared to a baseline of the system (i.e., No-MTD) by incorporating built-in ONOS applications such as org.onosproject.fwd and org.onosproject.dhcp" (L446; p10); and "A No-MTD system is considered as a baseline of the measurements that operate to handle network packets without any defense mechanisms" (L450).
- Parameter table: yes — Table 4 "Key design parameters and their default values" (p9; L358–370), columns Type | Variable | Description | Value; rows grouped into "Inputs" (λ "Varying"; ATKλ 0.2/min) and "System Param." (T_MTD 300 s; T_RST 600 s; Web_s 2 MB; N 65,535; M "4096 x Repeat"; BW 1 Gbps; WKR_max 400). Distributions declared: "A Poisson distribution of the request rate is used to determine a number of benign and attack workloads" (L378; p9). Each row is then justified one by one in prose in §6.1.2 (L386), with the interval anchored to prior work: "the MTD interval (T_MTD) of 300 seconds is used … as in the prior works [11,12,22]. The 300-second MTD interval in [11,12] was used to consider acceptable overhead while ensuring the system imposed security level" (L386).
- Replications: not stated. No number of runs, trials or seeds for either the performance or the security experiment. The only "repeat" is the attacker's scan-repeat parameter (5), not an experimental replication (L386–388). The appendix gives an incidental denominator — "a failure rate (FFJ) of 0.0029 (9/3061) and 0.0000 (0/3061)" (L514; p12) — which implies ~3061 jobs per condition in that side experiment; nothing equivalent is given for the main results. Horizon: implicitly one MTD interval (T_MTD = 300 s) per attack attempt, since remaining time per phase is T_k = T_MTD − T_ATK − ΣAST_i (L434–438; p10). Termination rule: not stated.
- Statistics: point values only. Table 5 reports ASP to two decimals and AST to four decimals with no dispersion (L459–464). No std, CI, min–max, or significance test anywhere. One analytic-vs-measured check is offered in place of statistics: "three web applications are running so that its analytic probability can be estimated at 0.33, which is slightly larger than our experimental results (i.e., 0.26)" (L452; p10).
- Anything else declared: software versions "httpd-2.4.41, Nginx-1.20, Litespeed-1.6.21" (L372); ONOS 2.4.0, OpenFlow 1.3 (L356); Apache Benchmark (AB) tool for HTTP GET load (L380); Ubuntu only (L292); web-server selection justified by Netcraft market share (L292); job size 2 MB chosen "to emphasize the network overhead in our testbed" (L446); "Data will be made available on request." (L498).

## C. Results — how the numbers are shown

- Order of results: performance (§6.2, benign workloads, cost of MTD) before security (§6.3, attack workloads, benefit of MTD). The order follows the paper's stated two-sided purpose ("evaluate both advantages and disadvantages of MTDID adoption", L73) and the inputs split ("benign and attack workloads, respectively", L352); no other reason is given. Within §6.3, single techniques are discussed first, then pairs, then the triple.
- Figures in the evaluation portion:
  - Fig. 7 (p9): "Security metrics at phases of the CKC." — a metric-definition timeline diagram (AST/ASP/ART per phase), not a data chart.
  - Fig. 8 (p10): "Performance degradation due to the abrupt disconnections at MTD interval of 300 s." — y = FFJ, x = request rate λ (10–50/min, L380), series = MTD combinations (and No-MTD, L446). Chart type not determinable from text. Facets: none stated.
  - Fig. 9 (p10): "Attack success probabilities of MTD systems at MTD interval of 300 s." — y = ASP, grouped by CKC phase (vIP-REC, VUL-REC, DEI) and MTD system. Chart type not determinable from text.
  - Fig. 10 (p11): "Rules in SDN switches." — appendix illustration of flow rules; not a data chart.
- Tables:
  - Table 4 (p9): 9 rows × 4 columns (Type, Variable, Description, Value) — the parameter table (see B).
  - Table 5 (p11): 6 rows (No MTD, S_vIP, D_SW, S_vIP+D_SW, S_vIP+R_HSW, S_vIP+D_SW+R_HSW) × 7 metric columns grouped under four phase headers ("vIP in REC", "VUL in REC", "DEI", "C2A"): ASP_vIP, AST_vIP, ASP_VUL, AST_VUL, ASP_DEI, AST_DEI, ART_C2A. The caption carries an interpretive sentence: "The results present that a single diversity redundancy could not be an effective proactive security mechanism in vIP in REC. However, it could provide security benefits in REC as well as in DEI if it combined other MTD sub-techniques." (L454).
- How the baseline appears: Table 5 has a "No MTD" row with ASP = 1.00 in every phase, "-" for every AST, and "≫ 600" for ART_C2A (L459); the prose reads this as "Adversaries are likely to have ample time to collect information on a target in a system without any defense mechanism (i.e., No-MTD)" (L466). In Fig. 8 the baseline is a series (stated at L446); in Fig. 9 not determinable.
- How comparisons are stated in prose:
  - Magnitude, relative: "At the request rate of 30, the FFJ of S_vIP + D_SW + R_HSW is reduced by about 46% when compared to that of S_vIP" (L440; p10); "the ASP_VUL of S_vIP + D_SW is reduced to 0.08, which is about 65 % smaller than the ASP of a single MTD adoption" (L452); "The ASP_vIP of either S_vIP + R_HSW or S_vIP + D_SW + R_HSW is almost doubled to the ASP of a single MTD technique, S_vIP. With the help of the operation in D_SW, its ASP_VUL can be reduced by about 1/3" (L466; p11).
  - Magnitude, absolute: "Their ASP_VUL have decreased to 0.22 and 0.26, respectively" (L452).
  - Ordering: "the FFJ of software diversity (D_SW) incurs less than that of the vIP shuffling (S_vIP)" (L448); "pairs of MTD sub-techniques such as S_vIP + D_SW are likely to increase network overheads as benign workloads increase" (L422).
  - Threshold/knee: "exceeding 30 requests per minute causes a sharp increase in network workloads" (L448).
  - Per-phase attribution: "each MTD technique can improve security effectiveness in different phases of the CKC. Either vIP shuffling or software diversity can help to thwart the reconnaissance acts … whereas R_HSW can shorten the time for an attacker to reside on the victim's compromised system (ART_C2A)" (L466).
  - Recommendation-flavoured close of §6.2: "optimally combining different ways of triggering MTDs can properly serve their system's request rate without experiencing significant performance degradation" (L440). No explicit "A is the best choice when …" statement.

## D. Narrative — the claims, in order

1. MTD adoption "entails some performance overhead"; overhead grows with request rate; knee at 30 req/min (L448; p10).
2. D_SW degrades less than S_vIP, "implying the changes in network addresses may cause more network overhead than the software diversity" (L448).
3. Pairs increase overhead as load increases (L422), but the replica in R_HSW acts as a load balancer, so the triple beats S_vIP alone by ~46% FFJ at λ = 30 (L440); mechanism offered: TCP retransmission up to timeout occupies bandwidth (L440).
4. Therefore "optimally combining different ways of triggering MTDs can properly serve their system's request rate" (L440).
5. Single S_vIP or D_SW lowers ASP_VUL to 0.22 / 0.26; D_SW's 0.26 is checked against the analytic 1/3 (L452).
6. S_vIP + D_SW lowers ASP_VUL to 0.08, ~65% below either single technique (L452).
7. Redundancy "increases attack surfaces, which leads to higher ASP in reconnaissance", roughly doubling ASP_vIP, while serving more reliably; D_SW cuts ASP_VUL by ~1/3 within those combinations (L466; p11).
8. Each technique helps at a different CKC phase; R_HSW alone is what shortens ART_C2A (L466; Table 5 shows ART_C2A finite only in the two R_HSW rows, L463–464).
9. A single redundancy technique was not evaluated (L466).
10. Appendix: job size and job arrival time relative to the MTD trigger are "crucial factor[s]" in performance (L514; p12); switch CPU/memory do not differ between No-MTD and MTD, overhead comes from software address translation in switches (L520).

Claims about the ATTACKER's properties from the data: limited. The attacker is treated as an instrument with fixed parameters; the paper reads the attacker's situation off the defence results rather than characterising the attacker: "Adversaries are likely to have ample time to collect information on a target in a system without any defense mechanism (i.e., No-MTD) and to gain access if any potential vulnerabilities are open" (L466), and the closing generalisation "From an attacker's point of view, it has a better chance to control a victim's system either when AST_REC and AST_DEI are shorter or when ASP_REC, ASP_DEI and ART_C2A are larger" (L466). The only quantitative attacker-side observation is the analytic-vs-measured discovery probability under D_SW (0.33 vs 0.26, L452). No claim is made about attacker skill, adaptation, or timing distributions from the data.

## E. Sensitivity / parameter analysis

Present only in a narrow, unlabelled form:
- Benign request rate λ swept over 10–50 req/min (L380) — the x-axis of Fig. 8 (p10); one-at-a-time with all else at Table 4 defaults; range justification: not stated; used to support the overhead-vs-load claim and the 30 req/min knee (L448). Applies to the performance experiment only; the security experiment is run at a single ATKλ = 0.2/min.
- Job size varied (512 KB, 1 MB, 2 MB) in the Appendix "Performance Impact of Job Sizes" (p12; L512–514), one-at-a-time, motivated by "the limitations of our testbed's switch hardware"; used to claim job size and job arrival time are critical factors; reported in prose only (two FFJ values), no figure or table.
- MTD interval T_MTD is fixed at 300 s and NOT swept; every figure and table caption carries "at MTD interval of 300 s" (Fig. 8, Fig. 9, Table 5), and the fixed value is defended by citation to prior work (L386). T_RST, N, M, scan repeat, WKR_max, BW: fixed, not swept.
- No grid/factorial design; the five MTD combinations are the only multi-level factor and are enumerated exhaustively subject to the R_HSW-needs-S_vIP rule (L388).
- Where it sits: inside results (Fig. 8) and in the Appendix; no section named sensitivity.

## F. Discussion / limitations

Discussion is a named subsection §6.4 "Discussions and limitations" (p11; L468–484): a six-bullet list, each bullet bold-labelled and phrased as a constraint paired with future work ("The constraints of experiments have resulted in a few discussions in this study. The outline for future work can be presented as follows", L470). Interpretation of results is folded into §6.2/§6.3 (mechanism sentences at L440, L448, L452, L466) and into the Table 5 caption. No threats-to-validity heading; no statistical caveat; no comparison of numbers to other papers' numbers, though the introduction positions the testbed against prior "analytic models, simulation, or emulation" (L73) and related work calls out prior evaluation "limited to a Mininet simulation" (L73).

Verbatim limitation sentences:
- "A time-based MTD: In our experiments, we try to set up an environment that is as naive as possible. The use of adjustable trigger mechanisms to enhance security can be considered in order to combat other types of cyberattacks as well;" (L472; p11)
- "Threat Models: This work assumes that the network provides secure DNS and only legitimate clients can access it. There are more potential threat models that can discover IP addresses (e.g., DNS enumeration). Moreover, by exploiting the vulnerability (Apache CVE2021-41773), the scope of our assessment is restricted. Therefore, our future work will take into account more advanced threat models;" (L476; p11)
- "Combinations of MTD: In this paper, we present defense models utilizing three distinct MTD sub-techniques without advanced decisionmaking. However, other MTD techniques and optimization methodologies [92,93] will be considered;" (L478)
- "Evaluation Limitations: Our quantitative analysis conducted on a physical SDN testbed may not be substantial in replicating real-world conditions and accurately capturing the diverse range of attack scenarios. A comparative analysis conducted for future study could provide valuable insights in contrast to other frameworks or network environments." (L484; p11)
- Attacker-realism concession stated in the model rather than in §6.4: "This work proposes a single attack scenario and follows sequential steps. The overlap in time between each phase is out of scope." (L276; p7); "Redundancy techniques are usually used in combination with other MTD techniques and in our experiment, a single redundancy technique is not evaluated." (L466; p11)
- Positioning statement that frames what the testbed evaluation is for: "Since our framework offers knowledge-based models, the case studies are valuable for evaluating the feasibility and adaptability of our framework for realistic network systems." (L105; p3)
- Hedged conclusion: "Our work has shown that our proposed framework of MTD in Depth may help defenders proactively secure their systems by using multiple MTD techniques in depth." (L490; p12)

## G. Transferable vs purpose-specific

Transfers to an honours dissertation evaluating existing MTD mechanisms against a new attacker model on a simulator:
- A parameter table with Type / Variable / Description / Value columns, rows grouped into inputs vs system parameters, followed by a prose walk-through that justifies each value and cites the source for any inherited value (T_MTD = 300 s "as in the prior works").
- The inputs / systems / outputs triad for the setup subsection.
- Separate model section (system / attack / defence) preceding the evaluation section, with the attack phases labelled once and reused as metric subscripts (REC / DEI / C2A → ASP_REC, AST_DEI, ART_C2A).
- Per-phase security metrics with an explicit composition rule (Eq. 2, remaining time per phase), so the defence effect is attributed to a kill-chain stage rather than reported as one aggregate.
- A "No MTD" row in the main table with the degenerate values (ASP = 1.00, AST "-", ART "≫ 600") shown explicitly rather than omitted.
- Comparisons stated as relative magnitudes with the reference named ("reduced by about 46% when compared to that of S_vIP").
- An analytic sanity check placed beside a measured value (1/3 vs 0.26).
- Cost (performance) reported before benefit (security), so the trade-off framing is symmetric.
- Limitations as a labelled bullet list, each item a constraint plus the future work that lifts it, including an explicit "Threat Models" item that names the attacker assumptions.
- Interpretive sentence in a table caption stating what the table shows.

Artefacts of this paper's own purpose/venue:
- No replication, seed, or dispersion reporting, and 4-decimal point estimates: a physical-testbed convention where a run is expensive; a simulator study cannot inherit this.
- MTD interval fixed at one value with every caption stamped "at MTD interval of 300 s" — a consequence of the physical testbed and of the framework (not the scheduler) being the contribution.
- A single attack scenario with a single CVE and a fixed scan budget: the attacker is an instrument for demonstrating the framework, so no attacker characterisation is attempted.
- Performance measured as FFJ under Apache Benchmark load; the load sweep is the only sweep.
- The large conceptual apparatus (ontology, digital artefacts, Tables 1–3 mapping ATT&CK to MTD) that precedes and dominates the evaluation; the evaluation is a "case study" (§5 title) of that framework.
- Appendix carrying side experiments (job size, switch overhead) that answer testbed-hardware questions.
- Data-availability and CRediT statements (Elsevier FGCS convention).
