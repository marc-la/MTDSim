Source read: `docs/sources/lit_review/alavizadeh2022.pdf` (17 PDF pages = journal pp. 1772–1787 + author bios; IEEE TETC two-column, read in full via pdfplumber column-split extraction plus page renders of pp. 8, 9, 10, 12, 15 for figure axes/series and Table 8). The companion md, `docs/sources/lit_review/alavizadeh2022.md`, is a **partial/garbled conversion** — it is a Ghostscript `txtwrite` dump that interleaves the two columns line-by-line and mangles every equation (subscripts fall onto their own lines, `(cid:N)` glyph codes replace symbols); its own header says so: "Spacing is imperfect; the PDF is authoritative" (alavizadeh2022.md:1). All locators below are therefore **PDF page numbers ("p.N")**; the PDF page number is the journal page minus 1771 (PDF p.1 = journal 1772).

Paper's own research question / purpose (one sentence): there has been "no joint evaluation of the effectiveness of MTD techniques with respect to security **and** economic metrics" (p.1, abstract), so the paper (i) gives mathematical definitions for the *combination* of Shuffle, Diversity and Redundancy, (ii) scores that combination on four security metrics on a large cloud model, and (iii) scores Shuffle and Diversity on economic metrics for an e-health cloud case study, ending in an optimisation model (O-DAP) that maximises expected net benefit (p.1, abstract). The object evaluated is the DEFENCE (technique/strategy/assignment); the attacker is a fixed modelled quantity, not a treatment.

## B. Setup — what is declared before any result

### Network configuration(s)
**Two distinct networks, one per evaluation half.**

1. *Cloud-band model* (security half, IV): "A cloud-band system typically consists of two main cloud-band nodes, with each accommodating up to 450 VMs, and one resource node connecting to a database (DB)" (p.7). "the VMs are connected in a mesh topology" (p.7). Declared graph properties for the 400-VM instance: "the mode of path lengths are 10.53 and eight, respectively, with the shortest path between the attacker and the DB being eight. The standard deviation of the attack path lengths is 1.36. We compute the betweenness of all VMs. The highest values for the three most important VMs in the cloud-band are 0.35, 0.27, 0.21, respectively. The minimum betweenness value in the upper layer of the HARM is zero" (p.7). Size is **swept**: "We compute these metrics for different cloud-band sizes ranging from 150 VMs up to 400 VMs in the cloud" (p.7) — realised as n = 150, 200, 250, 300, 350, 400 on the x-axis of Fig. 4 and Fig. 5 (p.8 render). How the topology is generated (random model, degree, seed) is **not stated**.
2. *Personal health cloud (PHC) / e-health model* (economic half, V, and defined up front in III.A): "a private personal health cloud (PHC) that includes 10 VMs located on different cloud hosts (servers)"; vm₁ and vm₂ in Host1 are internet-facing entry points; vm₁₀ in Host5 connects to the PHI database; "The VMs located in Host1 and Host2 use Windows 10, and the VMs in the other hosts are installed with Enterprise Linux OS" (p.4). Shown as Figure 1 (p.4) and as a two-layer HARM in Figure 2 (p.5). One configuration only, hand-specified — no generator.

The security model is the two-layer HARM (Hong & Kim): "an upper layer to model the connectivity of VMs, and a lower layer to capture the vulnerabilities on each VM" (p.4), formalised as a 3-tuple H = (U, L, C) in Definition 1 (p.4).

### Attacker model / scenarios
**One attacker, defined by assumption, never named or varied.** "we assume that an attacker is outside the private cloud and can exploit the vulnerabilities of those operating systems to gain access. The goal of the attacker is to compromise the database (DB) in Host5" (p.4). For the large model: "we assume that an attacker is outside of the cloud-band, and can penetrate the cloud by exploiting the vulnerabilities of VMs in the first cloud band node. We further assume that there are vulnerabilities that can be exploited by the attacker to give them the root privilege" (p.7). Exploitation granularity: "we assume that the attacker needs to exploit only one vulnerability to exploit the VM. Thus, we only use the OR-gate in the lower layer of the HARM" (p.5), with the AND/OR alternative explicitly deferred: "more complicated vulnerability analyses ... are considered outside the scope of this paper" (p.5). There is **no attacker procedure, no scenario taxonomy, no skill level, no give-up rule, and no attacker state machine** — the attacker exists only as (a) the source node of the attack-path set AP, and (b) an arrival rate for reliability: "We assume that the attack rate for the cloud-band models follows an exponential function with an average value of 0.2 (i.e., one attack per every five hours)" (p.7).

There *are* two named **scenarios**, but they are defence-deployment scenarios inside V.H, not attacker scenarios: "*Scenario 1.* We deploy the Diversity technique only on a single VM through exhaustive search (ES)" and "*Scenario 2.* We evaluate the deployment of the Diversity technique on various VMs with a single back-up OS" (p.12).

### Defence conditions
Three mechanism families and their combination, each given a formal definition on the HARM (p.6–7):

- **Shuffle**, realised as VM live migration: "We utilize the virtual machine live migration (VM-LM) as the main technique for deploying the Shuffle MTD technique" (p.6). *Definition 3*: S(H, k) = Hˢ, transforming only the upper layer to Uˢ·ᵏ = (VM, E′) — connectivity changes, vulnerabilities do not (p.6–7).
- **Diversity**, realised as OS diversification: *Definition 4*: D(H, k) = H^d = (U, L^{d,k}, C) — "The Diversity technique affects the lower layer and varies vulnerabilities V_{k,u} … while U = (VM, E) is preserved" (p.7).
- **Redundancy**, realised as VM replication: *Definition 5*: R(H, k, r) = H^r, |VM′| = n + r (p.7); *Definition 6* adds the vulnerabilities the replicas bring: "V′ = V ∪ V^r is a set of new vulnerabilities introduced by adding the new VMs" (p.7).
- **Combination S+D+R**: *Definition 7*: "Let S+D+R(H, k_s, k_d, k_r, r) be a S+D+R function on the HARM where k_r shows the VM selected to be replicated r times, k_s is the VM selected to be shuffled, and k_d denotes the VM selected for the Diversity technique" (p.7), yielding H^{s+d+r} = (U^{s+d+r}, L^{s+d+r}, C) with V′ = V ∪ V^r ∪ V^d (p.7).

**How the mechanisms are combined (the paper's distinctive move).** Combination is *compositional on the HARM layers, not on a schedule*: Shuffle rewrites the upper-layer edge set, Diversity rewrites the lower-layer vulnerability sets, Redundancy adds upper-layer nodes and consequently lower-layer vulnerabilities; because they touch disjoint parts of the tuple, S+D+R is literally the composition of the three transforms applied to disjoint chosen VMs (k_s, k_d, k_r) (Definitions 3–7, p.6–7). There is **no timing model, no MTD trigger interval, and no interleaving** — an MTD "deployment" is a one-shot structural change to the model, and the limitation section concedes this explicitly (p.15, quoted in §F).

**Which VMs get which mechanism** is set by a *derived* rule rather than declared up front — the combination criteria are chosen from the earlier results: "In order to combine the three techniques, we set combination criteria based on the results obtained from previous sections. The results discussed in Section IV-B showed that OS diversification on the VMs having higher betweenness (grouped in BVS) has a better effect on security metrics. … Based on those results, we only consider the BVS group for deploying the Diversity technique in this section. Moreover, based on the results of previous studies reported in [4] for combining the Shuffle and Redundancy techniques, we deploy the Shuffle technique on the most suitable VMs, which can be found by analyzing only the top 10% of the VMs with higher values of betweenness. Finally, we deploy the Redundancy on the DB or on VMs connected to the DB (target) to increase the reliability of the cloud and availability of the DB against DDoS attacks." (p.9)

**Selection strategies** are themselves a treatment factor (three levels, defined once with acronyms): "we deploy OS diversification on multiple VMs based on three selection criteria: (i) betweenness VM selection (BVS), (ii) closeness VM selection (CVS), and (iii) random VM selection (RVS). The RVS method selects a set of random VMs in the cloud. The BVS method selects the set of VMs based on their higher betweenness ranks … the CVS method uses the closeness ranks" (p.8). A fourth, for Shuffle placement, is proposed in V.G: "the shortest path injection approach, in which a selected VM can be moved and connected to the VMs located in the shortest path in the upper layer of the HARM", selecting among shortest paths by minimum in-degree, Eq. (15) (p.11).

**No-defence baseline: YES, and it is the paper's reference condition throughout.** It is called "the current cloud-band" / "the current security posture": "We compute the defined security metrics of the current cloud-band system before deploying the MTD techniques" (p.7); "In the following sections, we compare the results obtained from deploying the MTD techniques on the cloud-band against the current security posture of the cloud" (p.7). It appears as a whole figure (Fig. 4, p.8), as the "AC-Current" dashed series in Fig. 5 (p.8 render), and as the "Current n=150 / Current n=400" series in Fig. 7(b) (p.9 render).

### Metric definitions (exhaustive)

*Four security metrics*, introduced together: "we utilize four security metrics, (i) system risk (Risk), (ii) attack cost (AC), (iii) return on attack (RoA), and (iv) system reliability (Reliability), to evaluate the security of the cloud after deploying MTD techniques, and to identify the most suitable technique deployment strategies" (p.5).

- **Risk** — per-VM as the max over that VM's vulnerabilities of exploitability × impact: `Risk(vm_i) = max_{n_{j,u} ∈ V_{i,u}} ( E_{n_{j,u}} × I_{n_{j,u}} )` (Eq. 3, p.6); per attack path as the sum over VMs on the path, `Risk_ap = Σ_{vm_i ∈ ap} Risk_{vm_i}` (Eq. 4, p.6); system-wide as the sum over *all* attack paths, `Risk_c = Σ_{ap ∈ AP} Risk_ap` (Eq. 5, p.6). Framing: "Risk is based on the vulnerabilities of the network's components" (p.5). E and I come from CVSS/NVD (Table 2, p.4). A worked "Example 1" computes one path by hand: "Risk_{ap1} = … = 7.2. Finally, the total risk of the cloud is the sum of all Risk_ap values which is Risk_c = 211.692 for the cloud example" (p.6).
- **Attack Cost (AC)** — "AC measures the difficulties attackers face in attacking a system, and can be quantified in terms of the costs an attacker incurs when seeking to exploit a network component or the whole system" (p.5); "The cost of exploiting the vulnerabilities on a VM for an attacker is defined as the attack cost (AC)" (p.6). System-wide: `AC_c = Σ_{ap ∈ AP} ( Σ_{vm_i ∈ ap} AC_{vm_i} )` (Eq. 6, p.6). Per-vulnerability AC values are tabulated (Table 2, p.4: e.g. CVE-2018-8490 → AC 1.6; CVE-2018-14633 → AC 3; Fedora CVE-2014-1859 → AC 4.5) — i.e. **AC is an assigned per-CVE constant, not a derived quantity**, and higher AC means a *harder* exploit.
- **Return on Attack (RoA)** — the economic/attacker-eye metric, credited to Cremonini & Martini [16]: "Return on attack (RoA) is a security metric based on the attacker's perspective [16]. RoA quantifies the costs of the attack versus the benefits of the attack. A higher value of RoA indicates a higher probability that an attacker will exploit those vulnerabilities (a higher tendency to attack)" (p.6). Per VM it is risk-over-cost: `RoA_{vm_i} = max_{n_{j,u} ∈ V_{i,u}} ( E_{n_{j,u}} × I_{n_{j,u}} ) / AC_{vm_i}` (Eq. 7, p.6) — i.e. numerator = the same quantity as Risk(vm_i). System-wide: `RoA_c = Σ_{ap ∈ AP} ( Σ_{vm_i ∈ ap} RoA_{vm_i} )` (Eq. 8, p.6). **Direction of goodness: lower is better for the defender** (a decrease "indicates that the attacker would be less likely to attack", p.14). Earlier framing: "RoA indicates the willingness of the attacker to use the same components, attack path(s), and vulnerabilities to penetrate the network" (p.5).
- **Reliability** — the only metric with **no equation**: "Reliability quantifies the reliability of the network's components (i.e., critical components) under certain attack circumstances. The Reliability can be calculated using the symbolic hierarchical automated reliability and performance evaluator (SHARPE) that is an analytic modeling software tool [37]" (p.5). Operationalised only by tool and horizon: "For the reliability analysis, we use the SHARPE software package [37]. We assume that the attack rate for the cloud-band models follows an exponential function with an average value of 0.2 (i.e., one attack per every five hours). In addition, we compute the Reliability values during a 10-hour period" (p.7).

*Five economic metrics*, each defined in its own subsection of V immediately before use:

- **SLE (single loss expectancy)** — "measures an organization's expected loss from a single threat [29]"; per VM: `SLE_{vm_i} = (1 − Π_{v_{j,u} ∈ V_{i,u}} (1 − EF_{v_{j,u}})) × AV_{vm_i}` (Eq. 9, p.10), where EF is the exposure factor, "the maximum percentage of loss for that asset caused by a threat" (p.10), and AV "consists of the costs associated with running an active VM (i.e., purchasing a license for an OS, applications, DB values, etc.)" (p.10). Cloud-wide: `SLE_c = Σ_{ap ∈ AP} ( Σ_{vm_i ∈ ap} SLE_{vm_i} )` (Eq. 10, p.10).
- **ALE (annual loss expectancy)** — "the expected financial loss due to an attack event … computed by the product of SLE and the annualized rate of occurrence (ARO)": `ALE_c = Σ_{ap ∈ AP} ( Σ_{vm_i ∈ ap} SLE_{vm_i} × ARO_{vm_i} )` (Eq. 11, p.10).
- **BS (benefits of security)** — the ALE delta: `BS_c^m = ALE_c − ALE_c^m`, where "ALE_c^m denotes the ALE value of the cloud after deploying MTD techniques. m ⊆ {S, D, R} denotes a set of MTD used as defensive techniques" (Eq. 12, p.11).
- **MF (mitigation factor)** — a normalised, clipped version of the same delta: `MF^m = 1 − ALE_c^m/ALE_c if ALE_c^m < ALE_c, else 0`; "MF^m takes values within the range [0,1] … a larger value of MF^m is more desirable" (Eq. 13, p.11).
- **RoSI (return on security investment)** — "can be used to evaluate the profitability of a defensive investment relative to the costs": `RoSI_c^m = (BS_c^m − CS^m) / CS^m` (Eq. 14, p.11).
- **ENB (expected net benefit)** — the O-DAP objective, `ENB = ALE_after − ALE_before − cost of security − Σ_{(i,j)∈E} M f_ij` (Eq. 16, p.13), i.e. BS minus CS minus a big-M penalty for giving adjacent VMs the same back-up OS.

Two **importance measures** are also defined as inputs to the selection strategies: closeness `C_c(vm_i) = ((n−1) Σ_j d(vm_i, vm_j))^{-1}` (Eq. 1, p.5) and betweenness `C_b(vm_i) = Σ_{s,t} δ_st(vm_i)/δ_st` (Eq. 2, p.5); "we use two important NCMs, closeness and betweenness [12], to identify more crucial VMs in the cloud" (p.5).

Vulnerability parameters (BS/I/E) are sourced, not assumed: "the values for the vulnerabilities are real metrics drawn from the National Vulnerability Database (NVD) [31]" (p.14); the economic ones are not: "We have selected the economic parameters consistent with our modeling assumptions for the purposes of designing an experiment to demonstrate how mathematical optimization can be used to solve the optimal diversity assignment problem" (p.14). One parameter is conceded as unknown and fixed at unity: "because we lack real data to estimate ARO, we assume in all our evaluations that the ARO value is one (similar to [9])" (p.11).

### Explicit assumption list
The large-model section carries a numbered assumption block, which is the closest thing to a setup declaration: "Our additional assumptions are as follows: (1) The cloud provider permits virtual machine-live migration (VM-LM) for cloud-band nodes; (2) the VM-LM downtime is negligible; (3) the cloud provider purchases enough licenses for a back-up OS; and (4) the VMs' OS can be replaced with other variants if needed." (p.7). Plus: "we assume that the cloud provider has up to five OS variants as back-up. Note that increasing the OS variants raises the cloud provider's costs … For simplicity, we do not consider the cloud provider's costs in this section." (p.8) — i.e. cost is deliberately switched off in the security half and switched on in the economic half.

### Replications
**NOT STATED — no run count, no seeds, no repetitions, no confidence intervals, anywhere in the paper.** The word "simulation" appears in the contribution list ("Using simulation, we evaluate the MTD techniques based on economic and security metrics", p.2; "We conduct our experiments using simulation on a large cloud-band model", p.2) but no simulation protocol follows. The evaluation is in fact *analytic*: every security and economic metric is a closed-form sum over the enumerated attack-path set AP ("the computation will incorporate the analysis of all possible attack paths that are calculated using the upper layer of the HARM", p.7), so most conditions are deterministic given the model. The one genuinely stochastic condition — RVS random VM selection (p.8) — is reported as a single curve in Fig. 6 and Fig. 9 with **no averaging statement and no error bars** (p.8, p.12 renders). Termination/horizon exists only for Reliability ("during a 10-hour period", p.7).

### Statistics
No means, standard deviations, confidence intervals, or significance tests are reported for any result. The only dispersion statistic in the paper describes the *network*, not the results: "The standard deviation of the attack path lengths is 1.36" (p.7). Result tables (4, 5) report raw point values to 2 decimal places with a **"Best" row naming the argmax/argmin VM per column** (p.12 render).

### Anything else declared
Hardware and solver are declared **only for the optimisation experiment**: "the Gurobi solver obtains the globally optimal solution (associated with the maximum value of the expected net benefit) in 0.02 seconds on an ordinary laptop with 8.00 GBs of RAM and Intel Core i5 6360U CPU @ 2.00GHz" (p.14). The Gurobi model itself is published as supplementary material: "The Gurobi model for this instance of the O-DAP is provided in the Appendix, which can be found on the Computer Society Digital Library at http://doi.ieeecomputersociety.org/10.1109/TETC.2022.3155272, in which the value of 'big M' is considered to be 100,000" (p.14). SHARPE is named as the reliability tool (p.7). **No hardware, language, version, or code link is given for the HARM/metric computations themselves.**

## C. Results — how the numbers are shown

### Order of results
**Metric-family-major, then mechanism-arity-ascending, run twice.**
Half 1 (Section IV, security metrics, large cloud): (a) no-MTD baseline across all network sizes → (b) Diversity alone, varying number of variants and network size → (c) Diversity alone, varying *selection strategy* → (d) S+D+R vs. Diversity-only → (e) an all-metrics normalised summary.
Half 2 (Section V, economic metrics, small cloud): (f) Shuffle on each VM → (g) Diversity on each VM → (h) Diversity on multiple VMs, RVS vs. BVS, RoSI against cost → (i) the optimisation solution.
The order is driven by *dependency*: each step's winner becomes the next step's fixed setting (BVS wins in (c) and is then the only strategy used in (d), p.9).

Three different ways, one per figure family: as its **own figure** (Fig. 4, p.8), as a **dashed series inside the treatment figure** ("AC-Current", Fig. 5, p.8; "Current n=150 / Current n=400", Fig. 7b, p.9), and as the **upper row of a before/after gauge grid** (Fig. 8, p.10). ### How comparisons are stated in prose
All three registers are used, with **magnitudes given as absolute value pairs rather than percentages**:
- Magnitude (absolute): "Deploying OS diversification by assigning 5V in a cloud band with 400 VMs increases the AC value from around 2.3 million to three million, while the increase for 1V does not go beyond 2.5 million." (p.8); "RoA values of the cloud-band with 400 VMs are between one and 1.5 million … while this rate is between 300,000 and 350,000 for the cloud-band including 200 VMs" (p.8); "the highest RoSI metric after deploying the BVS strategy is about 75, while the highest RoSI metric resulting from the RVS strategy is 70" (p.12).
- Magnitude (percentage) — used exactly once, for reliability: "After passing 10 hours of an assumed attack with α = 0.2, the cloud-bands that are secured with S+D+R are around 40% reliable, while this rate reaches almost 0% for the current cloud-bands on which no MTD techniques are deployed." (p.9)
- Ordering: "deploying the Diversity technique on a set of VMs selected using BVS provides better results than the other groups" (p.8); "the most promising approach based on the security metrics is deploying the Shuffle technique on VM vm₅, which yields the lowest Risk_c and RoA_c values" (p.11).
- Trend/shape: "when the size of the cloud increases, the three metrics increase too, but the increase of the metrics is in a linear fashion" (p.7); "The values of RoA for the RVS groups have very gentle decrements … However, the RoA values for both the BVS and CVS groups decrease sharply when the OS diversification numbers increase" (p.8).
- Recommendation: "it appears that the cloud provider can incorporate both RoA and RoSI into the decision-making process, and prioritize them based on their values" (p.12); "we found that deploying S+D+R could help cloud providers keep the security level of the cloud at the desired level" (p.14).
- A **normalisation aside** that reframes a null result: "We could also consider how the metrics normalized by dividing by n change when n increases. Doing so indicates that the attacker has to spend more resources per VM if the defender has greater scope for diversity." (p.8)

## D. Narrative — the claims, in order

1. Baseline scaling: "when the size of the cloud increases, the three metrics increase too, but the increase of the metrics is in a linear fashion" (p.7). — establishes that the network-size sweep is well behaved before any treatment.
2. Diversity raises attacker cost, and more variants raise it more: "deploying Diversity on the VMs with higher betweenness ranks results in a larger increase in the costs for the attacker, and raises the AC value. This increase is greater if we add to the number of OS variants and deploy the Diversity technique on multiple nodes" (p.8), quantified from 2.3M → 3M for 5V at n=400 (p.8).
3. **A declared null result:** "We do not observe a any changes in the Risk values after deploying the Diversity MTD techniques. The Risk value remains almost steady after increasing the OS variants, but it still increases sharply after increasing the cloud-band nodes" (p.8) [*sic*, "a any"] — immediately rescued by the per-VM normalisation argument (claim in §C above).
4. Selection strategy matters and betweenness wins: "deploying the Diversity technique on a set of VMs selected using BVS provides better results than the other groups" (p.8), with RVS flat and BVS/CVS falling sharply (p.8).
5. Combination beats single: "We observe that the values of AC in D-Only are lower than the values of AC in S+D+R. However, the corresponding RoA values for S+D+R are also lower in D-Only, which shows that the attacker is less likely to attack again" (p.9). [The sentence is garbled in the original — the intended reading is that S+D+R has higher AC and lower RoA than D-Only.]
6. Reliability is where Redundancy pays: the 40%-vs-0% ten-hour comparison (p.9).
7. All-metrics summary: "deploying S+D+R decreased the RoA and the overall risk of the cloud, while the AC and Reliability values increased" (p.14, reading Fig. 8).
8. Economic half, Shuffle: the security-best and economics-best deployments are **different VMs** — "the most promising approach based on the security metrics is deploying the Shuffle technique on VM vm₅ … the most promising approach based on the economic metrics is deploying the Shuffle technique on VM vm₉, which yields higher RoSI_c values (RoSI_c = 2631) … However, when the VM vm₉ is selected for the Shuffle technique, it still yields adequate results for RoA of about 87 (the second highest RoA values)" (p.11–12).
9. Economic half, Diversity: here they agree — "deploying the Diversity technique on VM vm₅ yields the best results in terms of Risk_c, AC_c, and RoA_c. For the economic metrics, it yields the lowest ALE_c, which is 157266. It also leads to the highest BS_c and RoSI_c values, which are 2928 and 52.24" (p.12).
10. Diminishing returns / an interior optimum: "deploying the Diversity technique on the four VMs with the highest betweenness values reaches a peak and yields the best RoSI values, while the cost of security remains between $100 and $150. By contrast, the results based on the RVS strategy suggest that deploying nine back-up OSs increases the RoSI, but incurs the highest cost of security, of more than $250" (p.12).
11. Optimisation tractability: "While this instance of the problem has (|u|+1)^{|VM|} = 8⁹ = 134217728 feasible solutions, the Gurobi solver obtains the globally optimal solution … in 0.02 seconds" (p.14); "The optimal value of the expected net benefit is 117.8 which is achieved by assigning back-up operating system 6 to virtual machines 5 and 6 and back-up operating system 5 to virtual machine 9" (p.14). Scaling claim: "our formulation provided in (18) is a binary linear programming model, and can be used to efficiently find the globally optimal solutions to instances with thousands of virtual machines in a reasonable time" (p.13).

### Does the paper make claims about the ATTACKER's properties from the data?
**Yes — and this is its defining feature.** Two of the four security metrics are attacker-side by construction, and the paper reads results *off* them as statements about attacker behaviour and willingness:
- Framing at definition time: "we use the return on attack to evaluate the effectiveness of the combined MTD techniques from the attacker's perspective" (p.2); "RoA indicates the willingness of the attacker to use the same components, attack path(s), and vulnerabilities to penetrate the network" (p.5); "A higher value of RoA indicates a higher probability that an attacker will exploit those vulnerabilities (a higher tendency to attack)" (p.6).
- Read back as findings: "the corresponding RoA values for S+D+R are also lower in D-Only, which shows that **the attacker is less likely to attack again**" (p.9); "deploying the Diversity technique decreases the RoA values, which indicates that **the attacker would be less likely to attack**" (p.14); "Doing so indicates that **the attacker has to spend more resources per VM** if the defender has greater scope for diversity" (p.8); "deploying the Diversity technique can enhance the security of the cloud by increasing the AC values (i.e., **the attacker must expend more effort** to penetrate the cloud and exploit a target)" (p.14).
Crucially these are **inferences from a defender-computed ratio, not measurements of a simulated attacker** — no attacker is ever executed. The attacker's "willingness" is entirely an artefact of the per-CVE AC constants in Table 2/Table 3 and the max(E×I) numerator.

## E. Sensitivity / parameter analysis

**No section named sensitivity analysis.** But parameter variation is the paper's *primary presentational device* — every results figure is a sweep, embedded in the results rather than sectioned off. Four axes are varied, all one-at-a-time (no factorial grid, no interaction analysis):

| Axis | Range | Where | Justification given |
|---|---|---|---|
| Network size n (VMs in cloud-band) | 150, 200, 250, 300, 350, 400 | x-axis of Fig. 4 & Fig. 5; facets of Fig. 6; two levels in Fig. 7(b) | Only the platform envelope: cloud-band nodes accommodate "up to 450 VMs" (p.7). Why the floor is 150 is **not stated**. |
| Number of OS diversification variants | 1V–5V (security half); 1–9 (economic half) | x-axis of Fig. 6, Fig. 7(a), Fig. 9 | "we assume that the cloud provider has up to five OS variants as back-up" (p.8) — an assumption, not an argument. The economic half runs to 9 because the PHC has 9 non-target VMs (p.12). |
| VM selection strategy | BVS / CVS / RVS (security half); BVS / RVS (economic half) | series of Fig. 6, Fig. 9 | Motivated by the importance-measure argument in III.C: "we use two important NCMs, closeness and betweenness [12], to identify more crucial VMs" (p.5), with RVS as the random control. |
| Which single VM is treated | all 9/8 VMs, exhaustively | rows of Table 4 and Table 5 | "We deploy the Shuffle techniques on all VMs in the upper layer of the HARM, and evaluate the effectiveness of each migration scenario" (p.11); "We deploy the Diversity technique only on a single VM through **exhaustive search (ES)**" (p.12). |

The reliability horizon (0–10 hours) is a fifth swept axis inside Fig. 7(b) (p.9). The attack rate α = 0.2 is **not** swept — the discussion explicitly flags it as a knob that was fixed at one value: "we could also change the parameters used to obtain the desired results based on the type of cloud and the required security levels. For instance, we experimented with setting the attack rate at 0.2, and setting the OS diversification variants between 1v and 5v." (p.15). Also not swept: all economic constants ($20 Shuffle, $55 Diversity, AVs, EFs, ARO=1), the big-M value (100 000), and the topology.

What the sweeps are used to support: (a) that findings are not an artefact of one network size ("Other results for different cloud-band nodes show the same trend", p.8); (b) that the effect is *monotone in dose* (more variants → more AC, less RoA, p.8); (c) that there is an **interior economic optimum** (RoSI peaks at 4 VMs under BVS, p.12) — the one place where the sweep produces a non-monotone, decision-relevant shape.

## F. Discussion / limitations

**One combined section, VI. DISCUSSION AND LIMITATIONS (p.14–15), separate from results.** Structure: ~5 paragraphs of results recapitulation (with no new numbers, each paragraph pointing back at a subsection and figure), then Table 8 (qualitative pros/cons), then three paragraphs introduced by the run-in italic "*Limitations.*" (p.15). There is **no threats-to-validity heading, no attacker-realism concession, and no comparability caveat against other papers or tools** — no cross-paper numerical comparison is attempted anywhere in the article.

The discussion's own summary of what was found: "In Section IV-C, we showed that combining all MTD techniques (S+D+R) could improve all aspects of security with respect to the security metrics used (i.e., the Risk, AC, RoA, and Reliability values)." (p.14), and, notably, an explicit restatement of the *negative* result: "However, deploying the Diversity technique was not shown to have significant effects on the Risk and Reliability values." (p.14).

Verbatim limitation sentences (all p.15):
- Scope of the combination result: "**Limitations.** In this paper, we did not consider the economic metrics for combining all three MTD techniques. For each MTD technique, the security and economic metrics may be expected to vary in different ways. A multi-objective optimization was needed to solve the problem in such a way that the three MTD techniques could be combined effectively to satisfy the security and economic demands of the cloud provider based on certain constraints, such as the given model and the allocated budget."
- Model coverage: "Moreover, we only considered OS-level vulnerabilities on each VM in order to perform the security analysis, even though there were other vulnerabilities on each cloud's components, such as network, application, and service vulnerabilities."
- Same paragraph, the follow-on: "based on [19], it is important to construct a model that is able to specifically evaluate how different types of vulnerabilities, and the potential losses from such vulnerabilities, may affect the optimal security investment when combining MTD techniques."
- Optimisation coverage: "Finally, we deployed an optimization model for the Diversity technique, while modeling and formulating optimization models for other MTD techniques, such as the Shuffle and Diversity techniques. Moreover, multi-objective optimization can be utilized to find an optimal solution based on several objective functions, such as RoSI and RoA. We plan to address the use of an integrated optimization model in future work."
- **The timing concession — the most load-bearing one for an MTD paper:** "In addition, the optimal values we obtained were based on a single operation only, even though MTD techniques can be adapted and deployed on a periodic basis. While defensive MTD techniques can be deployed periodically or occasionally based on various factors, such as the annual rates of attack (ARO) or of intrusion detection, such approaches are outside the scope of this paper. However, we aim to address these issues in our future research."

An in-body scope exclusion, made earlier at model-definition time rather than in the discussion: "in the interests of the readability of our proposed HARM, more complicated vulnerability analyses, such as those discussed in [36], are considered outside the scope of this paper" (p.5).

The conclusion's strongest claims: "In comprehensive experimental analyses, we demonstrated that a combined approach was more effective than a single MTD technique" and "We also showed that our binary linear programming formulation could handle large cloud models in a fraction of a second on an ordinary computer" (p.16) — note the second is a solver-performance claim, and the first is stated without qualification even though the discussion concedes that Diversity moved neither Risk nor Reliability (p.14).

## G. Transferable vs purpose-specific

### Transfers to an honours dissertation evaluating existing MTD mechanisms against a new attacker model on a simulator

- **Defining each metric in its own numbered subsection with a display equation, placed immediately before the results that use it** (III.D.1–D.3, V.B–V.F) — and stating in one clause what the metric *means* and which direction is good ("A higher value of RoA indicates a higher probability that an attacker will exploit those vulnerabilities", p.6). This is the cleanest metric-declaration pattern of the four papers surveyed.
- **Composing metrics up the structure explicitly**: per-component → per-attack-path → per-system, each with its own equation (Eqs. 3→4→5, 6, 7→8, 9→10). It makes the aggregation choice auditable, which matters when a new attacker model changes which paths are actually walked.
- **A numbered, explicit assumption block** for the evaluated model ("Our additional assumptions are as follows: (1) … (4) …", p.7) — cheap, and it separates modelling choices from findings.
- **Naming the no-defence condition as a persistent reference** ("the current cloud-band" / "the current security posture", p.7) and carrying it into figures three different ways, including as a dashed series inside the treatment plot (Fig. 5, p.8).
- **A worked hand-computation of one metric on one path** ("Example 1 … Risk_{ap1} = … = 7.2 … Risk_c = 211.692", p.6) — a very effective way to make a metric definition checkable without shipping code.
- **Acronymised selection strategies as an explicit treatment factor** (BVS / CVS / RVS, p.8) with a *random* strategy as the control — directly reusable for "which hosts does the defence protect first" questions, and the random arm is what makes the betweenness claim interpretable.
- **Result tables that split columns into two labelled metric families and carry a trailing "Best" row** (Tables 4 and 5, p.12), so that a disagreement between families is legible at a glance (Table 4's Best row: security → vm₅, economics → vm₉).
- **Declaring a null result and then declaring the reframing separately** ("We do not observe a any changes in the Risk values …" followed by the per-VM normalisation argument, p.8) rather than quietly dropping the metric.
- **Stating when a parameter is a real datum versus an assumption**, in the same breath: "We have selected the economic parameters consistent with our modeling assumptions … However, the values for the vulnerabilities are real metrics drawn from the National Vulnerability Database (NVD)" (p.14); and conceding an unmeasurable one outright: "because we lack real data to estimate ARO, we assume in all our evaluations that the ARO value is one" (p.11).
- **A discussion limitation that names the abstraction a reviewer would attack first** — here, that MTD was applied once rather than periodically (p.15).

### Purpose-specific artefacts (IEEE TETC journal extension of an ACM MTD-workshop paper; analytic, not simulation)

- **No replication count, no seeds, no error bars, no CIs** — tolerable because the metrics are closed-form sums over an enumerated attack-path set, but *not* transferable to a stochastic simulator, and it is a live defect even here for the RVS (random-selection) arm.
- **The "simulation" vocabulary without a simulation protocol** (p.2) — the experiments are analytic evaluations of a graphical model; borrowing the word without the protocol would be a real weakness in a simulator dissertation.
- **Two different networks for two different metric families** (400-VM synthetic cloud-band for security; 10-VM hand-built e-health cloud for economics) — a consequence of the two-contribution structure, and it means no result in the paper is scored on both metric families on the same network.
- **The attacker as a rate constant and a source node** (α = 0.2, "outside the cloud", p.4/p.7): fine when the research question is defence-placement economics, and exactly the gap a new attacker model exists to fill.
- **Related work appearing twice** (Section II, and again as the untitled opening of Section V, p.10) — a journal-extension seam.
- **Deriving the combination criteria from the paper's own earlier results** (p.9) rather than declaring the conditions up front: it makes the S+D+R condition a *selected* configuration rather than a pre-registered one, and it is a page-budget/narrative artefact.
- **Table 8's qualitative pros/cons summary sourced partly from a survey rather than from the experiment** ("based on the results obtained in this study, and on insights from the MTD survey presented in [14]", p.15) — a review-article convention that would blur the evidence boundary in a dissertation.
- **The O-DAP optimisation half** (binary LP, Gurobi, big-M colouring constraint, solver-time reporting, published solver model) — a distinct contribution type; its reproducibility hygiene (exact solver, exact hardware, published model file) is worth copying even though the optimisation itself is not.
- **Absolute magnitudes in millions with no normalisation to a per-path or per-host basis** in most prose comparisons — readable inside a fixed model, unusable across models.
