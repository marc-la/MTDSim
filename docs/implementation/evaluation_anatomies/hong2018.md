# hong2018 — evaluation-section anatomy

Source read: docs/sources/lit_review/original/1.2_hong2018dynamic.pdf (PDF pp. 12–18 for §6–§8; journal pagination 33–52, so PDF p. N = journal p. N+32) and docs/sources/lit_review/1_2_hong2018dynamic.md (md lines 465–625). Locators are page numbers (PDF) or line numbers (md) — every claim below carries one. The md extraction has some column-order scrambling around §5.4/§6 (md 453–475) and §6.2.2/§6.2.3 (md 559–571); the PDF page text was used to confirm order.
Paper's own research question / purpose (one sentence, so its conventions are read against its purpose, not ours): to propose a set of *dynamic security metrics* (attack-effort and defence-effort, built on a temporal graphical security model, T-HARM) and to demonstrate via simulation that they can "assess and compare" the effectiveness of different MTD techniques — "it is of paramount importance to assess and compare their effectiveness. However, each technique causes distinct (dynamic) changes in the network, making an objective comparison difficult" (abstract, md 22; PDF p. 1). The simulation is a demonstration of the metrics, not the primary contribution: "This analysis also demonstrates the functionalities of the proposed metrics" (md 471; PDF p. 12).

## B. Setup — what is declared before any result

- **Network configuration(s):** "a generic dynamic network that could implement various MTD techniques (i.e., host and network configurations can be dynamically updated)" with an SDN-cloud example (md 481; PDF p. 13). Three declared network variables: "(1) the number of hosts, (2) the number of software variants, and (3) the number of network states" (md 481). Topology: "The initial connections between hosts are randomly assigned with a density value 0 > d > 1 [sic] (i.e., a host is connected to d∗N number of other hosts)" (md 481) — the value of d is **not stated**. The justification for the random generic network is generalisation: "To generalize our proposed approach, we conduct experimental analysis using a generic network that randomly connects the hosts, which includes any possible network configurations. By doing so, the subset of practical network configurations is included in the analysis" (md 473; PDF p. 12). Ranges actually run (read from figure axes, PDF pp. 14, 15, 17): hosts 10–20 (Fig. 4), variants 2–5 (Fig. 5), network states 2–10 (Fig. 6). Fixed values when not varied: variants = 3, states = 5 (md 499); hosts = 20, states = 5 (md 545); hosts = 20, variants = 3 (md 567). Number of distinct configurations: three one-factor sweeps (see §E). Other network properties are explicitly excluded: "other network properties (e.g., protocols, IP addresses, port number etc) can be modeled in the T-HARM ... " but are not (md 483).
- **Attacker model / scenarios:** one attacker, defined in `6.1.2. Threat model` (md 489; PDF p. 13). Scoped by threat type: "we scope the threat specific to a privilege escalation based on a STRIDE threat model (LeBlanc and Howard, 2002)". Position and goal: "the attacker is located outside the network, and aims to compromise a specific target host inside the network. The attacker must carry out a reconnaissance and execute exploitations in a sequence in order to compromise the target host." One behavioural rule under MTD: "if the chain of privilege escalation is broken (e.g., a shuffle technique redirecting service routes), then the attacker loses the privilege gained back to the last reachable host in the chain" (md 489). Not named, not bold-defined; there is a single attacker, no scenarios. Attacker capabilities are explicitly deferred: "The most difficult characteristic to quantify is the unknown nature of the attackers ... However, this is out of scope in this paper" (§5.4.3, md 463; PDF p. 12).
- **Defence conditions:** four "defense scenarios": "(1) no MTD techniques are used (base case), (2) shuffle-based MTD technique only, (3) diversity-based MTD technique only, and (4) combination of shuffle and diversity. For the case of (4), shuffle was applied to the network topology first and then diversified software on hosts" (md 483; PDF p. 13). **No-defence baseline: yes**, named "base case" in setup and "No MTD" in figure legends (PDF p. 14 key). Mechanisms defined in `6.1.3`: "(1) topology reconfiguration using the shuffle-based MTD technique (Hong et al., 2017) (shuffle-based for short), and (2) assigning software variants (Cox et al., 2006) to hosts using the diversity-based MTD technique similar to the one shown in Newell et al. (2013) (diversity-based for short)" (md 493). No schedulers, triggers, or timing parameters — MTD is modelled as a sequence of network states, "The number of network states is governed by the number of iterations made by the MTD techniques" (md 481). Optimisation of combinations is "out of scope" (md 483).
- **Parameter table:** **no** table in §6. Parameters are declared in prose (md 485; PDF p. 13): "The exploitability value for each software variant is randomly assigned uniformly between values 0.1 and 1 inclusive. The downtime, variant assignment cost, edge update time are all assigned with the value of one unit." Distribution declared for exploitability only (uniform [0.1, 1]). Justification for the unit values is stated as a scoping choice: "These values can be populated from empirical studies or other statistical data to be more accurate, but our analysis did not take those into account as we are focusing on comparing different MTD techniques when such parameters are changed" (md 485). Metric weights: "the weight distribution among selected metrics is equal (i.e., each dynamic security metric is equivalently important)" (md 499). (Earlier worked-example tables, Table 3 "Example SDN network states" and Table 4 "Basic metric values associated with variants", are on PDF p. 10 within §5.3, not the evaluation.)
- **Replications:** **not stated.** No runs, seeds, episodes or repetitions are declared anywhere in §6. The only acknowledgement of randomness is in the results: "There are slight variations due to the exploitability of variants being assigned randomly. However, the trend is still observed" (md 549; PDF p. 15). Horizon = the number of network states (2–10); termination rule: not stated beyond that.
- **Statistics:** none. No mean/std/CI/min–max/significance tests. Each plotted point is a single metric value in [0, 1] (all metrics are normalised; the reading convention is declared: "For attack efforts, a metric value toward one is making the attack more difficult, and for defense efforts, a metric value toward zero is making the defense more difficult ... For the overall combination ... a metric value towards one is beneficial to the defender", md 485).
- **Anything else declared:** hardware, software, implementation language, versions — **not stated**. A "Supplementary material" section exists (md 631; PDF p. 18) pointing to the online DOI; contents not described.

## C. Results — how the numbers are shown

- **Order of results:** by *swept variable*, one subsection each, in the order the variables were listed in the system model (hosts → variants → network states; md 481 → md 497/541/565). Inside each subsection the order is fixed and identical: (a) reconnaissance attack efforts, (b) resource attack efforts, (c) node defence efforts, (d) communication defence efforts, (e) overall effectiveness — i.e., attack-side metrics first, defence-side second, compound last. The paper walks panel-by-panel in prose ("Fig. 4a shows ...", "Fig. 4b shows ...", ..., "Finally, Fig. 4e shows ...", md 501–523). Every subsection opens with a one-to-three-sentence motivation for why the variable matters (e.g., "As the number of hosts increases, the management of the network becomes more complex", md 499; "The number of available software variants is a significant factor, as if the number of variants equals to the number of hosts, no such diversity-based MTD techniques are necessary", md 543; "In practice, there are tens of thousands of network states. But for comparing our chosen MTD techniques, we did not need so many observations to identify the changing attack and defense effort trends", md 567) and then states the fixed values of the other two variables.
- **Figures** (all three are the same 5-panel layout; series identical throughout; read from PDF pp. 14, 15, 17):
  - **Fig. 4** (PDF p. 14; md 511): "Comparative analysis of Shuffle and Diversity MTD techniques with respect to the changing number of Hosts." Five line charts with markers. x = No. of Hosts (10–20, integer steps). y = compound metric value in [0, 1] (each panel's y-range differs: (a) 0–0.7, (b) 0.65–0.95, (c) 0.5–1, (d) 0.75–1, (e) 0.6–0.8). Series (shared "Key" box in the sixth grid cell): No MTD (red square), Diversity Only (green triangle), Shuffle Only (purple cross), Shuffle + Diversity (blue star). Panel captions: "(a) Measuring the Reconnaissance Attack Efforts subcategory using a compound security metric with APV, APN and APE; (b) Measuring the Resource Attack Efforts subcategory using a compound security metric with ACE and ACD; (c) Measuring the Node Defense Efforts subcategory using a compound security metric with NVC and NVDT; (d) Measuring the Communication Defense Efforts subcategory using a compound security metric with EVC and EVT; (e) Overall Effectiveness of MTDs taking into account both Attack and Defense Efforts" (PDF p. 14). No error bars.
  - **Fig. 5** (PDF p. 15; md 537): same layout; x = No. of Variants (2–5). Caption: "Comparative analysis of shuffle and diversity MTD techniques with respect to the changing number of software variants."
  - **Fig. 6** (PDF p. 17; md 595): same layout; x = No. of Network States (2–10). Caption: "Comparative analysis of shuffle and diversity MTD techniques with respect to the changing number of network States."
- **Tables in the evaluation portion:** none. (Tables 1–4 are in §4–§5, PDF pp. 7, 10: terms, functions, an example SDN's network states, and basic metric values for variants.)
- **How the baseline appears:** "No MTD" is one of four series on every panel; on defence-effort panels it sits at the constant value 1 (no defence effort) — "There is no network node related costs for No MTD and shuffle-based MTD technique scenarios as they do not modify the network nodes" (md 517); on attack panels it is the flat lowest line ("not deploying any MTD techniques is not effective in increasing the attack efforts, but it keeps the number of attack paths constant", md 501). On the overall panel it is *not* always worst: "The result shows that not deploying any MTD technique is the best solution, because there are no defense efforts needed for this approach. However, if we increase the weight value of the attack efforts, then not deploying any MTD technique quickly becomes the worst scenario" (md 523; PDF p. 14–15).
- **How comparisons are stated in prose:** overwhelmingly *ordering* and *trend*, never magnitude. Examples: "the shuffle-based approach is slightly better than the diversity-based approach" (md 515); "The software diversity provided the highest attack efforts, followed by the combination of the shuffle and diversity" (md 547); "both shuffle and diversity-based MTD techniques are better than no MTD techniques deployed ... the combined shuffle and diversity MTD technique performed poorly" (md 557); "Only the shuffle-based MTD techniques benefited as the number of network states increased" (md 571). No percentages or absolute differences are reported anywhere in §6. Conditional *recommendations* close each subsection: "the diversity-based MTD technique would be most suitable when the network has the same number of software variants and network states, but the number of hosts increases" (md 523; PDF p. 15); and in §7.1: "the shuffle-based MTD technique is more effective than the diversity-based MTD technique when considering multiple network states to be generated, while it is the opposite if the network is expected to be expanding with a growing number of hosts" (md 581; PDF p. 17). Each observation is paired with a causal mechanism sentence ("This is because a large proportion of the attack paths is changed", md 501; "Shuffling the network topology can increase the length of attack paths, while diversifying software cannot", md 571).

## D. Narrative — the claims, in order

1. (hosts, attack recon) All MTDs raise attack effort as hosts grow, "because a large proportion of the attack paths is changed"; shuffle at small host counts "may have a negative impact as it may increase the number of attack paths"; No MTD is flat; combining shuffle with diversity "does not necessarily benefit" (md 501–513; PDF pp. 13–14).
2. (hosts, attack resource) Normalised attack cost falls with more hosts because "the attack surface is likely to increase ... provides more options for attacks"; shuffle "slightly better than" diversity (md 515).
3. (hosts, defence node/comm) Diversity's node cost grows with hosts; shuffle's edge cost grows with hosts; each technique costs nothing in the other's category (md 517–521).
4. (hosts, overall) No MTD is "best" at equal weights because it has no defence cost; becomes "worst" if attack-effort weight is raised; weight optimisation out of scope; diversity "most suitable" when hosts grow (md 523; PDF pp. 14–15).
5. (variants, attack recon) Number of variants "does not affect significantly"; diversity highest, then combination (md 547).
6. (variants, attack resource) "slight variations due to the exploitability of variants being assigned randomly. However, the trend is still observed"; shuffle-only and diversity-only "gradually decrease" → "less effective as the number of variants increases"; combination "may increase attack efforts if the deployment configuration can be optimized. However, it is out of scope" (md 549–553).
7. (variants, defence) Defence metric values rise toward 1 as variants → hosts (md 555).
8. (variants, overall) Both MTDs beat No MTD "even with equal weights"; combination "performed poorly" (md 557).
9. (states, attack recon) Little impact; APE up but APV down for diversity — "within path-based attack efforts, there were trade-offs" (md 569).
10. (states, attack resource) "Only the shuffle-based MTD techniques benefited"; mechanism: shuffle lengthens attack paths, diversity cannot (md 571, 559).
11. (states, defence) Diversity node cost rising "Although not very effective"; shuffle comm cost reduces with more states, with "a limit to the number of network states ... which will set the upper-bound of the defense efforts" (md 561).
12. (states, overall) Only shuffle benefits; "Even if the weight values are changed, the effect will be similar" (md 563).
13. (§7.1 synthesis) "there is a trade-off between the attack and defense efforts, as increasing the attack efforts also increases the defense efforts (i.e., reducing the security risk increases the security cost) ... in most cases, not using any MTD techniques showed the worst case for the attack efforts even though there are no defense efforts needed ... These results showed that MTD techniques can enhance the security posture of the network" (md 579; PDF p. 16).

**Claims about the attacker from the data:** none. The attacker is a fixed model (privilege-escalation chain, outside-in, single target; md 489). Every result is phrased as a property of the *network change* or the *MTD technique* ("attack efforts" are a metric of the defence's effect on the attack surface, not of attacker behaviour). The one attacker-related interpretation is structural, not empirical: more hosts "provides more options for attacks" (md 515). Attacker capability is explicitly declared out of scope in §5.4.3 (md 463) before the evaluation begins.

## E. Sensitivity / parameter analysis

**Present, and it *is* the results section** — the entire §6.2 is three one-factor-at-a-time sweeps of "network variables" (md 481), not a separate sensitivity analysis appended to a headline result. Parameters and ranges (ranges from figure axes, PDF pp. 14/15/17; fixed values from md 499/545/567):

| Swept | Range | Held fixed | Subsection |
|---|---|---|---|
| number of hosts | 10–20 | variants = 3, states = 5 | 6.2.1 (md 497) |
| number of software variants | 2–5 | hosts = 20, states = 5 | 6.2.2 (md 541) |
| number of network states | 2–10 | hosts = 20, variants = 3 | 6.2.3 (md 565) |

Design: one-at-a-time (OAT), not a grid. Range justification: **not stated** numerically; qualitative justification only (variants bounded by hosts, md 543; "we did not need so many observations to identify the changing ... trends", md 567). Reported as Figs. 4–6, one figure per swept variable. Sits inside §6.2 as the whole of the results. Claim supported: the conditional recommendations (which MTD "would be most suitable when ..." a given variable grows; md 523, 581) and the general trade-off claim (md 579).

A *second* sensitivity axis is discussed but **not run**: metric weights. Every sweep used equal weights (md 499); the effect of changing them is asserted verbally ("if we increase the weight value of the attack efforts, then not deploying any MTD technique quickly becomes the worst scenario", md 523; "Even if the weight values are changed, the effect will be similar", md 563) and deferred: "Finding a better distribution of the weight values ... is out of scope in this paper" (md 523); "In our experiment, we assigned the same weight values to all metrics, but in practice, they could be different" (md 613; PDF p. 18). Network density d and the unit costs (downtime, assignment cost, edge update time) are not varied.

## F. Discussion / limitations

Discussion is a **separate section** (§7, PDF pp. 16–18, md 573–619), four subsections, each ending with a "future work" sentence. The framing sentence: "In this section, we discuss our findings and limitations of our work" (md 575).

Contents:
- **§7.1 Comparing MTD techniques** — interpretation/synthesis of the sweeps into the trade-off claim and the conditional recommendation (md 579–581, quoted in §D.13 above). Future work: "we will consider incorporating more MTD techniques" (md 581).
- **§7.2 MTD techniques and threats** — scope concession on the attacker/threat: "We have mainly focused on the effectiveness of MTD techniques against the privilege escalation-based attacks in our comparative analysis. By focusing on a specific threat, we have classified the properties of attack and defense efforts related to that threat more precisely. However, it also scoped the ability to evaluate various MTD techniques that are designed for mitigating other threats" (md 601; PDF p. 17). Remedy is the modular category design; future work "to include various threats" (md 603).
- **§7.3 Security metric modules and weights** — comparability/weighting caveat: "Some security metrics may not be normalized due to the boundary-less nature (e.g., system risk), but the focus was to observe effort-based metrics" (md 609); "In our experiment, we assigned the same weight values to all metrics, but in practice, they could be different. For example, assigning a variant will have a significant cost to the defense node category, while SDN shuffling will have less cost to the communication category with respect to variant assignment" (md 613; PDF p. 18).
- **§7.4 Parameter measurement** — measurement-validity concession: "One of the major issues is to identify which subcategories of the attack and defense efforts are needed in order to characterize an MTD technique, and the relative efforts between them. For example, the value 0.5 computed for the downtime subcategory may be more significant compared to the value 0.8 computed for the service overhead ... However, the method to assign those weights is currently done manually" (md 617); "Some parameters, however, were more difficult to measure. ... relying on the impact scores from the vulnerability databases may not fully reflect the practical aspects of exploiting the vulnerability. However, there are various empirical studies ... and we expect the accuracy of those data would increase over time" (md 619; PDF p. 18).

No "threats to validity" taxonomy (internal/external/construct) is used. No statement about replication, variance or the randomly-assigned exploitability beyond md 549. The attacker-realism concession is entirely a *threat-scope* concession (§7.2) — nothing about attacker behaviour, knowledge or adaptivity. Comparability caveat is about metric weighting and normalisation (§7.3), not about comparability with other papers' numbers. Earlier scoping sentences that function as limitations but sit in the setup: "optimizing the combinations of MTD techniques for maximizing security is out of scope in this paper" (md 483); "our analysis did not take those [empirical parameter values] into account" (md 485).

## G. Transferable vs purpose-specific

**Transfers to an honours dissertation evaluating existing MTD mechanisms against a new attacker model on a simulator:**
- One umbrella evaluation section split into `Simulation setup` (system model / threat model / MTD techniques as three named sub-blocks) and `Simulation results` (md 477–495) — the three-part setup decomposition (network, attacker, defence) is the reusable unit.
- An explicit reading convention for every metric stated once in setup before any figure ("a metric value toward one is ...", md 485).
- Results ordered by the swept variable, each subsection opening with why the variable matters and the fixed values of the others (md 499, 545, 567), and the same panel sequence repeated in every figure so the reader learns the layout once.
- A named "No MTD"/"base case" series present on every panel (md 483; PDF p. 14).
- Every observation paired with a mechanism sentence ("This is because ...", md 501; "Shuffling ... can increase the length of attack paths, while diversifying software cannot", md 571).
- Recommendations phrased as conditionals on a network property rather than absolutes (md 523, 581).
- A discussion section organised by *topic* of limitation (threat scope, weighting, parameter measurement), each closing with a future-work sentence, rather than a flat bullet list (md 577–619).
- Declaring a scoping choice for unmeasured parameters honestly ("we are focusing on comparing different MTD techniques when such parameters are changed", md 485).

**Artefacts of this paper's own purpose/venue:**
- Deterministic, single-run, no-replication, no-error-bar plots (no runs/seeds stated anywhere in §6) — acceptable because the contribution is the metric definitions and the simulation is a "demonstrat[ion of] the functionalities of the proposed metrics" (md 471); a dissertation whose contribution is the empirical result could not inherit this.
- The results *being* the sensitivity sweep (three OAT sweeps of structural network variables with no headline experiment) — an artefact of demonstrating metric behaviour rather than answering an effectiveness question.
- Metrics normalised to [0, 1] and combined with equal weights into "compound" metrics, and the resulting "No MTD is best at equal weights" artefact (md 523) — specific to the effort-metric framework.
- Attacker as a fixed, unnamed, single privilege-escalation chain with capability "out of scope" (md 463, 489) — a consequence of the paper measuring the *network's* attack surface, not attacker behaviour.
- A generic random-graph network justified by "includes any possible network configurations" (md 473) rather than a concrete enterprise topology.
- Journal-format numbered headings (6.1.1–6.2.3, 7.1–7.4), no hardware/implementation statement, no parameter table.
