Paper's own research question / purpose: to propose "a network defense method based on random domain name and address mutation (RDAM), which increases the scanning space of the attacker through a dynamic domain name method and reduces the probability that a host will be hit by an attacker scanning IP addresses using the domain name system (DNS) query list and the time window methods" (:21). ## B. Setup — what is declared before any result

**Network configuration(s).** Two, declared at different points and never reconciled:
1. *Laboratory prototype* (:225): "we implemented a RDAM prototype and deployed it in our laboratory network according to Fig 1, in which all the software-defined switches and the controller were implemented in the X86 platform using Intel's DPDK (Data Plane Development Kit) [34]. The network's external address space was a Class C subnet, and there were 36 hosts in the network distributed within three physical subnets. One subnet included a web server and a FTP server, which were both set as public hosts, while in the other subnets, four internal hosts enabled the remote desktop service, of which two hosts were set as public hosts."
2. *Simulation* (:255): "we created a network of SDN switches using Mininet [35], and developed the RDAM controller using POX [36] to manage the SDN network. The network included _n_I_ = 12000 internal hosts, of which _n_E_ = 6000 hosts were public hosts; the external address space was a Class B subnet (_m_E_ = 65536); and the length of the 3LD was 4 (_l_ = 4)." Declared **once**, in §5.1.1, and then reused by back-reference: "The simulation environment is the same as that described in Section 5.1.1." (:297), "The simulation environment is the same as that presented in Section 5.1.1." (:347). A single-declaration-plus-back-reference convention, which keeps the three results subsections directly comparable.
3. A third configuration for the flow-table overhead: n_I = 12000, θ = 10 s (:379) — shares the simulation's host count.
Topology: not stated for the simulation beyond "a network of SDN switches"; no generator, no degree, no subnet structure. For the prototype: three physical subnets, 36 hosts. How either was chosen: not stated. The design constraint that shapes topology *is* stated in the method — "all the hosts should be configured in separate subnets" (:131), i.e. each host in its own /L subnet.

**Attacker model / scenarios.** Defined as a **three-way cross**, and the three axes are introduced in different places:
- *Scan repetition* — the only axis given a taxonomy paragraph: "we consider the following two typical scanning strategies: 1) non-repeat scans, which never scan the same address twice, usually employed in scanning tools; and 2) repeatable scans, in which the addresses scanned are generated randomly so they may be repeated, usually employed in worms and other malwares." (:233). Each strategy is tied to a real class of tool.
- *Scan target* — domain names vs IP addresses, appearing as numbered cases inside every subsection: "(1) Domain name scans", "(2) IP address scans by an external scanner", "(3) IP address scans by an internal scanner" (:245/:249/:253, :273/:285/:295, :305/:339/:345).
- *Scanner position* — internal vs external, folded into the same numbered cases.
So each of §5.1.1–5.1.3 works the identical three-case template, giving 3 defence/scan conditions × 3 scanner cases = 9 analysed cells, of which case (3) is trivially zero in all three ("the internal scanner cannot hit any host by scanning IP addresses", :253, :295, :345 — stated three times).
- The attacker's *rate* is the sweep variable, as a dimensionless ratio: "Assume that _r_ denotes the ratio of the attacker scanning rate to the defender mutation rate" (:269, restated :301). A boundary condition is stated before the analysis: "When _r_ ≤ 1, the domain name (IP address) will be changed between any two scans; therefore, the scanning process is equivalent to a repeatable scan, and the scan results are consistent with those presented in the previous section." (:269) — so the repeatable-scan case is positioned as the *limit* of the non-repeat case, which is why §5.1.1 comes first.
- Attacker capabilities are otherwise fixed by the threat premise in §3: the attacker cannot obtain a dynamic domain name (must go through the security authentication server, :89, :186), and the DNS query list / time window gate every connection (:129, :133).
- Simplifying assumptions stated at the head of §5.1.2 and repeated at §5.1.3: "that the external address mutation rate of all public hosts is the same; and that they mutate at the same time" (:269, :301); "assuming _r_ is an integer" (:271, :303).
- Tool named for realism: "The attacker uses scanning tools, such as Nmap, to discover the active hosts in the target network" (:233).

**Defence conditions.** Two mutation policies, defined in the method and carried into the evaluation as the subsection split: "1) uniform mutation, that is, the domain names and the external addresses are uniformly selected in the mutation space; and 2) failure-prior mutation, that is, the destination domain names and the addresses of the connection failure packets are preferentially selected." (:182). Crossed with the time-window parameter p ∈ {0.2, 0.8, 1} (figure legends at :359; prose at :257, :299).
- **The baseline is a named prior system, OF-RHM, and it is obtained as a *parameter setting of the proposed method* rather than by re-implementation.** Stated three times, once per results subsection, in near-identical wording: "In existing network address shuffling techniques, such as NASR [10], OF-RHM [11], etc., internal and external scanners can directly access an internal host once they hit the host's IP address, because of the lack of the DNS query list and the time window methods. Therefore, the result of the internal/external scanner scanning IP addresses in OF-RHM is equivalent to the result of the external scanner scanning IP addresses in RDAM when _p_ = 1 in Fig 5(B)." (:255; parallel sentences at :297 and :347). The figure legend carries this as a single fused series — "Exper. External p=1/OF-RHM" (:359). This is the paper's most distinctive convention: **the competitor is the p = 1 special case of the authors' own model, so comparison costs no extra experiment and no re-implementation.**
- A "without RDAM" condition also exists, but only for the delay measurement (:381, Table 1 row "Without RDAM").
- Scheduler: domain names mutate on a fixed global period ("the domain names of all hosts are periodically changed at fixed times", :137, :178); external addresses mutate per-host at a configurable rate R^E_i ("_R^E_i_ can be pre-configured, and the more critical a public host is, the higher its mutation rate should be", :137). Internal addresses "can mutate over a long period or remain unchanged" (:129).

**Metric.** One security metric, defined once at the end of the §5.1 preamble: "we will analyze the defense performance of RDAM when using uniform mutation and failure-prior mutation by calculating **the expected ratio of hosts missed by the scanner (to total hosts)**" (:233). The paper then notes an identity that lets it double as a per-host probability: "Because the probability of each host being hit is independent of each other host, the probability of the scanner missing each host is also the expected ratio of missed hosts." (:245). Everything in §5.1 is reported on this one axis, so all nine cells and all three subsections share a y-axis — the figures are directly stackable.

**Parameter table.** **None.** Parameter values are in prose at their point of use: n_I = 12000, n_E = 6000, m_E = 65536, l = 4 (:255); θ = 10 s (:379); p ∈ {0.2, 0.8, 1} (:257, :299, :359); internal address space m_I ≈ 2^24 + 2^20 + 2^16 (:113); domain space m_D = 36² × 37^(l−2) (:115). Distributions declared: "It can be assumed that the time interval of external hosts issuing the DNS query for _s_i_ follows an exponential distribution with parameter _λ_i_(t)" (:135) — used to derive the time window; hypergeometric for the hit count under failure-prior mutation (:319); uniform selection for both mutation policies (:182); Little's law for the flow-table length (:379).

**Replications.** Stated **three times, identically, once per results subsection**: "In the simulation, every data point was taken as the average of 10 runs, and the scanner executed a total of _m_E_ scans." (:255, :297, :347). Horizon is therefore m_E = 65536 scans per run, stated in the same sentence as the replication count. For the delay experiment: "we measured the delay results of connections between internal hosts and connections of external hosts accessing public hosts, ran 100 trials respectively by using 25 internal hosts/external hosts visiting 4 public hosts" (:381). Seeds: not stated. Termination: implicit at m_E scans.

**Statistics.** Figures report averages of 10 runs with no dispersion. **Table 1 is the exception and the only place in the paper where variance is reported** — the footnote reads "*average delay (standard deviation)" (:400), and cells read e.g. "24.57ms(1.52ms)*" (:395). No confidence intervals, no significance tests, no error bars anywhere. Note the asymmetry: dispersion is given for the *overhead* measurement and withheld from every *security* measurement.

**Other declarations.** Hardware, for the delay test only, in unusually complete detail (:381): "The software-defined switches and the controller were implemented in the X86 platform operating at 4 GHz using Intel's DPDK; the controller had two cores and 4 GB of memory; the switches had six cores and 8 GB of memory. All internal hosts, the DNS server, the DHCP server, and the security authentication server had two cores operating at 3.7 GHz and 4 GB of memory; the internal hosts ran the Win7 operating system, and the servers ran the Windows Server 2003 operating system. External hosts were generated through a server running Hyper-V with 32 cores operating at 3.9 GHz and 64 GB of memory; each external host had one core and 512 MB of memory running the Windows XP operating system." Tools cited: Mininet [35], POX [36], DPDK [34], Nmap (named, uncited at :233). Versions: not stated for Mininet/POX/DPDK. Feasibility check before any measurement: "We ran several network activities during mutation, including: 1) web browsing, FTP file download, and remote desktop connections … All network activities behaved normally, and long-lived connections were maintained during mutations. … Our implementation proved that RDAM is feasible in real networks." (:227).

## C. Results — how the numbers are shown

**Order.** Defence-policy-major, with the simplest attacker first. §5.1.1 repeatable scans (the case where "regardless of which mutation method the defender uses, the probability of the scanner hitting a designated host is the same as the probability in the static address environment", :241 — i.e. mutation policy does not matter, so it is analysed once); then §5.1.2 non-repeat under uniform mutation; then §5.1.3 non-repeat under failure-prior mutation. Inside each subsection the order is fixed: **closed-form derivation for case (1), (2), (3) → asymptotic regimes as a numbered list → figure → one paragraph reading the figure.** The identical template three times over makes the three subsections line up cell-for-cell.

**Tables.** One, `Table 1. **How the baseline appears.** Three ways, all distinctive: (i) as a *fused legend entry* with the p = 1 series (:359) rather than as its own curve; (ii) as a sentence repeated once per subsection establishing the equivalence (:255, :297, :347); (iii) as the "Without RDAM" row of Table 1 (:394) for the cost side. The static/no-defence case is not plotted at all in §5.1 — instead §5.1.1 argues that repeatable scanning against RDAM has "the same [hit probability] as the probability in the static address environment" (:241), making the static case a stated analytical reference rather than a measured one.

**Comparison phrasing.**
- Percentages read off the figure, in a fixed order and repeated near-verbatim across subsections: "RDAM allows 96.2% of hosts to be missed by internal and external scanners scanning domain names; an internal scanner cannot hit any host by scanning IP addresses; for external scanners scanning IP addresses, when _p_ = 1, that is, no time window, RDAM allows only 37% of hosts to be missed, while when _p_ = 0.2, RDAM allows 81% of hosts to be missed by adjusting the time window setting." (:257) — and at :299 the same sentence with "at most 37%" and "80%". The near-identical repetition is itself the comparison: the reader is shown that the domain-name result (96.2%) is invariant across scan types while the IP-address result is not.
- **Two-sided analytical bounds, stated as the headline for each case:** "when the number of scans is _m_E_, RDAM allows at most _e^−p_ and at least 1−_p_ of the hosts to be missed by the scanner." (:287); "RDAM allows at most (m_D − 2n)/(m_D − n) and at least 1−_m_E_/_m_D_ of the hosts to be missed by the scanner." (:337); "RDAM allows at most (m_E − 2pn_E)/(m_E − pn_E) and at least 1−_p_ …" (:343). Reporting a bracket rather than a point value is the paper's signature result form.
- **Numbered asymptotic regimes** replacing prose interpretation, e.g. (:277–281): "1) when _r_ ≪ _k_, … _P_miss_(r,k) reaches its maximum, and RDAM achieves the best defense performance; 2) when _r < k_ ∧ _r → k_, _P_miss_(k) ≈ 1−_r_/_m_D_; and 3) when _r_ ≥ _k_, … the domain name mutation offers no additional defense performance compared to the static environment." Four such regimes for the failure-prior case (:327–335).
- Monotonicity and its reversal: "we can see that _P_miss_(r,k) decreases as _r_ increases" for uniform mutation (:275), versus the non-monotone failure-prior result: "2) when _r < k_ ∧ _X_i < n_, the larger _r_ is, the larger _X_i_ is, and the better the defense performance is, so _P_miss_(r,k) **increases** as _r_ increases; 3) … so _P_miss_(r,k) **decreases** as _r_ increases" (:329–333), concluding "when _r_ = _n_/(1−_n_/_m_D_), _P_miss_(r,k) reaches its maximum" (:337) — an **interior optimum in the attacker's rate**, i.e. a scanning rate that is worst for the attacker.
- Overhead verdicts in plain terms: "the connection delay is unlikely to be noticed by users, and the transmission delay is negligible compared with the whole packet transmission process" (:381); "the established data flow packet transmission delay was negligible" (:227).
- Model-vs-experiment verdict, verbatim and identical in two places: "From the figure, we can see that **the experimental results are basically the same as those predicted by the theoretical analysis**." (:257, :299).

## D. Narrative — the claims, in order

§5.1:
1. Repeatable scanning is policy-insensitive: "regardless of which mutation method the defender uses, the probability of the scanner hitting a designated host is the same as the probability in the static address environment." (:241) — a negative result stated first, which is why §5.1.1 is short and does the whole repeatable case at once.
2. Domain-name scanning is defeated by space size alone: 96.2% missed (:257), because m_D ≫ m_E (:115, :283).
3. Internal IP-address scanning is defeated categorically by the DNS query list: "the internal scanner cannot hit any host by scanning IP addresses" (:253, :295, :345) — the same claim in all three subsections, an absolute rather than a probabilistic result.
4. External IP-address scanning is where the time window earns its place: 37% missed at p = 1 (= OF-RHM) vs 81% at p = 0.2 (:257) — the paper's central comparative number.
5. Under uniform mutation, faster attacker relative to defender monotonically erodes the defence (:275), with the r ≥ k regime giving "no additional defense performance compared to the static environment" (:281).
6. Under failure-prior mutation, the relationship inverts over part of the range and there is a rate at which the attacker does worst (:329–337).
7. (§5.2, lost: per the abstract and conclusion, RDAM "can effectively defend against scanning attacks and worm propagation" (:55, :416); per the surviving legend (:367), worm propagation is plotted for RDAM-Domain, RDAM-IP at p ∈ {1, 0.8, 0.2}, and OF-RHM on one axis over 3000 s.)

§5.3: flow-table length follows Little's law, ( w_1 + 2w_2 ) n_I θ (:379); connection delay ≈25–27 ms and insensitive to a million flow entries; transmission delay <1 ms (:381, Table 1).

**Claims about the ATTACKER's properties from the data.** Yes, and unusually the paper derives an attacker-side *optimum* rather than only a defence-side one:
- The interior maximum of P_miss in r (:337) is a statement about which scanning **rate** is worst for the attacker — derived analytically from the failure-prior recursion X_(i+1) = min(n, r − r(n − X_i)/(m_D − X_i)) (:319, :323), not measured.
- Scanner *classes* are tied to real adversary types by assertion: non-repeat scanning "usually employed in scanning tools", repeatable scanning "usually employed in worms and other malwares" (:233). No citation for either attribution.
- The attacker's knowledge is a modelling premise, not an inference: the attacker cannot get a dynamic domain name (:89), cannot build a hit-list (:55, :87), and is blocked from internal hosts absent a DNS query (:129).
- The one attacker-effort statistic in the paper is imported: "It has been reported that attackers can spend an average of 45 percent of their time performing reconnaissance [1]." (:39) — the same claim crouse2015 makes uncited (`2808475.2808480.md:35`); here it carries a citation.
- Nothing about the attacker is inferred from the simulation output; the simulation only checks the closed forms.

## E. How theory and simulation are reconciled

This is the paper's most systematically executed convention, and it is stronger than crouse2015's or jafarian2015's.
- **Every security figure is a paired theory/experiment overlay.** Each of Figs. 5, 6, 7 is introduced with the same formula: "Fig N shows **the theoretical and experimental results** of the ratio of hosts missed by …" (:255, :297, :347). Legend entries are explicitly labelled "Theor." and "Exper." per series (:359), so agreement is readable curve-by-curve rather than in aggregate.
- **The derivation always precedes the figure within the same subsection**, case by case, so each plotted series has an equation behind it. The three numbered cases in the prose map onto the plotted series.
- **The verdict is a fixed sentence, repeated verbatim:** "the experimental results are basically the same as those predicted by the theoretical analysis" (:257, :299). No residual, no error metric, no goodness-of-fit — the same weakness as jafarian2015 (":313, roughly consistent"), but applied consistently to every figure rather than to one.
- **The simulation configuration is stated once and back-referenced** (:255 → :297, :347), so the three overlays share parameters exactly. This is what crouse2015 fails to do (its analytical and simulated honeypot densities differ, `2808475.2808480.md:143` vs `:229`).
- **Theory covers regimes the simulation cannot reach.** The asymptotic regimes (r ≪ k, r → k, r ≥ k; :277–281, :327–335) and the closed bounds (:283, :287, :337, :343) extend past the plotted x-range of 0–60000, and the paper leans on them for its general claims while using the figure only for the specific p values.
- **One theoretical curve is claimed to cover three experimental conditions** — legend "Theor. External p=0.2,0.8,1" (:359) — a compact way of showing that the model collapses a parameter the experiment varies.
- **Prototype and simulation have disjoint jobs and are never cross-checked**: the 36-host prototype does feasibility (:227) and delay (:381); the 12000-host Mininet network does security (:255). No statement reconciles the class-C prototype with the class-B simulation, and no result appears in both.

## F. Sensitivity / parameter analysis

Present, distributed through §5.1 and §5.3, not sectioned separately.
- **Primary sweep: r, the scanning-to-mutation rate ratio**, x-axis of Figs. 6 and 7 over 0–60000 (:359). Dimensionless by construction (:269), so results do not depend on the simulator's time unit — the same device jafarian2015 uses (Γ = η/θ).
- **Secondary sweep: scanning number k**, x-axis of Fig. 5, run to k = m_E = 65536 (:255).
- **Series parameter: p, the time-window access probability**, at {0.2, 0.8, 1} (:257, :299, :359). p = 1 doubles as the OF-RHM baseline, so the sweep and the comparison are the same axis.
- **Design-parameter sweeps in the overhead section:** session establishment rates w_1 and the ratio w_2/w_1 (Fig. 9, :379) — a two-factor sweep; flow-table occupancy at {0, 1 million} entries (Table 1) — a two-level stress factor.
- **Design:** one-at-a-time with p as series; no factorial; no cell count reported.
- **Range justification:** not stated for r, k, or the w's. p's levels are unjustified but their *meaning* is derived: p is the probability an external host can reach a public host within the time window, and the window is solved from it — "we set the above probability of each public host as _p_. Then the time window of _s_i_ is win_i = −ln(1−p)/λ_i(t); that is, the more a public host is DNS-queried by external hosts per unit time, the smaller its time window will be." (:135). So the swept parameter is an operator-facing service level, not an arbitrary knob. l = 4 is justified structurally rather than empirically: "By setting the appropriate _l_, _m_D_ can be much larger than _m_E_ … In particular, when _l_ is 6, the size of the domain name space can be the same order of magnitude as the entire IPv4 address space size." (:115) — note the justification quotes l = 6 while the experiments use l = 4, with no comment.
- **Claim supported:** that RDAM's domain-name channel is insensitive to attacker rate while its IP channel is not, and that the time window (p) is the tunable that recovers the IP channel.

## G. Discussion / limitations

**§5.4 Discussion (:404–410) is the only limitation-bearing text, and it is a subsection of the evaluation.** Three paragraphs; the first is a compatibility argument, the second and third are genuine limitations. Verbatim:

> "RDAM is a network-based defense method, so it can be used simultaneously with host-based defense methods, such as firewall, to strengthen the network security. Also, RDAM does not affect the normal use of VPN (Virtual Private Network), because 1) when a VPN connection is established, the corresponding flow table entries are installed in the SDN switches, so VPN communications will not be interrupted due to domain name and network address mutation, and 2) as we described in Section 4.4.1, RDAM implements ALG in the switch connected to the gateway to perform the detection and address information replacement of the TCP/UDP payloads including those of VPN protocols." (:406)

> "The topology of RDAM is that a number of hosts and physical subnets are connected to the SDN network composed of SDN switches and the controller. However, RDAM does not support the topology that hosts and physical subnets are connected to the SDN network behind routers, because communications within routers will not be forwarded to the controller (if they can, the routers are actually SDN switches), and thus will not be protected by RDAM." (:408) — a **deployment-scope limitation stated with its mechanism**, and with no mitigation offered.

> "In addition, because internal hosts cannot access each other by scanning IP addresses, so some LAN software based on scanning IP addresses cannot work normally in RDAM. In further work, we will consider establishing a virtual network in RDAM, mapping the IP addresses of the hosts using LAN software to the network to allow these hosts to communicate through a specific port and protocol without leaking the IP addresses." (:410) — **the paper's strongest security result (internal scanners hit nothing, :253/:295/:345) restated as its own usability cost.** Naming the same mechanism as both the headline result and the headline limitation is the most transferable move in this section.

Other limitation-adjacent statements elsewhere, verbatim:
- "the external address space is _S_E_ ⊆ _S_P_ with a size (the number of available public addresses) _m_E_ = |_S_E_| that is very limited because of the IPv4 address space allocation strategy." (:113) — the constraint the whole design works around.
- "if hosts in the same physical subnet are configured with the same subnet, then they can directly access each other without protection. Therefore, in RDAM, all the hosts should be configured in separate subnets." (:131) — a configuration precondition for the security claim to hold.
- "IP address mutation may disrupt the normal communication of these protocols." (:219, on FTP/GRE payload-embedded addresses), immediately followed by the ALG mitigation.

**Absent:** any threat-to-validity discussion of the evaluation. Nothing on the gap between the 36-host prototype and the 12000-host simulation, the unstated simulated topology, the choice of l = 4 against the l = 6 justification, the absence of dispersion on the security figures, or what "basically the same" means quantitatively. The Conclusion (:412–416) carries no limitations at all.

**Replication statement — verbatim, and it is a venue requirement rather than an authorial choice:** "**Data Availability Statement:** All relevant data are within the paper." (:31). No code release, no seeds, no versions. Also carried: "**Funding:** This work is supported by the National Natural Science Foundation of China (nos. 61271252). The funder had no role in study design, data collection and analysis, decision to publish, or preparation of the manuscript." (:33); "**Competing interests:** The authors have declared that no competing interests exist." (:35); an Author Contributions section (:424). The reproducibility position is therefore: the closed forms and the stated parameters are reproducible; the simulation is not.

## H. Transferable vs purpose-specific

**Transfers to an honours dissertation evaluating existing MTD mechanisms against a new attacker model on a simulator:**
- **Deriving the comparator as a parameter setting of your own model** (OF-RHM ≡ RDAM at p = 1, :255/:297/:347) when the prior technique is genuinely a special case, and saying so once per results subsection so a reader arriving at any figure has the equivalence to hand. Fuse the label into the legend (:359) rather than plotting a separate curve you did not measure.
- **Declaring the experimental configuration once and back-referencing it** ("The simulation environment is the same as that described in Section 5.1.1", :297, :347). Cheap, and it guarantees the subsections are comparable — precisely the failure mode crouse2015 exhibits.
- **One security metric for the entire results section** (:233), with the identity that lets it read as both a population ratio and a per-host probability (:245). Every figure then shares a y-axis.
- **A fixed three-case template repeated across every subsection** (domain scans / external IP scans / internal IP scans), so the reader learns the shape once and can compare cell-to-cell across defence policies.
- **Overlaying theory and experiment series-by-series with "Theor."/"Exper." legend labels** (:359) rather than reporting agreement in aggregate.
- **Reporting two-sided bounds rather than point values** ("at most _e^−p_ and at least 1−_p_", :287) — a result form that survives parameter disagreement.
- **Enumerating asymptotic regimes as a numbered list before the figure** (:277–281, :327–335), including the regime where the defence provides nothing ("offers no additional defense performance compared to the static environment", :281). Naming your own null region is a credibility move a dissertation can afford.
- **Reporting a non-monotone result and locating its optimum** (:337) — an attacker rate that is worst for the attacker. Directly analogous to finding the MTD interval that maximises attacker cost.
- **Stating the replication count in the same sentence as the horizon** ("average of 10 runs, and the scanner executed a total of _m_E_ scans", :255).
- **A stress row in the overhead table** (1 million flow entries, :396) chosen to test whether the cost scales, alongside the ordinary case.
- **Restating your strongest security result as your headline usability limitation** (:410) — the single most useful paragraph in the paper to imitate.
- **Running a feasibility pass with named real workloads before any measurement** (:227: web browsing, FTP download, remote desktop, long-lived connections) and reporting that it passed.

**Purpose-specific / artefacts of this paper's aim and venue:**
- The DNS/domain-name mutation mechanism itself, and with it the m_D ≫ m_E argument (:115) that supplies the paper's largest number (96.2%) — the result is a property of alphabet size, not of a scheduler; nothing transfers except the habit of naming where a defence's leverage actually comes from.
- Live SDN implementation (Mininet + POX + DPDK), flow-table sizing by Little's law (:379), and connection/transmission delay measurement (Table 1) — all require an implementation, not a simulator.
- PLoS front matter: Data Availability, Funding-with-no-role, Competing Interests, Author Contributions (:31–35, :424). Venue-mandated; note that the Data Availability statement is satisfied by "within the paper" with no artefact.
- Dispersion reported only for the overhead table and withheld from every security figure (:400 vs :255) — do not import the asymmetry; a simulation-first dissertation needs the dispersion on exactly the results this paper omits it from.
- No parameter table across a 22-page article — workable with the single-declaration-plus-back-reference device, but a table would still serve a dissertation better.
- "basically the same as those predicted by the theoretical analysis" (:257, :299) as the entire agreement claim — the *practice* of overlaying transfers; the *phrasing* does not. Quantify it.
- l = 4 used in experiments while the justification paragraph argues from l = 6 (:115 vs :255), uncommented — a defect, not a convention.
- The prototype (36 hosts, class C) and the simulation (12000 hosts, class B) never meeting — acceptable when their jobs are disjoint and stated as such, but it leaves no evidence that the security results hold on the implementation.
