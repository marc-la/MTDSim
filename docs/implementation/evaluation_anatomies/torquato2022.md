## B. Setup — what is declared before any result

- Network configuration(s): none in the network sense. The system is three components — "_Primary Host_ … _Target Host_ … and _VMs_" (line 89) — justified by generality: "We consider this architecture appropriate for the scope of this paper because it is the baseline of virtualized environments. It appears in various systems: from small-sized virtualized environments to large-scale cloud computing" (line 89). The one structural quantity that varies is the number of hypervisor variants: "we studied the MTD behavior while having up to four variants, as we have four major _hypervisors_ for server virtualization: Xen, KVM, ESXi, and Hyper-V" (line 102) — the range 1–4 is justified by an external fact about the market, not chosen for illustration.
- Attacker model / scenarios: one attacker, no named scenarios. Two phases, each with its own SPN encoding: a _reconnaissance_ phase (transition reconV1, 30 minutes, line 223) and an _attack_ phase modelled as "a four-phase (transition atkV1Phase) Erlang sub-net to represent the increasing success rate of the _attack_ phase" (line 177), 6 hours per phase so "_attack_ phase total delay is of 24 hours" (line 226). The behavioural assumption is stated once and defended: "the attacker follows a _persistence_ tactic. This way, the VM migration can only interrupt the attack progress temporarily. Once the attacker identifies the _hypervisor_ variant, it is possible to resume the attack based on the obtained knowledge. The net does not remove the tokens stored in the places related to the _attack phase_ upon VM migration triggering" (line 179). The alternative is named, costed, and explicitly excluded: "it is possible to adapt the models to cover _non-persistent_ attacks (i.e., remove the attack progress after each migration) by adding cleaning transitions … However, we emphasize that _non-persistent_ attacks are out of the scope of this paper" (line 179). Attack start time is declared: "we consider that the attack is in place from the initial moment of the evaluation (i.e., attack starts at time _t_ = 0)" (line 252).
- Defence conditions: one mechanism — time-based VM migration with hypervisor diversification, characterised as three properties: "i) applies a regular time interval between VM migration triggering; ii) follows the _live migration_ approach [8] and iii) the migrations are made between different hypervisors to enforce _diversity-based_ MTD deployment" (line 33). Two orthogonal defence knobs: the trigger interval (transition migTrigger) and the variant count (1N/2N/3N/4N). Baselines: two, and both are named as such — an availability baseline "in which the VM migration is disabled" (line 230) and a security baseline "The **1N** curve corresponds to the probability of attack success with disabled MTD" (line 252).
- Parameter table: yes, one results-bearing table plus one structural table.
  - Table II "PARAMETERS USED IN THE TIMED TRANSITIONS" (lines 205–226), columns: Transition | Description | Delay. Fourteen rows. The swept parameter is entered as a non-value: "migTrigger | Time for VM migration | **Depends on the scenario**" (line 211). Two footnote rows carry the parameters that are not scalars: ∗1 gives the marking-dependent pre-copy delay in closed form, "pcMigrationdelay = _PC_ + _PC_ ∗ (#_FailureProbable_)/3, where _PC_ = 72 seconds" (line 225); ∗2 converts the per-phase Erlang delay to a total, "As we have four Erlang phases, _attack_ phase total delay is of 24 hours" (line 226).
  - Table I "GUARD FUNCTIONS" (lines 106–121), columns: Transition | Guard function | Guard function description — ten rows of boolean firing conditions (g1–g10). This is model structure, not parameters, but it is declared in the same declarative-table register.
  - Distributions: declared per transition class in the model text rather than in the table — deterministic transition for the clock (line 125, "The CLOCK MODEL has a deterministic transition, migTrigger, whose delay represents the interval between migrations"), exponential ("white rectangle", line 143), immediate transitions carrying the guard functions (line 104), a two-phase hypoexponential for aging ("we use a two-phase (i.e., transitions agingPhase and agingAccumulation) hypoexponential net to represent the increasing failure rate due to software aging", line 157), and a four-phase Erlang for attack progress (line 177). Marking-dependent firing rates are declared and motivated: "Software aging may slow down the pre-copy phase as it affects system performance. We use marking dependent firing rates to represent this behavior" (line 135).
  - Parameter provenance is stated in one sentence, with the estimation admitted: "We consider the parameters in Table II for the case studies presented below. **These parameter values come from previous published papers [7] [24] [28]. Note that it is necessary to estimate some of these values since they are unavailable or are hard to obtain through experimentation.** For the sake of simplicity, we assume the same _reconnaissance_ and _attack_ phase delays for all the available _hypervisor_ variants. Moreover, in the lack of _hypervisor_-specific aging parameters, we also use the consolidated values from the works mentioned above in all the _hypervisor_ variants" (line 193). Which specific rows are cited vs estimated is **not stated** — the citation is blanket.
- Replications: none — analytical/numerical SPN solution, no simulation. Horizon: declared per case study, not globally. CS#1 is steady-state (line 230); CS#2 is transient with an explicit window, "The evaluation results show the probability of attack success curve in the first week (168 hours) of the system runtime" (line 252). Termination rule: not applicable; but a steady-state degeneracy is disclosed in a footnote — "It is worth noting that the steady-state _PAS_ is equal to 100% because of the considered _persistence_ tactic adopted in the attack" (line 258), which is why CS#2 must be transient.
- Statistics: none. No means, CIs, error bars, or significance tests anywhere; every number is a single deterministic model output.
- Anything else declared: tool — "We use TimeNet tool [27] for model design and analysis" (line 193; also line 193 is the only place the tool appears). Hardware, versions, solver settings, numerical tolerances: **not stated**. Validation is declared by inheritance in the related-work section rather than by experiment: "Our previous paper [7] presents the validation of the considered MTD model through simulation … So, the model presented in the current paper leverages a **partial validation** from these works" (line 343).

## C. Results — how the numbers are shown

- Order of results: availability first (CS#1), security second (CS#2), trade-off third (CS#3) — the order is forced by the chaining, since CS#2 and CS#3 both consume CS#1's 5.1 h answer. Each case study opens by restating its RQ in italics as a question (lines 199, 252, 308).
- Every figure in the evaluation portion:
  - **Fig. 3** "CS#1 Results" (caption at line 235, inside the picture-text block), a two-panel figure sharing one x-axis: x = VM Migration Trigger (h), ticks 0/6/12/18/24/30/36/42/48. Panel (a) "Steady-state availability", y = Steady-state Availability, 0.994–0.999, **two series: "Baseline" and "Rejuvenation"** (the baseline is a flat reference line, since it does not depend on the swept parameter). Panel (b) "Downtime reduction", y = Downtime reduction (h/yr), 16–32, one series (the baseline is the zero of the derived metric, so it does not appear as a line).
  - **Fig. 4** "CS#2 Results" (caption line 267; axis text line 265), line chart, x = Time (h) 0–168 with 24 h ticks, y = Probability of Attack Success 0–1, four series **1N / 2N / 3N / 4N** (1N = MTD disabled). Time, not a parameter, is the x-axis here.
  - **Fig. 5** "CS#4 Results" [sic — the caption says CS#4 though the section is CS#3, line 319], **dual-y-axis** line chart, x = VM Migration Trigger (h) 0.5–5, left y = "Increased Resistance (IR) PAS=10% (h)" 0–55, right y = "Downtime Reduction (h)" 0–32. Four series: three IR curves (IR 2N, IR 3N, IR 4N) plus one downtime-reduction curve. Series identification is by colour and stated in prose rather than left to the legend: "_IR_ results curves are in black … The downtime reduction curve is in gray" (lines 310, 316).
  - No facets, no error bars (analytical).
- Every table in the evaluation portion:
  - **Table III** "COMPARISON BETWEEN BASELINE AND AVAILABILITY-AWARE MIGRATION TRIGGER RESULTS (5.1 HR)" (lines 239–248): 1 row × 5 columns — baseline availability, baseline downtime (h/yr), rejuvenation-enabled availability, rejuvenation-enabled downtime (h/yr), downtime reduction. Values 0.995068 | 43.20 | 0.99861 | 12.19 | 31.01. A two-condition head-to-head at the single selected parameter value.
  - **Table IV** "_PAS_(_t_) WHILE USING _migTrigger_ = 5.1 HRS" (lines 271–281): 5 rows (t = 1, 6, 24, 72, 144 hours) × 4 columns (1N, 2N, 3N, 4N). Reads point values off Fig. 4 at chosen times.
  - **Table V** "_ETTL_ RESULTS WHILE USING _migTrigger_ = 5.1 HRS" (lines 289–298): 4 rows (PAS = 1%, 20%, 70%, 100%) × 4 columns (1N–4N). The **axis-inversion table**: the paper states the design reason explicitly — "The time (_t_) is the independent variable in the _PAS_(_t_) calculation, and _PAS_ is the dependent variable. However, there are other systems where we need to swap these variables" (line 285).
  - **Table VI** "MULTI-CRITERIA DECISION MAKING - VM MIGRATION TRIGGER ALTERNATIVES" (lines 329–339): 5 rows (weight triples) × 7 columns (w_ir, w_dwt, w_cost, best-solution migTrigger, best-solution architecture, IR, downtime reduction). A sweep over *decision weights*, not model parameters.
  - Table VII (lines 381–391) is a related-work feature matrix, outside the evaluation.
- How the baseline appears: three different ways, one per case study. CS#1 — as its own plotted series and its own table column ("Our results also include the _baseline_ scenario, in which the VM migration is disabled", line 230). CS#2 — as the degenerate level of the variant-count factor (1N, line 252). CS#3 — subtracted away: the reported metric *is* a difference from baseline, "_IR_ is the _ETTL_ difference between the system with and without MTD" (line 308), as is downtime reduction, "the difference between the expected downtime results with and without software rejuvenation" (line 230).
- How comparisons are stated in prose: **percentages and absolute deltas against the baseline**, consistently, and always tied to the specific condition. "Even the worse rejuvenation scenario (i.e., VM migration trigger of 30 min) produces more than 16 hours of annual downtime reduction compared to the baseline" (line 232); "it reduces the annual downtime by more than 70% when compared to the baseline scenario" (line 237); "in the case of the 4_N_ architecture, the reduction is 47%" (line 283); "when _PAS_ = 70%, the use of a 4_N_ architecture more than doubles the _ETTL_ when compared to the 1_N_ architecture" (line 300). Null results are stated as plainly as positive ones: "The results show that, up to 6 hours, the use of MTD provides no reduction in the probability of attack success" (line 283); "the results suggest that assuming _ETTL_ = 1%, it makes no difference in applying MTD or not" (line 287). Recommendation language is confined to an explicitly hypothetical worked example (line 302) and to the MCDM (line 325).

## D. Narrative — the claims, in order

1. Sweep-range framing before the sweep: the trade-off is asserted mechanistically first, so the sweep has a shape to find — "Frequent migrations may increase system downtime because of the interruptions associated with each migration. Alternatively, less frequent migrations increase the chance of software aging failure due to the lack of timely rejuvenation actions" (line 199).
2. Whole-range claim, then point claim: "The availability improvement is noticeable among the entire sensitivity analysis range" (line 232), then the optimum, "Our results suggest that the _availability-aware migration trigger_ is of 5.1 hours" (line 237), then its baseline-relative size (Table III, >70% annual downtime reduction, line 237).
3. Shape claims from Fig. 4: "We notice a flattening effect on the curve while increasing the number of _hypervisor_ variants. We also see that the MTD has a **time window of effectiveness**, which means that there are intercepts of _PAS_ curves at the early or late stages of the evaluation. There is no MTD effect on reducing the probability of attack success compared to the system without MTD in these stages" (line 254).
4. Boundary conditions of that window, mechanistically explained by the parameter value used: "at the early stages of the evaluation (_t_ < 5.1 hours), the MTD effect is yet to take place as the system is still waiting for the first migration" (line 283); and at the far end, "the difference of _PAS_ results with _t_ > 144 hours is negligible" (line 283).
5. Metric-invention claim: the secondary metrics are justified by practitioner use-cases, not by the model — "_PAS_(_t_) results are relevant for systems with job completion deadlines" (line 256); "_ETTL_ is particularly useful when setting up security SLAs because it highlights the expected system resistance time observing a _PAS_ tolerance level" (line 285).
6. Trade-off claim: "while the best policy for maximizing system availability is on the rightmost side of the plot, the best policy for security is on the leftmost side. It is noticeable that deciding on one of the metrics (availability or security) will compromise the other. **It is hard to define the best policy** as the availability and security requirements depend on the specific business running in the virtualized environment" (line 321) — an explicit refusal to give a single answer, which is what motivates the MCDM.
7. MCDM claim, with a mechanism given for why the weights behave as they do: "The MCDM results suggest a preference for security-aware VM migration triggers … over availability-aware triggers. We see this behavior because **the range of values in the _IR_ curves is wider than the range of values in the downtime reduction curve**" (lines 325–327) — i.e. the ruling is attributed to the scales of the swept outputs, not to the criteria themselves.

Claims about the ATTACKER from the data: minimal, and hedged. The attacker's parameters (recon 30 min, attack 24 h Erlang, persistence) are pure inputs; nothing about the attacker is inferred from the output. The one attacker-side statement derived from the model is a degeneracy disclosure rather than a finding — "the steady-state _PAS_ is equal to 100% because of the considered _persistence_ tactic" (line 258) — and one mechanism attribution, "This delay is due to the accumulation of attack progress interruptions during the MTD deployment" (line 300). The results are consistently phrased as properties of the *defence* ("MTD has a time window of effectiveness"), never as a ranking of attackers.

## E. Sensitivity / parameter analysis

Present: yes, and the paper **names it as such** — "We search for the _availability-aware VM migration trigger_ using **sensitivity analysis** of transition migTrigger delay on the system availability" (line 230). It is one parameter only, and the paper admits this in future work (see F).

- Parameter varied (the sensitivity analysis proper): **migTrigger** — the interval between VM migrations. Range and step are given verbatim and completely, in one sentence: "We study the steady-state availability while varying VM migration triggers **from 30 minutes to 48 hours using a 6-minute (0.1 hours) step**" (line 230). That is 286 evaluated points; the paper does not state the count. It is the only parameter in Table II given as "Depends on the scenario" (line 211) rather than a value.
- Second varied factor (not called sensitivity analysis): **number of hypervisor variants**, levels 1N / 2N / 3N / 4N (line 252). Range justified by an external fact: "we studied the MTD behavior while having up to four variants, as we have four major _hypervisors_ for server virtualization: Xen, KVM, ESXi, and Hyper-V" (line 102).
- Design: **one-at-a-time in CS#1 and CS#2, a 2-factor grid in CS#3**. CS#1 sweeps migTrigger with variant count irrelevant (availability model only). CS#2 freezes migTrigger at the CS#1 optimum (5.1 h) and sweeps variant count. CS#3 crosses them — three IR curves (2N, 3N, 4N) each over the migTrigger range. All other Table II parameters are held at their tabled values throughout; no other parameter is ever varied.
- Range justification, parameter by parameter:
  - migTrigger range 30 min – 48 h: **not justified** — no citation, no rationale given for either endpoint or for the 6-minute step.
  - migTrigger range in CS#3 truncated to 0.5–5.1 h: **justified by the CS#1 result**, and the justification is stated: "We limit the X-axis range up to the _availability-aware migration trigger_ (i.e., 5.1 hours). We adopt this approach because **longer VM migration trigger intervals provide worse results for both availability and security**" (line 316) — i.e. the truncated region is dominated, so it is dropped.
  - Variant count 1–4: justified by the four major server hypervisors (line 102).
  - Table II fixed values: blanket-cited to [7] [24] [28] with the estimation admitted (line 193); per-row provenance not stated.
  - The *secondary-metric thresholds* are explicitly arbitrary and the paper says so each time: "We computed _ETTL_ metrics with **_PAS_ arbitrary values**" (line 285) for the 1%/20%/70%/100% rows of Table V; "For this **hypothetical example**, we assume _PAS_ = 10% for the _ETTL_ computation" (line 308) in CS#3; and for the MCDM inputs, "**For illustration**, we conduct MCDM considering three criteria" and "**For this illustrative example**, we consider that 2_N_ costs 100, 3_N_ costs 200, and 4_N_ has cost 300" (line 323). The t values of Table IV (1, 6, 24, 72, 144 h) carry no justification at all.
  - The MCDM weight rows of Table VI (33/33/33, 50/25/25, 25/50/25, 25/25/50, 15/85/0) are not justified either; they read as a corners-plus-centroid probe of the weight simplex, and the paper's own summary of them is that they are "illustrative and highlight how the VM migration schedule should be adapted accordingly to the system requirements" (line 325).
- Reporting: figure first (Fig. 3, two panels, raw metric and baseline-relative derived metric side by side over the same swept x), then a single-row table pinning the selected operating point against the baseline (Table III). In CS#2 the pattern inverts — the figure (Fig. 4) is the continuum and the tables (IV, V) sample it at chosen points on each axis in turn. In CS#3 the sweep and the derived security metric share one dual-axis figure (Fig. 5) and the weight probe gets its own table (VI).
- Where it sits: entirely inside the case-studies section (V); it *is* CS#1, and it is re-used as the x-axis of CS#3. No appendix, no separate sensitivity section.
- Claim supported: (i) the existence and location of an availability optimum in the trigger interval (5.1 h, line 237) and its size against the no-migration baseline (Table III); (ii) the monotone opposition of the two objectives over the same swept parameter — availability best at long intervals, security best at short (line 321); (iii) via the truncation argument, that the interesting region is bounded above by the availability optimum (line 316).
- Distinctive convention: the sweep is used as a **selector**, not just a descriptor — CS#1's sweep produces a single scalar (5.1 h) that is then carried as a *fixed, named, quoted-in-every-caption* parameter through the rest of the paper ("WHILE USING _migTrigger_ = 5.1 HRS" appears in both Table IV and Table V titles, lines 273 and 291), and the same parameter is then re-swept over a truncated range in CS#3 to expose the trade-off the selection hid.

## F. Discussion / limitations

No discussion section and no limitations section. Interpretation is folded into each case study's prose immediately after its figure/table; the related-work section (VI) carries the validation argument that would elsewhere be a threats-to-validity paragraph.

Limitation-flavoured statements, all of them elsewhere:

- Scope exclusion, in the model section: "we emphasize that _non-persistent_ attacks are out of the scope of this paper" (line 179), with the fix costed in the same paragraph ("by adding cleaning transitions (like transitions clear and clear2)").
- Parameter-quality admission, in the case-studies preamble: "it is necessary to estimate some of these values since they are unavailable or are hard to obtain through experimentation. **For the sake of simplicity**, we assume the same _reconnaissance_ and _attack_ phase delays for all the available _hypervisor_ variants. Moreover, **in the lack of _hypervisor_-specific aging parameters**, we also use the consolidated values from the works mentioned above in all the _hypervisor_ variants" (line 193).
- Validation admission, in related work: "the model presented in the current paper leverages a **partial validation** from these works" (line 343).
- Model-scope admission, in the related-work comparison table: this work is entered as "Yes, **including only steady-state availability**" in the availability-evaluation column (line 391).
- Space-driven omission: "The same applies to the MTD models for the environments with three and four _hypervisor_ variants, which are **omitted from this paper due to space limitations**" (line 185) — i.e. the 3N/4N models that produce Fig. 4 and Table VI are not shown.
- Sweep-coverage admission, as future work: "Besides that, we aim to conduct a **comprehensive sensitivity analysis of the other parameters of the models**" (line 399) — an explicit acknowledgement that only migTrigger was swept.
- Generalisability claims (arguing *for* transfer rather than conceding against it): "It is possible to adapt the availability and security modeling of VM migration to alternative approaches (i.e., alternative migration methods) … we can represent other migration techniques through parameter adjustment" (lines 139–155); and the modularity claim in the highlights, "The users with SPN expertise can reproduce the sub-nets to represent only the desired behavior in their models (e.g., using CLOCK MODEL to represent time counting for a task)" (line 61).

## G. Transferable vs purpose-specific

Transferable to an honours dissertation evaluating existing MTD mechanisms against a new attacker model on a simulator:

- **RQ→case-study 1:1 mapping, with each RQ restated verbatim as the first sentence of its case study** (lines 199, 252, 308). The evaluation's structure is legible from the introduction alone.
- **Sweep declared in one sentence with all three of range, both endpoints, and step** (line 230: "from 30 minutes to 48 hours using a 6-minute (0.1 hours) step"), and the swept parameter entered in the parameter table as "Depends on the scenario" (line 211) so the table stays complete.
- **Chaining a sweep into a selection**: a swept parameter yields a named scalar ("_availability-aware VM migration trigger_ … is of 5.1 hours", line 237) which is then carried, and *named in every downstream table title*, as the fixed operating point (lines 273, 291).
- **Truncating a later sweep's range with a stated dominance argument** rather than silently (line 316).
- **Baseline appearing in three forms, each declared**: as its own plotted series (line 230), as the degenerate factor level 1N (line 252), and subtracted into a difference metric (line 308).
- **Naming and marking the arbitrary numbers as arbitrary**: "arbitrary values" (line 285), "hypothetical example" (line 308), "For illustration" / "For this illustrative example" (line 323) — the paper never dresses a chosen threshold as a derived one.
- **The axis-swap table** (Table V): reporting the same model both as "what is PAS at time t" and "when does PAS reach level x", with the reason for the swap given in prose (line 285). Directly transferable to a time-to-compromise metric.
- **Stating null results in the same register as positive ones** (lines 283, 287: "provides no reduction", "it makes no difference").
- **Explicitly excluding an attacker variant, and costing the change that would include it** (line 179) — an attacker-model concession that is a scope statement rather than an apology.
- **Declaring the horizon per case study and disclosing why the steady state is uninformative** (line 258).
- Admitting in future work that only one parameter was swept (line 399), rather than implying coverage.

Purpose-specific / venue artefacts:

- No replications, seeds, CIs, or error bars — a consequence of numerical SPN solution in TimeNet. A simulator evaluation cannot inherit this and must add what this paper has no need for.
- The availability half of the study (software aging, rejuvenation, downtime in h/yr) and the dual-purpose framing are the paper's novelty claim; the security half alone would not have carried the ISSRE venue.
- The TOPSIS/MCDM weight table (Table VI) is a decision-analysis flourish the paper itself calls illustrative (line 325); it presupposes a cost model (2N=100, 3N=200, 4N=300, line 323) invented for the example.
- Blanket citation of a whole parameter table to three prior papers (line 193) without per-row provenance is a gap, not a convention to copy — particularly given the paper's own model inherits its validation from those same papers (line 343).
- Single-host, topology-free scope with no network structure; the "variant count" factor substitutes for what would be network size or diversity in a network model.
- Fig. 5's caption says "CS#4 Results" for the CS#3 section (line 319) — an uncorrected error, not a convention.
