# brown2023 — evaluation-section anatomy

Source read: docs/sources/lit_review/original/1.2_brown2023evaluating.pdf (8 pages, IEEE two-column; read in full via pdfplumber text + page-6 render for the figures). Cross-checked figure captions/keys against docs/sources/lit_review/brown2023.md (md line numbers given as "md L…" where used). Locators are PDF page numbers ("p.N") unless marked md.

Paper's own research question / purpose (one sentence): to propose MTDSim, "a simulation-based tool to evaluate the effectiveness of combinations of MTD techniques against practical and realistic attack scenarios" (p.1, abstract/intro), the two scenarios being "(i) a take-over style attack, and (ii) a targeted attack scenario like APT" (p.1) — i.e. the object evaluated is the DEFENCE combinations; the scenarios are the instrument.

## A. Skeleton of the evaluation portion

Section numbering is Roman (I–VI). Setup is NOT a separate section: the network/defence/attacker model and the parameter table sit in Section III, and the run configuration is a single paragraph opening Section IV.

- III. MTD EVALUATION FRAMEWORK (p.2) — model description [setup: system/defence/attacker model]
  - A. modeling the Network (p.2; sic, lowercase "modeling")
  - B. Modeling Defense (p.3)
  - C. Modeling the Attacker (p.4) — 1) Attack Scenarios; 2) Attack Procedure
  - D. Defense and Adversary interaction (p.4) — 1) Connection to Host is Lost; 2) Connection to Service is Lost; 3) User Access Has Changed (p.5)
  - TABLE I: MTDSim parameter values (p.5) — physically placed at the top of p.5, inside III.D
- IV. SIMULATION RESULTS (p.5) — one untitled opening paragraph = run configuration [setup], then:
  - A. Attack Actions Blocked (p.5) [results]
  - B. Average Attempts Required to Compromise (p.5–6) [results], ending in an untitled "In summary" paragraph (p.6)
- V. DISCUSSION (p.7) [discussion + limitations, one section]
  - A. Attacker capabilities and realism (p.7)
  - B. Regaining access to previously compromised hosts (p.7)
  - C. Attacker limitations (p.7)
  - D. Need for multiple MTD techniques (p.7)
- VI. CONCLUSION (p.7–8)

Setup and results: two sections (III model + IV results), but the actual run declaration is folded into IV's first paragraph. Discussion is a separate section from results.

## B. Setup — what is declared before any result

- Network configuration(s): ONE configuration. Table I (p.5): Total No. of Hosts 200; No. of exposed hosts 20; No. of layers 5; No. of subnets 20; No. of services per host [3,11]. Topology generated by Barabási–Albert for subnets per depth level and Watts–Strogatz for service connectivity (p.2). "the network generation uses the same initial configuration, meaning that at the beginning of the simulation, the 3-layer HARM is identical for both the attack scenarios we are evaluating" (p.5). How chosen: "The variable values in the graph generations above are reasonably selected to reflect the real-world systems closely and to demonstrate the use of MTDSim when such values are varied. In practice, the user would replace the variables with actual host and system values" (p.3). No alternative network sizes are run.
- Attacker model / scenarios: TWO, named and defined once in III.C.1 with bold bullet headers: "General Attack Scenario (Scenario 1)" — take-over style, "the attacker is looking to obtain the most amount of control by attempting to compromise the whole network. The attacker prioritizes the weakest host" (p.4); "Target Attack Scenario (Scenario 2)" — "like APT-style attacks, the attacker is looking to compromise a specific 'target' host (e.g., a credential database)" (p.4). Both scenarios have "the same capabilities but ... different goals in identical networks" (p.4). Scenario 2 is further split in the figures by target depth: "TX refers to the target host residing in the Xth layer in the network" (p.6 captions); T3 and T4 appear in Fig. 4a/5a, T3 only in the double/triple panels (p.6 render). The attack procedure is a flowchart (Fig. 3, p.5) "inspired by the Cyber Kill Chain [17] and MITRE ATT&CK Framework [18]" (p.2, p.4). Give-up rule: "No. of atack attempts before giving up 10" (Table I, p.5); "when the attacker is conducting a targeted attack (i.e., scenario 2), the attacker is set to never give up on the target node" (p.7).
- Defence conditions: six mechanisms, numbered 1)–6) in III.B (p.3–4): IP Shuffle, Port Shuffle, User Access Shuffle, Host Topology Shuffle, Service Diversity, Operating System Diversity. Conditions = all single MTDs, all pairs ("Double MTD") and all triples ("Triple MTD") (Fig. 4/5 panels a–c, p.6). Scheduling: one scheduler only — "the MTD operation events are chosen using a uniform distribution ... Defense trigger time Uniform(1000,5000) ms, where E(T) = 3000" (p.5, Table I). No-defence baseline: YES — appears as "None" on the x-axis of every panel (p.6 render) and is named in prose as "the No MTD control group" (p.6).
- Parameter table: YES — TABLE I "MTDSim parameter values" (p.5), two columns (Parameters | Value), 10 rows: Total No. of Hosts 200; No. of exposed hosts 20; No. of layers 5; No. of subnets 20; No. of services per host [3,11]; Vulnerability cross-platform 0.5; Vulnerability attack complexity [0.4,1]; Vulnerability impact [0,1]; No. of atack attempts before giving up 10; Defense trigger time Uniform(1000,5000) ms. Distributions declared: yes for trigger time (Uniform) and as ranges for the vulnerability parameters; the prose adds "randomly generated between [0.4, 1]" and "[0, 1]" (p.3), a 50% cross-platform chance, version numbers 1–99 with a vulnerability "patched in 10 versions on average" (p.2–3), 5 users per host with "5% chance for password reuse" (p.4). Two footnotes justify arbitrary values (p.2, fn 1–2).
- Replications: NOT STATED. The only hint is the word "trials" — "keeping the frequency of the MTD operation similar between trials" (p.5). No run count, no seeds, no horizon/simulation length, no termination rule beyond the scenario goals (compromise whole network / reach target) and the 10-attempt give-up. Whether the same generated network is reused across trials is not stated beyond "identical for both the attack scenarios" (p.5).
- Statistics: means only, implicitly. Metric 2 is "the average attempts required to compromise" (p.5); no std, CI, min–max or significance test; figure bars carry no error bars (p.6 render). Metric 1 is "total actions blocked" (p.5) — a total, not stated as averaged over runs.
- Metrics justified: "We look at these two metrics as the simplest form of metrics when considering multiple attack scenarios, as other metrics such as cost, RoA, probability of attack success, etc. depend on other external factors" (p.5).
- Anything else: no hardware, no language/version, no code link, no run-time figures.

## C. Results — how the numbers are shown

- Order: metric-major. IV.A "Attack Actions Blocked" first (Fig. 4), then IV.B "Average Attempts Required to Compromise" (Fig. 5). Within each metric: scenario 1 first, then scenario 2; within scenario: single → double → triple MTD. The blocked-actions metric seems to come first because it is the "direct" count of MTD interference; the attempts metric is then used to correct it ("the key finding here is when we compare MTD results to the No MTD control group", p.6).
- Figures in the evaluation portion:
  - Fig. 3 (p.5): flowchart, "The attack procedure implemented in MTDSim" — setup, not results.
  - Fig. 4 (p.6): three stacked panels (a) Single MTD, (b) Double MTD, (c) Triple MTD; grouped (clustered) bar chart; x = MTD technique / combination code (letters I,H,O,S,U,P; e.g. "Host", "IP", "None", "OS", "Port", "Service", "User" in (a); "IH", "IO", … in (b); "IOS", … in (c)), including "None"; y = "No. of Actions Blocked"; series = Scenario 1, Scenario 2 T3, Scenario 2 T4 in (a); Scenario 1, Scenario 2 T3 in (b) and (c); no error bars; caption "Total actions blocked using different MTDs. Key - I: IP Shuffle, H: Host Topology Shuffle, O: OS Diversity, S: Service Diversity, U: User Shuffle, P: Port Shuffle. TX refers to the target host residing in the Xth layer in the network."
  - Fig. 5 (p.6): same layout (a)/(b)/(c) grouped bars; y = "No. of Attack Attempts per Compromise"; same series pattern; no error bars; caption "The average attempts required to compromise. Key - …" (same key).
  - Facets = MTD arity (single/double/triple), one column per metric.
- Tables: only TABLE I (p.5), parameters (10 × 2). No results table.
- Baseline appearance: "None" bar in every panel of Fig. 4 and Fig. 5 (p.6 render); in prose as "the No MTD control group" (p.6). In Fig. 4 the None bar is zero blocks by construction; in Fig. 5 it is the reference level against which "most MTD techniques provide minimal increases in attempts required" (p.6).
- Comparison prose: ORDERING dominates, no magnitudes anywhere. E.g. "the host shuffle performed the best, followed by port shuffling" (p.5); "host and port shuffling performed the best, closely followed by host and IP shuffling" (p.5); "host-port-IP shuffling performed the best in triple MTD" (p.5); "OS diversity performed the second best when combined with ... IP shuffling" (p.5). Recommendation form: "Hence, to mitigate attacks such as scenario 1, host-based and/or port-based shuffling is effective compared to other types" (p.5); "host-based shuffling is an effective MTD technique that showed better performance than others for our two attack scenarios. However, ... host-based shuffling is computationally expensive" (p.6). No percentages, no absolute numbers quoted in text.

## D. Narrative — the claims, in order

1. "In general, more attack actions are blocked against scenario 1 compared to scenario 2, because the total number of hosts compromised in scenario 2 is much smaller ... So this is an expected observation." (p.5) — cross-scenario claim, explained by the scenario goal.
2. Scenario 1 ordering: host shuffle best single, port second; host+port best double, host+IP close; host-port-IP best triple → "host-based and/or port-based shuffling is effective" (p.5).
3. Scenario 2: "similar but with some notable differences" — host shuffle best in all arities; in double MTD "a diversity-based technique such as OS diversity performed the second best when combined with ... IP shuffling. Hence, there is a possibility when more MTD techniques are evaluated, we may find better-performing combinations of MTD that are not necessarily the best by themselves." (p.5)
4. Attempts metric: "a similar trend as the analysis of the blocked actions. But the key finding here is when we compare MTD results to the No MTD control group, where most MTD techniques provide minimal increases in attempts required in the general attack scenario apart from host shuffle." (p.6)
5. Mechanism explanation, shuffle vs diversity: "when the attacker is blocked, the attacker simply needs to reconnect and then exploit the same vulnerabilities. In contrast, when diversity techniques are used, the attacker is introduced to new vulnerabilities to exploit. So, this implies that diversity-based techniques can increase attack efforts more than shuffle-based techniques in general." (p.6)
6. Target depth: "having a deeper target node doesn't increase defense dramatically apart from Host Topology Shuffle and even works inversely for IP shuffle. This is because all these techniques work at a host level, meaning the number of hosts the attacker needs to compromise to reach the target node is the same." (p.6)
7. Summary: host-based shuffling best but "computationally expensive"; "there may be different combinations of MTD techniques that may perform better than only selecting the best individual MTD. Therefore it is essential that all considered MTD techniques should be evaluated before being deployed" (p.6).
8. Discussion V.D: "the best performing results between single, double and triple MTD techniques are similar, indicating that for systems only interested in the measured metrics we showed ... then it would be viable using only the best single MTD technique" (p.7).

Claims about the ATTACKER from the data: none as findings — every data claim is about the defence. Attacker properties enter only as explanations of defence results (claim 1: scenario goal explains the blocked count; claim 5: attacker "simply needs to reconnect" explains why blocks do not raise attempts; claim 6: hosts-to-target is invariant under host-level MTDs). The attacker's own properties (procedure, give-up, no skill levels) are asserted in III.C and V.A/V.C, not measured.

## E. Sensitivity / parameter analysis

Present only in a minimal, embedded form: the target-host depth (T3 vs T4) is varied for Scenario 2 in the single-MTD panels of Fig. 4a and Fig. 5a (p.6 render), and the text draws one claim from it ("having a deeper target node doesn't increase defense dramatically apart from Host Topology Shuffle and even works inversely for IP shuffle", p.6). Range justification: not stated. Only T3 appears in the double/triple panels; why T4 is dropped is not stated. No other parameter (network size, trigger time, give-up count, vulnerability ranges) is varied — Table I is a single column of values (p.5). No sensitivity section, no appendix. The paper instead defers variation to users: "the user would replace the variables with actual host and system values" (p.3) and to footnote 1: "this value can easily be updated with future studies or custom values" (p.2).

## F. Discussion / limitations

Separate section V. DISCUSSION (p.7), four titled subsections; contents = interpretation + concessions, with "future work" attached to each concession. No "threats to validity" heading. No comparability caveat against other simulators/papers (no cross-paper comparison is attempted anywhere).

Verbatim sentences worth quoting:
- Framing of the section: "In this section, we discuss some of the key findings and limitations of MTDSim." (p.7)
- Attacker-realism concession (V.A): "All attacker agents in the simulation will always follow the attack procedure (as shown in Figure 3) to decide their next move. Although the attack procedure has been created by adopting Cyber Kill Chain and MITRE ATT&CK Framework, which are the current industry practice for threat modeling and analysis, the actual actions taken by the attacker may vary. However, the profiles captured in these frameworks are continuously expanding, so we suspect a large proportion of attacker actions are captured and reflected in MTDSim." (p.7)
- Confusion modelling (V.A): "Whilst the goal of MTD is to cause confusion for the attacker, it is also impractical to program the randomness of confusion accurately. MTDSim looks to counteract this by giving a time penalty whenever the attacker is blocked due to an MTD and forces them to re-scan the network to decide their next decision. However, there may be more suitable randomness modeling that the MTDSim could adopt to reflect more realistic attacker capabilities, which we will look into in our future work." (p.7)
- Simulator realism (V.A): "As with all simulators, the realism of the results is closely correlated with the number of details captured in the model. Our proposed simulator, MTDSim, uses many variables from the system and networks and simulates their behaviors, but it still cannot capture all aspects of real systems and networks. Instead, it does capture more aspects of the attackers (with their attack procedures not well captured in previous literature), so our results should reflect closer to the real-world observations than existing solutions. Further analysis in the realism of MTDSim will be explored in our future work." (p.7)
- Monotonicity assumption (V.B): "It is assumed that once a host is compromised, it will remain compromised for the rest of the simulation - i.e., a monotonic assumption often seen in the literature. But MTD is designed to break the monotonic assumption ... if the attacker regains a network path to a previously compromised host, it is assumed that the attacker will instantly recognize that it has been previously compromised and regains control of the host. This is a reasonable assumption given that if the host configurations are unchanged, then re-exploiting the host should be straightforward" (p.7)
- Attacker skill (V.C): "However, the capabilities of the attackers are profiled in MTDSim, so the exploitation skills are not configured to distinguish the different skills of adversaries. The incorporation of attacker skills and capabilities will be looked into in our future work." (p.7)
- Scope of metrics (V.D): "readers should note that system and network security has many other important aspects to consider, and we have not been able to show how combined MTD techniques perform in those respectful areas. Therefore, more in-depth analysis (e.g., cost-value) should be carried out to determine the most suitable MTD techniques for deployment. This framework we propose simply enables us to evaluate multiple MTD techniques using realistic attack scenarios, which should help users to make more informed decisions." (p.7)
- Conclusion's strongest claim (VI): "we found that combining Host and IP shuffling techniques with a diversity technique was most effective against the two practical and realistic attack scenarios. Hence, MTDSim can be used in practice to provide an accurate evaluation of MTD techniques and their combinations." (p.8) — note this differs in wording from the results section's "host-port-IP shuffling performed the best in triple MTD" (p.5).

## G. Transferable vs purpose-specific

Transfers to an honours dissertation evaluating existing MTD mechanisms against a new attacker model on a simulator:
- A single parameter table (Parameters | Value) with distributions written as Uniform(a,b) / [lo,hi] ranges, placed before results and referenced by name ("the starting configuration found in table I", p.5).
- Bold-defining each attack scenario once, with a short name in parentheses ("Scenario 1"/"Scenario 2") reused everywhere thereafter, and stating that scenarios share capabilities but differ in goal on an identical network (p.4).
- "None"/no-MTD as an explicit x-axis category in every panel and named in prose as the control group (p.6).
- A one-line justification for the choice of metrics (p.5) and for arbitrary constants via footnotes (p.2).
- Metric-major results order with a fixed inner order (scenario → arity), and a closing "In summary" paragraph before the discussion (p.6).
- Discussion subsections that each pair a concession with what would resolve it (V.A–V.C), the attacker-realism concession leading (p.7).
- The interpretive move of claim 5 (p.6): explaining a defence result by what the attacker has to do after a block — this is exactly the seam a new attacker model would be argued through.

Purpose-specific artefacts (workshop paper; framework proposal):
- No replication count, no error bars, no CI — acceptable in a 6+2 page framework-demonstration paper, not in a dissertation.
- Setup folded into the framework-description section (III) with the run configuration as one paragraph opening the results section (IV): a page-budget artefact.
- All comparisons stated as orderings ("performed the best, followed by") with no magnitudes — fits a "which combination" question, not an effect-size question.
- Panels by MTD arity (single/double/triple) are specific to the combinations research question.
- The sole sensitivity axis (target depth T3/T4) is an artefact of the "targeted scenario" contribution, and is silently dropped for higher arities.
- Discussion's "future work" attachment to every limitation is the venue's convention for a first framework paper.
