Structural facts worth naming:
- **Setup and results are two chapters**, and the setup half is unusually large: §3.3 + §3.4 run six printed pages (printed 18–24) and carry eight of the thesis's nine tables.
- **Discussion is not a chapter.** It is a nested `x.y.3 Discussion` subsection inside §4.1 and §4.2, and it is absent from §4.3 and §4.4 — those two fold interpretation into the same subsection's prose. Nothing is titled "Limitations"; the limitation content lives under §5's five titled subsections, each phrased as a deficiency and then a call for future work.
- **The results chapter runs one template twice.** For each of the two sweep factors: (i) a full-page small-multiple *detail* figure at the head of the subsection with no text at all beside it, (ii) an *aggregate* figure marginalising over MTD type, in the `.1` subsection, (iii) an *inverted* figure in the `.2` subsection with the sweep factor moved from facet to bar-series, and (iv) a `.3 Discussion` supplying the mechanism. §4.3 and §4.4 are single-figure codas.
- **Every literature-review subsection also ends in a `Discussion` subsection** (§2.1.4, §2.2.1, §2.3.1, p.10, p.13, p.13) — the "state the material, then a titled Discussion" rhythm is a house pattern applied at both ends of the thesis.

## B. Setup — what is declared before any result

- **Network configuration(s).** Declared in Table 2 "Simulator Settings" (p.19): Start Time 0; Finish Time 15000; Total Nodes 150; Static Degrade Factor 2000(ms). Structural model: "The simulator uses a 3-layer HARM model which consists of the Host Attack Graph(AG), the Services on the Host Attack Graph(AG), and the Service Attack Tree(AT)" (p.15). **Three network configurations are run** (100, 150, 200 — Table 7, p.23), and the thesis is explicit that "network size" is not the node count: "The number of nodes in the network stays constant to reflect different density of the network when the network size parameters changes" (p.19), restated in the discussion as "In larger networks, the lower connection density per node (since the number of nodes in the setting did not change) results in fewer connections per node" (p.32). **What the "Network Size" parameter actually is, in simulator terms, is not stated** — only its effect on density. Not stated anywhere: topology generator, number of layers/subnets, services per host, vulnerability distributions, exposed-host count, user/credential model.
- **Attacker model / scenarios.** **ONE adversary, one sentence, no scenarios:** "Adversary was built using the Cyber Kill Chain [20] and MITRE ATT&CK [21] framework to try to compromise as many hosts as possible" (p.15). The attacker's action vocabulary is declared only as three rows of the symbols table (Table 3, p.19): SCAN_PORT "Scans a target system to identify open ports and services running on those ports"; EXPLOIT_VULN "Attempts to exploit a known vulnerability in a service or application to gain unauthorized access or control"; BRUTE_FORCE "Uses automated methods to guess passwords or encryption keys through repeated attempts". No goal variants, no skill levels, no give-up rule, no target selection rule, no bold-defined named scenarios. The single-attacker limitation is owned in §5.1: "In the current simulator system there is only one type of adversary" (p.35). The literature review had already made attacker under-specification its own critique: "the capability and intelligence of the attackers are underdeveloped [16, 9]. For example, the attacker only focuses on one target node even if it is too difficult to compromise [9]" (p.11) and "the complexity of the adversary is often lacking and not adaptive enough" (p.13) — so the gap the thesis names in others is the gap §5.1 concedes in itself.
- **Defence conditions.**
  - Techniques: four, bullet-defined once in §3.3.3 (p.22) — "**Complete Topology Shuffle**: Completely regenerates the network while preserving the hosts from the previous network"; "**IP Shuffle**: Assigns existing hosts a new random IP address"; "**OS Diversity**: Switches between different Operating System types and versions across the network"; "**Service Diversity**: Updates the services running on the nodes of hosts within a network" — plus "one overarching MTD technique that can deploy any of the four strategies" (p.22), i.e. **five defence conditions**: 4 single techniques + AnyMTD.
  - Scheduling: the controller is the scheduler, bounded below by a forced-trigger guard. §3.1.2, verbatim: "The default value for static degrade factor is set to be 2000ms. The 2000ms threshold is not as aggressive as 1000ms and it can allow more meaningful and proper deployment of MTD to avoid disrupting the previous deployment. When period between the last MTD trigger and the current time exceed the static degrade factor, the system will be forced the trigger a random MTD based on the selected MTD deployment type and reset the interval counter. This check will happen before the network metrics being feed into the MTD AI model." (p.15) — with the assumption stated: "The assumption is that when the network stay static for too long it will become more vulnerable to attackers."
  - MTD interval: swept at 50, 100, 200 (Table 6, p.23).
- **"No defence" baseline: YES, and it is run.** "Trials with no MTD deployment will be run so that these metrics can be obtained for the baseline scheme. The metrics results collected by the trained models will be scaled accordingly." (p.24). Like Tay, the baseline is a denominator rather than a plotted bar — but unlike Tay, this thesis **also plots three real comparators**.
- **Comparator schemes: THREE, and they appear as bars.** "Since there are no existing similar AI models to compare to, the MTD AI scheme will be compare to three previous schemes - alternative, random and simultaneous. The evaluation score for other schemes will be calculated similar to the trained MTD AI models for consistency." (p.25). Their run conditions are pinned in Table 8 "Comparison with Previous Schemes" (p.24): all four columns (Random, Alternative, Simultaneous, MTD AI) at MTD Interval 200, Network Size 150, Number of Nodes 150.
- **Parameter tables: NINE tables, eight of them setup.** This is the thesis's most conspicuous convention — every condition set gets its own small table rather than a paragraph.
  - **Table 1 "Learning Parameters"** (p.19), 6 rows × 2 cols: Discount Rate (γ) 0.95; Exploration Rate (ε) 1.0; Minimum Exploration Rate (ε_min) 0.01; Exploration Decay Rate (ε_decay) 0.995; Training Start 1000; Episodes 100.
  - **Table 2 "Simulator Settings"** (p.19), 4 rows × 2 cols (above).
  - **Table 3 "Metrics and Symbols"** (p.19), ~24 rows × 2 cols (Symbol | Description) — the full notation table, covering hosts, attack paths, risk, CSP, AI, RoA, SAP, SAPV, NAV, AC, N_MTD, Time_now, Time_LME, and the three attack actions.
  - **Table 4 "Combinations of Models"** (p.23), 10 rows × 5 cols: rows = metric optimisation (All Features, Hybrid, Host Compromise Ratio, Attack Path Exposure, Attack Success Rate, Return on Attack, Risk, MTD Frequency, Mean Time to Compromise, Time Since Last MTD); columns = MTD technique (Any MTD, Complete Topology Shuffle, IP Shuffle, OS Diversity, Service Diversity). **The cells of this table are blank** — it is a cross-product grid whose cardinality is given in the prose instead: "In total 50 models will be trained for each intersection between MTD techniques and metrics optimization" (p.24).
  - **Table 5 "Comparison of Metrics in Hybrid and All Features Optimization"** (p.23), 11 rows × 3 cols (Metric | Hybrid | All Features), Yes/No cells: Hybrid = HCR, APE, ASR, RoA, Risk, MTD Frequency, MTTC, Attack Stage (8 Yes); All Features = those eight plus Time Since Last MTD, Shortest Path Variability, Host IP Variability (11 Yes).
  - **Table 6 "Parameters for testing on different MTD Intervals"** (p.23), 3 rows × 3 cols: (50, 150, 150), (100, 150, 150), (200, 150, 150) under MTD Interval | Network Size | Number of Nodes.
  - **Table 7 "Parameters for testing on different Network Sizes"** (p.23), 3 rows × 3 cols: (50, 100, 150), (50, 150, 150), (50, 200, 150) — note the MTD interval is pinned at 50 throughout, and the choice is justified: "The reason why different network sizes are tested in low MTD interval is because previous work indicates MTD deployments works better in lower interval [16]" (p.24).
  - **Table 8 "Comparison with Previous Schemes"** (p.24), 3 rows × 5 cols (above).
  - Table 9 "Markov Decision Process components" (p.40), appendix notation.
- **Features vs evaluation metrics — declared as two different sets.** Eleven candidate features are each given a numbered definition and a formula in §3.3.2 (p.20–22): APE (Eq. 5–6), Risk (Eq. 7), RoA (Eq. 8–9), HCR (Eq. 10), Attack Stage, ASR (Eq. 11), MTD Execution Frequency, Overall MTTC, Time Since Last MTD, SAPV (Eq. 12–14), NAV (Eq. 15). The **evaluation** set is only four: "A final evaluation score will be calculated using four evaluation metrics. Each evaluation metrics will be of equal weighting when contributing to the sum. The four evaluation metrics are Attack Success Rate (ASR), Return on Attack (ROA), Attack Path Exposure (APE), Risk (R)." (p.24). The four evaluation metrics are also four of the eleven features (Table 5, p.23); the thesis does not comment on that overlap.
- **Scoring and direction, stated explicitly.** "These valuation metrics should be minimised since they represents disadvantages or vulnerabilities of the network. The purpose of these scaling is so that the final evaluation score(sum) will be consistent. A larger score will indicate a better performance and vice versa." (p.24), with the two scaling formulae given: Maximize = V/N; Minimize = 1/(V/N) = N/V, "where V is the raw metric value obtained by the trained models and N is the baseline (no MTD) value" (p.25). So the composite is an equal-weight sum of four baseline-relative ratios, direction-corrected — and every part of that is written down.
- **Reward, stated separately from the evaluation score.** "R(s_t, a_t, s_{t+1}) = f(N_{t+1}) − f(N_t)"; multi-metric optimisation "will be using a weighted sum as the reward", R_t = Σ w_i·f_i(x_t) (Eq. 3), with a sign rule (Eq. 4): "w_i > 0 if f_i reflects dynamic behavior of the network; w_i < 0 if f_i reflects vulnerabilities of the network" (p.18). Feature normalisation: "each feature will be normalized using min-max normalization against previous data in the memory in each reward calculation. The reason why min-max normalization is used instead of other normalization is that it is assumed that the more samples it gets eventually most data will be in the middle and the normalization can be consistent since it does not affect the upper or lower boundary." (p.18). The magnitudes of the w_i are not given.
- **Replications — a stated protocol, but no count.** §3.4.1 in full, verbatim: "In order to ensure consistency, five checkpoints are used to collect the evaluation metrics for each trial. The mean of the checkpoints will be taken as the representative of that trial and the overall results for each models will be taken by the median of the trials." (p.24). So the aggregation rule is **mean over five checkpoints within a trial, then median over trials** — but **the number of trials is not stated**, and neither are seeds, a seeding convention, or whether the same generated network is reused across conditions.
- **Horizon and training length:** simulator horizon "Start Time 0 / Finish Time 15000" (Table 2, p.19), glossed as "Simulator settings run trials from 0 to 15000 to gather adequate data" (p.19); training length Episodes 100 (Table 1, p.19), with training beginning "after collecting 1000 samples over 100 episodes" (p.19). No termination rule beyond the finish time.
- **Statistics:** central tendency only (mean of checkpoints, median of trials). No standard deviation, no confidence interval, no min–max, no significance test, no error bars on any figure (p.26–34, p.41–44 renders).
- **Architecture (for completeness):** static feature module = two dense layers, 128 and 64 units, ReLU each, two batch-norm layers; time-series module = two LSTM layers, 64 and 32 units, with "activation, normalization and dropout layers" and 30% dropout; both feed a feature fusion module then "the Q-Network output layer" (p.17–18). Action space defined as MTD singletons plus pairs plus Null (§3.2.3, p.18), though the experiments use only the four singletons plus AnyMTD.
- **Anything else:** no hardware, no OS, no language/framework/version, no wall-clock training time, no code repository for the authors' own work (only the substrate citations [16], [17]). AI-tool declaration (p.2): "I have used AI tools in the preparation of this report: Yes … Double check English."

## C. Results — how the numbers are shown

- **Order:** factor-major, from the factor the controller most directly touches to the one it does not, ending in the external comparison. §4.1 MTD interval → §4.2 network size → §4.3 MTD type → §4.4 comparison with previous schemes. Interval comes first because it is the substrate's own scheduling parameter and the one prior work already made claims about ([16] is cited for it, p.24); MTD type comes third but turns out to dominate ("the choice of MTD technique place appears to be the most defining factor that determine the performance of models", p.33); the comparison is placed last so it can use §4.1's winner ("According to Figure 7, the hybrid combination on average performed the best in MTD interval = 200. Therefore, it was compared to the random, alternative, and simultaneous schemes from previous work", p.34).
- **Every figure in the evaluation portion.** All results figures are matplotlib bar charts sharing one 10-colour metric palette; **within every panel the bars are sorted ascending by value, so the x-order changes panel to panel**; no error bars anywhere.
  - **Figure 1** (p.14): block diagram, "System Overview" — AI engine + MTD simulator. Setup.
  - **Figure 2** (p.15): flowchart, "MTD Trigger Procedure" — the static-degrade-factor check ahead of the model. Setup.
  - **Figure 3** (p.16): diagram, "MTD AI Model Architecture". Setup.
  - **Figure 4** (p.17): diagram, "Feature Fusion Module". Setup.
  - **Figure 5** (p.26), full page, no accompanying text: "Performance between different metrics optimization across different MTD intervals and MTD types (Normalized)". **5 × 3 grid of small multiples.** Rows = MTD technique (panel titles CompleteTopologyShuffle, IPShuffle, OSDiversity, ServiceDiversity, AnyMTD); columns = MTD interval, each panel carrying an inset box "MTD Interval = 50, Network Size = 150" (and =100, =200). Per panel: x = the ten metric optimisations (tick labels `all_features`, `hybrid`, `host_compromise_ratio`, `attack_path_exposure`, `overall_asr_avg`, `roa`, `risk`, `mtd_freq`, `overall_mttc_avg`, `time_since_last_mtd`), sorted ascending; y = "Percentage Improvement (%)"; colour = metric optimisation, keyed by a shared 10-entry legend across the top of the grid. Grid-level axis labels: "MTD Type" (left) and "MTD Interval" (bottom). The worst optimisation in each panel sits at 0% by construction (see the normalisation statement below).

  - **Figure 11** (p.33): "Performance of different MTD techniques across different metrics optimization in MTD interval = 200 and Network size = 150 (normalized scores)". **Ten panels** (4 + 4 + 2), one per metric optimisation (panel titles `all_features`, `hybrid`, `host_compromise_ratio`, `attack_path_exposure`, `overall_asr_avg`, `roa`, `risk`, `mtd_freq`, `overall_mttc_avg`, `time_since_last_mtd`). This figure transposes Figures 5/8: MTD technique becomes the x-category and metric optimisation becomes the facet.

  - **Appendix Figure 13** (p.41): "The performance of different metrics optimization across different MTD Intervals and MTD Types (actual scores)". The same 5 × 3 grid as Figure 5, but each bar is a **stacked** four-segment bar (ROA / risk / ASR / attack_path_exposure) at **actual scores**, y = "Evaluation Score", values printed in-segment.

  - **Appendix Figure 16** (p.44): the same for network sizes.
- **Tables in the results portion:** none. All nine tables are setup or appendix notation.
- **How the baseline / comparators appear.** Two distinct references are used, and the thesis says which is which in the figure captions ("Normalized" vs "actual scores"):
  1. *Worst-model-in-panel*, for the main-text normalised figures: "Each score is normalized against the worst performing score in each graph." (p.27). This is why the lowest bar in every panel of Figures 5, 6, 8, 9 and 11 is at zero, and why the no-MTD run never appears as a bar there.
  2. *No-MTD run*, for the scaling that produces the evaluation score at all (p.24–25) and for the appendix improvement figures (p.43–44), which run to hundreds of percent.
  3. The three prior schemes (random, alternative, simultaneous) appear **as three of the thirteen bars in Figure 12** (p.34), on the same axis and computed the same way ("The evaluation score for other schemes will be calculated similar to the trained MTD AI models for consistency", p.25).
- **How comparisons are stated in prose.** Mixed, and unusually *range*-oriented: the thesis routinely reports the **spread between the best and worst condition** rather than a winner-versus-loser pair, and reports it as a way of saying the factor does not matter much.
  - Spread form: "The range between the best and worst metrics optimization average performance are 11.1%, 16.2%, and 10% respectively for MTD interval = 50, 100, and 200." (p.27); "It showed a maximum of 12.6% , 11.1% and difference in range on average for network size = 100, 150 and 200 respectively." (p.31, reproduced verbatim — the third figure is missing).
  - Ranking form: "ASR managed to do well across all tested network sizes compare to other metrics, consistently ranking second or third." (p.31); "ranking the top 3 metrics optimization in both shuffling technique" (p.31).
  - Magnitude form, reserved for the two claims the thesis actually wants: "The worst performing MTD technique is IP shuffling and the best is OS diversity, which can outperform IP shuffling by about 140% (i.e. hybrid)." (p.33); "most of our new models significantly outperformed the simultaneous scheme by at least 30% overall, and none of the proposed models under performed compared to the random and alternative schemes." (p.34).
  - Directional form: "When models are able to deploy any types of MTD, there was a clear invert correlation between the size of the MTD interval and the performance of the models (i.e. the smaller interval the better)." (p.28).
  - Null-result form, stated plainly: "different network sizes did not appear to have any significant overall impacts on models across different metrics optimization or MTD techniques." (p.32).
  - Attribution form — the thesis explicitly ranks its own factors: "When compare to the effect of MTD interval or network size, the choice of MTD technique place appears to be the most defining factor that determine the performance of models." (p.33); "the general performance of these models seems to be more influenced by the architecture of the reinforcement learning algorithm and MTD type rather than the specific metrics used for optimization." (p.34).
  - Recommendation form: essentially absent. The closest is the conclusion's "incorporating multiple metrics into reward optimization generally leads to favorable outcomes. However, the inclusion of metrics that do not directly represent the network's security posture can negatively impact overall performance." (p.35–36).

## D. Narrative — the claims, in order

1. Metric choice barely matters (§4.1.1, p.27): best-to-worst spread of 11.1% / 16.2% / 10% across the three intervals.
2. A few metrics are consistently good, two are consistently bad (§4.1.1, p.27): "The overall mean time to compromised optimization showed an advantage consistently over other metrics in the MTD interval = 50 across all MTD techniques in particular when coupling with OS diversity technique." … "However, TSLM and HCR performed the worst in comparison to other metrics".
3. Hybrid generally wins, all-features does not (§4.1.1, p.27): "besides the performance of MTD interval = 50, the hybrid combination of metrics generally outperformed other metric(s) optimization" … "the performance of the all features combination did not perform as well as expected in general since even as it incorporate more dynamic features compare to the hybrid counterpart."
4. Shorter intervals are better, and diversity is the technique that cares (§4.1.2, p.28): "All models under-performed in MTD interval = 200 especially with models that deployed diversity techniques … there was a clear invert correlation between the size of the MTD interval and the performance of the models."
5. Mechanisms for 2–4 (§4.1.3, p.28–29): shorter intervals let MTTC "reflect the individual attack exploit time … because it captures the specific disruptions caused by rapid MTD deployments"; ASR works at low interval because "the model can detect any ongoing attack and immediately cut off the attacks"; HCR/TSLM fail because "HCR is less sensitive to frequent changes in system configurations and TSLM may not reflect significant changes in security posture"; and all-features is diluted — "The all features combination under-performed probably because it is diluted by the poor performance of TSLM, although it did not explain why it performed so well when coupling with IP shuffle."
6. Network size barely matters (§4.2.1–4.2.2, p.31–32): spread of ≈12.6% / 11.1%; "different network sizes did not appear to have any significant overall impacts".
7. Mechanism for the size result via path structure (§4.2.3, p.32): APE does well in large networks because "the lower connection density per node … results in fewer connections per node. This sparser distribution decreases the probability that attackers can easily reach critical nodes … Attackers must traverse longer paths with more intermediate nodes to reach high-value targets."
8. MTD type dominates (§4.3, p.33): "Diversity techniques outperformed shuffling technique in every single metric optimization" … OS diversity beats IP shuffle "by about 140%" … "the most defining factor". Mechanism offered and flagged as speculative: "This is because shuffling technique is more resource intensive and requires more time to deploy and reconfigure. However, further research is needed to clarify this speculation."
9. The proposed models beat the prior schemes, with one exception owned (§4.4, p.34): "at least 30% overall" over simultaneous; "However, models that used IP shuffling exhibited lower performance compared to both the simultaneous scheme and other diversity techniques. Notably, the simultaneous scheme excelled in the ASR evaluation metric, outperforming all other models by a wide margin." — followed by the mechanism for the comparator's win ("the ability of simultaneous scheme to deploy multiple MTD strategies at the same time … However, this approach is resource-intensive").
10. Self-limiting attribution (§4.4, p.34): "the general performance of these models seems to be more influenced by the architecture of the reinforcement learning algorithm and MTD type rather than the specific metrics used for optimization" — i.e. the thesis reports that its own headline independent variable (metric choice) is the weakest of the factors it measured.

**Claims about the ATTACKER's properties from the data:** none measured. The attacker is never an outcome. Attacker behaviour appears only as *mechanism* in the Discussion subsections — always as an explanation for a defence number, in exactly one form: "what the attacker has to do under this configuration". Examples: "The high frequency of OS changes ensures that attackers face a moving target, significantly increasing the time needed to find vulnerabilities and execute successful attacks" (p.28); "the model can detect any ongoing attack and immediately cut off the attacks" (p.29); "Attackers must traverse longer paths with more intermediate nodes to reach high-value targets, increasing the difficulty of compromising the network and creating more opportunities for detection" (p.32); "these intervals result in frequent configuration changes that the ability of attackers to exploit vulnerabilities which leads to a consistently lower ASR" (p.33, reproduced verbatim). Two of the eleven declared feature metrics are attacker-facing (ASR, Attack Stage), and Attack Stage is the only attacker-state signal fed to the controller — its adequacy is conceded in §5.4 (p.35): "Although the proposed model have incorporated attack stage as a feature to make the model more aware of the attacks, it is far too simplistic".

## E. Sensitivity / parameter analysis

Sensitivity analysis **is the results chapter**: §4.1, §4.2 and §4.3 are three sweeps, and §4.4 is the comparison. There is no separate sensitivity section — the sweeps are the primary evidence.

- **Design: a partial factorial, declared table-by-table.** The full cross is 10 metric optimisations × 5 MTD techniques = 50 models (Table 4, p.23; "In total 50 models will be trained for each intersection between MTD techniques and metrics optimization", p.24). Those 50 are then run under two one-at-a-time condition sets — three MTD intervals with network size pinned at 150 (Table 6, p.23) and three network sizes with interval pinned at 50 (Table 7, p.23) — so the interval and size axes are never crossed with each other. Total main-text cells: 50 × (3 + 3) = 300, less the shared (interval 50, size 150) cell.
- **Ranges and their justification:** MTD interval 50/100/200 and network size 100/150/200 — the *values* are not justified, but the *pinning* is: "The reason why different network sizes are tested in low MTD interval is because previous work indicates MTD deployments works better in lower interval [16]." (p.24) — a design decision justified against the prior thesis in the same lineage. The static degrade factor is justified by comparison to an alternative that was not run: "The 2000ms threshold is not as aggressive as 1000ms and it can allow more meaningful and proper deployment of MTD to avoid disrupting the previous deployment." (p.15). The learning hyperparameters (Table 1) are declared as fixed and not swept — Tay's thesis sweeps exactly those, on the same model.
- **Reporting:** two full-page small-multiple figures (5, 8) plus an aggregate (6, 9) and an inverted view (7, 10) per factor, all in the results chapter; the actual-score and improvement-over-baseline versions of the same grids are relegated to the appendix (Figures 13–16, p.41–44).
- **What the sweeps are used to claim:** that metric selection matters little (§4.1.1, §4.2.1), that MTD type matters most (§4.3), and that the interval effect is inverse and technique-dependent (§4.1.2) — with the last of these used to pick the condition for the comparator study (§4.4).
- **Not swept:** attacker type or behaviour (one adversary only), node count (fixed at 150), simulator horizon, static degrade factor, reward weights w_i, and every learning hyperparameter in Table 1.

## F. Discussion / limitations

**Discussion is folded into the results chapter as nested subsections** — §4.1.3 "Discussion" (p.28–29) and §4.2.3 "Discussion" (p.32–33) — and §4.3 and §4.4 carry their interpretation inline with no separate heading. There is no chapter titled Discussion, no "threats to validity" heading, and no comparability caveat about measuring against other papers (the one cross-scheme comparison, §4.4, is run inside this thesis's own pipeline, which is precisely what the "for consistency" sentence on p.25 secures). **Limitations are a five-subsection block at the head of the final chapter**, §5.1–§5.5, before §5.6 Conclusion — each one titled as the deficiency itself, stated in two to four sentences, and closed with what would fix it.

Verbatim limitation subsections worth quoting in full:

- **§5.1 The need for more complex adversaries** (p.35) — placed first: "In the current simulator system there is only one type of adversary. Although certain previous gaps in researches have been addressed, this research did not incorporate for more advanced adversaries. This restrict our understanding of the limits of existing or future models and more complex adversaries need to be developed to test the performance of the models in different dynamics."
- **§5.2 Limited evaluation metrics** (p.35): "There have not been evaluation in terms of the performance of network in this report. The evaluation metrics should be more diverse and holistic to reflect how well the models perform in both security while maintaining the network efficiency. There is also a need for more diverse evaluation metrics to evaluate different aspects of security in the network to better evaluate the models."
- **§5.3 Limited types of MTD techniques** (p.35): "In this research, only four distinct types of MTD techniques were tested within the simulator. Utilizing more advanced or dynamic MTD techniques could enhance effectiveness in thwarting various types of attackers and defending against complex scenarios within the network."
- **§5.4 More reactive reinforcement model** (p.35): "Although the proposed model have incorporated attack stage as a feature to make the model more aware of the attacks, it is far too simplistic and there needs to be more complex reactive components being incorporate into future models."
- **§5.5 Lack of real life scenario testing** (p.35): "The current MTDSimTime simulator lacks the reliability needed to determine whether high-performing models can sustain their effectiveness in real-world scenarios. Testing in real-life conditions is essential, as failures in cybersecurity can lead to significant and detrimental consequences."

Concessions made inside the results chapter itself (not deferred to §5):
- An unexplained result left unexplained: "The all features combination under-performed probably because it is diluted by the poor performance of TSLM, although it did not explain why it performed so well when coupling with IP shuffle." (p.29)
- A mechanism flagged as unconfirmed: "This is because shuffling technique is more resource intensive and requires more time to deploy and reconfigure. However, further research is needed to clarify this speculation." (p.33)
- A comparator beating the contribution on one metric, kept and explained: "Notably, the simultaneous scheme excelled in the ASR evaluation metric, outperforming all other models by a wide margin." (p.34)
- The contribution's own variable ranked last among the measured factors: "the general performance of these models seems to be more influenced by the architecture of the reinforcement learning algorithm and MTD type rather than the specific metrics used for optimization." (p.34)

No limitation is stated about the number of trials, seeds, the absence of dispersion measures, or the un-crossed interval × network-size design.

Figure/text reference slips, recorded as facts (not judged): the §4.2.2 paragraph discussing Figure 10 opens "As shown in both Figure 11 , different network sizes did not appear to have any significant overall impacts…" (p.32); and the Table 6/7 condition sets are introduced as "These 50 models will in addition be tested across different MTD intervals and network sizes as shown in Table 8" (p.24), Table 8 being the comparator table.

## G. Transferable vs purpose-specific

**Transfers to an honours dissertation evaluating existing MTD mechanisms against a new attacker model on a simulator:**
- **A dedicated `Experiment Setup` section that is mostly tables** (§3.3, p.19–23): fixed parameters, simulator settings, the notation table, the model grid, and one small table per condition set (Tables 6, 7, 8). Every condition a reader might want to check is a row somewhere. This is the single most reusable convention in the pair of theses, and the direct opposite of Tay's zero-table prose.
- **A separate `Evaluation Method` section** (§3.4, p.24–25) declaring the measurement protocol *before* any number: how a trial is summarised (five checkpoints, mean), how trials are combined (median), what the composite score is (equal-weight sum of four metrics), which direction each metric runs, and the exact scaling formulae against the no-MTD baseline. Stating the direction convention and the maximise/minimise formulae explicitly (p.24–25) is what makes a composite score auditable.
- **Distinguishing the metrics used as model input from the metrics used to evaluate** (eleven features, four evaluation metrics — §3.3.2 vs §3.4.2), and tabulating exactly which features each composite condition contains (Table 5, p.23).
- **A `Discussion` subsection nested under each results subsection**, carrying mechanism and no new numbers, so the readout paragraphs stay numeric. Paired with the same habit in the literature review (§2.1.4, §2.2.1, §2.3.1), it gives the thesis one consistent "material, then interpretation" rhythm.
- **Plotting real comparators on the same axis as the contribution** (Figure 12, p.34), computed through the same pipeline and said to be so: "The evaluation score for other schemes will be calculated similar to the trained MTD AI models for consistency" (p.25). Sorting that figure ascending puts the prior schemes at the left as a visible floor.
- **Justifying a design decision against the prior work in the same lineage** rather than against the general literature: "The reason why different network sizes are tested in low MTD interval is because previous work indicates MTD deployments works better in lower interval [16]" (p.24).
- **Three-view figure discipline per factor**: a detail grid, an aggregate over the nuisance facet, and an inverted view with the factor as bar-series. The inverted view (Figures 7, 10) is what licenses the "overall impact" claim, and it is a different figure from the one that licenses the per-condition claims.
- **Splitting normalised and actual scores between main text and appendix** (Figures 5/8 vs 13/14; and worst-model-normalised vs baseline-improvement, Figures 5/8 vs 15/16), with the reference named in every caption ("Normalized" / "actual scores").
- **Owning the null result and the self-limiting attribution** — saying plainly that network size "did not appear to have any significant overall impacts" (p.32) and that performance is driven "more by the architecture … and MTD type rather than the specific metrics used for optimization" (p.34), which is the thesis's own independent variable.
- **Limitations as titled subsections named for the deficiency**, attacker realism first (§5.1, p.35), each two to four sentences.
- **Declaring the shared-authorship boundary in the Acknowledgements** (p.4) when a model is built jointly.

**Purpose-specific artefacts (RL-controller thesis; 7940-word GENG5512 report; one of a co-developed pair):**
- The **ten "metric optimisations" as the primary x-category** exist only because the research question is *what should the reward optimise*. A dissertation evaluating MTD mechanisms against an attacker model has no analogue; its x-category would be the mechanism or the attacker condition.
- **Reward design, min-max feature normalisation, episodes, exploration decay** (§3.2.4, Table 1) are learner apparatus, and here they are declared-and-fixed precisely because the sibling thesis sweeps them.
- **Normalising against the worst model in each panel** (p.27) suits a within-panel ranking question and makes the zero bar meaningless in absolute terms; it also means the main-text figures cannot be read against the no-MTD baseline at all — which is why Figures 15–16 exist in the appendix.
- **Bars sorted ascending within every panel**, so the x-order differs panel to panel: efficient for "which is best here", but it removes any dose–response reading and makes cross-panel comparison a matter of colour-tracking.
- The **5 × 3 small-multiple grid at one figure per page** (Figures 5, 8, 13–16) is legible only at full-page scale, and Figures 5 and 8 are printed with **no accompanying text on the page**.
- **The un-crossed design** (interval swept at fixed size, size swept at fixed interval) is a budget artefact of 50 models × 6 conditions in one semester, and it is what forces the "as shown in Figure 5 and 6" style of cross-referencing whenever a claim needs both factors.
- **Table 4's blank cells** — a cross-product grid that carries its cardinality in the prose rather than in the cells — works because the cross is complete; it would not survive a design with holes.
- **No trial count, no seeds, no dispersion, no error bars** in 44 pages, despite a stated mean-then-median aggregation protocol. Recorded here as the local genre's floor, not a target: the protocol is declared, the sample size behind it is not.
