\section{Moving target defence}
\label{sec:mtd-concept}

Moving target defence (MTD) is the timely manipulation of system
configurations to modify and control the \emph{attack surface}: the set
of points at which an attacker engages with the system \citep{cho2020}.
It inverts the conventional assumption that vulnerabilities can be
eliminated and system configurations held stable: no system is
perfectly secure, so attacks can be thwarted but not prevented
\citep{ghosh2009nitrd}. By continuously changing the configurations an
attacker relies on, MTD shifts uncertainty onto the attacker, whose
reconnaissance decays faster than it can be acted upon \citep{cho2020}.

The MTD design space is organised around three questions: \emph{what}
to move, \emph{how} to move it, and \emph{when} to move \citep{cho2020}.
The first concerns the configurable attributes available to the
defender: IP addresses, network topologies, operating systems, software
stacks.

The second is captured by the canonical
shuffle--diversity--redundancy (SDR) taxonomy \citep{hongkim2016},
whose three primitives are complementary rather than partitioned
\citep{cho2020}.
\emph{Shuffling} rearranges or randomises existing components (IP
mutation, topology reconfiguration), invalidating reconnaissance the
attacker has already performed. \emph{Diversity} deploys different
implementations of the same function, so that an exploit against one
variant is unlikely to apply to others. \emph{Redundancy} replicates
components to preserve service while the other two operate.

The third question, when to move, distinguishes proactive
(time-triggered), reactive (event-triggered), and hybrid scheduling
regimes \citep{cho2020}. When to move is the tension between cost and
security:
moving too often imposes overhead on legitimate users; moving too
rarely leaves the attacker's reconnaissance valid for longer than it
should be.

The network in MTDSim is a three-layer hierarchical attack representation
model (HARM) \citep{hongkim2012harm}: a graph of graphs. The host layer is
the topology, where the hosts are nodes and reachability between them is
the edges. The service layer is what is running on each host. The
vulnerability layer is the vulnerabilities each service carries, and the
attacker compromises from the bottom upwards.

On the host layer, hosts are placed in levels of depth. Each level is a set
of subnets constructed using the Barab\'asi--Albert model
\citep{barabasi1999} and joined to the level before it. The construction
mimics the scale-free characteristic of a real-world network
\citep{brown2023}. The first level is the exposed
endpoints, and reaching a deeper level requires compromising a host in the
level before it. On the service layer each host has one operating system
and a small number of versioned services, the services connected in a
service graph constructed using the Watts--Strogatz model
\citep{watts1998}. Each host also carries users and credentials, and an IP
address. The endpoints are never rewritten: they persist unchanged through
the life of the simulation while everything around them can move, because
they are the ingress into the network, so the MTD mechanisms protect the
interior, not the perimeter.

Each vulnerability is priced by a CVSS complexity, which sets how likely an
exploit is to succeed. A service is compromised when the impact of its
exploited vulnerabilities accumulates past its threshold, and the host
falls when a compromised service is adjacent to the host's internal target
node. The vulnerabilities are synthetic: they are generated, not drawn from
any real-world vulnerability database.

The attacker never sees the whole topology. It only sees a visible
subgraph, which comprises the endpoints plus all the compromised hosts and
all of their neighbours.

MTDSim implements shuffle
and diversity only; there is no redundancy. These two families are
split on attacker effect (Table~\ref{tab:defence-mechanisms}): shuffle
renames or relocates resources without changing what they can do, and
diversity changes the software stack so that found exploits no longer
apply. The optimised OS assignment variant \citep{zhang2023} has been
withdrawn from the mechanism pool: it added overhead without providing
the diversity-assignment value we needed. Across all seven mechanisms, the endpoints are not
manipulated, so their attack surface remains the same throughout the
attack campaign, although the topology around them can move
(Section~\ref{subsec:network-model}).

% That is the what and the how; when do we move? 
There are five
deployment strategies in MTDSim (Table~\ref{tab:deployment-strategies}).
Four are time-triggered, or proactive; one is hybrid: MTDShield, Tay's
reinforcement-learning selector \citep{tay2024}. \emph{No operation} is a
policy choice: MTDShield chooses one of four of the MTD mechanisms, or
nothing. That is the when not to move. The interval between deployments
is drawn exponentially \citep{zhang2023}. Two mechanisms rewriting the
same layer cannot operate concurrently \citep{zhang2023}. There are no
purely reactive deployment strategies in the simulator: no detection
channel is encoded, so a detection-triggered strategy, such as an
IDS-based scheme, is not possible.

Two literatures have developed alongside one another without

\subsection{Advanced persistent threat}
\label{subsec:apt}

An APT is a class of cyber threat in which a well-resourced attacker,
typically nation-state or organisation-sponsored, pursues a specific
objective against a specific target over an extended time horizon,
retooling at a tempo that outpaces
reactive defence \citep{alshamrani2019}. The three terms name three
properties: \emph{advanced} tooling and tradecraft, a \emph{persistent} low-and-slow tempo

\citep{alshamrani2019}. NIST states the same profile behaviourally: an
APT attacker pursues its objectives repeatedly, adapts to the defender's
resistance, and sustains the interaction needed to meet its goal
\citep{nist2011sp80039}.

\subsection{Attacker modelling traditions}
\label{subsec:modelling-traditions}

\noindent\emph{[GAP G4a --- the default attacker: the abstract,

\medskip

Modelling techniques cluster into game-theoretic, evolutionary, and
learning-based traditions, with game-theoretic formulations dominating
by volume \citep{cho2020}. A representative game-theoretic formulation
casts the defender as a leader committing to a configuration-switching
strategy and the attacker as a follower that performs reconnaissance
before launching, typically drawing on exploits from public
enumerations such as the Common Vulnerabilities and Exposures (CVE)
database, with attacker-type uncertainty encoded as a prior
distribution \citep{cho2020}.

\medskip
\noindent\emph{[GAP G4b --- what the strategic attacker buys

\medskip

the sequencing, adaptive attacker MTD evaluation omits is
constructible, if so far only on narrow, hand-built cases. Outkin et

engagement data: the apparatus is in place and validated; it has simply
never been brought to MTD evaluation.

\subsection{Attacker model criterion}
\label{subsec:attacker-criterion}

Cho et al.\ name three under-developed dimensions of the attacker model
\citep[Sec.~V-D]{cho2020}. The first is the smart, learning-capable
attacker: where defenders are routinely granted machine-learning
capability, the attacker is assumed to follow fixed patterns rather
than to learn and adapt, an asymmetry Cho et al.\ note runs contrary to
practice, where the attacker is often the more sophisticated of the
two. The second is the scarcity of multi-strategy scenarios, in which
attacker and defender each branch across plural options; most MTD work
instead pairs one mechanism against one attack path. The third is the
asymmetric application of the rational-actor framing: the agent
optimising for cost-effective outcome is modelled as such on the
defender side and seldom on the attacker's. The same survey names four
characteristics of a sophisticated attacker \citep{cho2020}, which
align with the APT profile of Section~\ref{subsec:apt}:
\emph{persistent}, operating across multiple stages with measurable
dwell time rather than as a one-time intrusion; \emph{adaptive},
responding to changing system and defensive conditions, including
awareness of the defence itself; \emph{stealthy}, blending with
legitimate traffic rather than operating at observable indicator
levels; and \emph{incentive-driven}, conditioning decisions on a
cost/benefit signal, not merely possessing an objective.

Jalowski et al.\ reach the same diagnosis six years later, through a
systematic gap-analysis of MTD's design principles and threat-modelling
assumptions that names the attacker model ``the most glaring flaw in
the MTD literature'' \citep[p.~8]{jalowski2026}. Their critique is
concrete about why. The active-scanning baselines (e.g., Nmap) against
which MTD is typically tested are too naive for an APT, which relies on
passive reconnaissance to stay hidden and learns the defender's
mutation patterns over time. The corrective they prescribe is an
attacker modelled at a higher level of capability, one that reasons
about the MTD scheme itself and the logic driving its movement, not a
scripted intruder oblivious to the defence.

Read together with the APT characterisation of Section~\ref{subsec:apt},
these sources yield eight properties an attack model can be scored on:
(1) persistence, as multi-stage campaign structure \citep{cho2020,
alshamrani2019}; (2) objective conditioning \citep{alshamrani2019};
(3) strategic plurality, the multi-strategy branching Cho finds scarce;
(4) adaptivity to defender resistance \citep{cho2020, alshamrani2019};
(5) stealth, the low-and-slow tempo and evasion \citep{cho2020,
alshamrani2019, jalowski2026}; (6) incentive-driven rationality
\citep{cho2020}; (7) learning capability \citep{cho2020,
jalowski2026}; and (8) awareness of the MTD scheme itself
\citep{jalowski2026}. The properties are the literature's; the
selection and the merge of NIST's clauses onto Cho's characteristics
are this thesis's own synthesis.

Where those properties describe the attacker qualitatively, a fidelity
descriptor captures what a threat model \emph{actually does} at the
level of attacker decision-making, ordered by depth from static
parameters to learned behaviour: \emph{parametric} (success
probabilities, fixed durations, or design-time parameters; no per-step
decision during execution); \emph{scripted} (pre-coded sequences
against specific CVEs or attack paths); \emph{procedural} (rule-based
decision-making within an attack progression at runtime, beyond
design-time configuration); and \emph{behavioural} (campaign-level
intent, motivation conditioning, and learning capability). The
descriptor is this thesis's own construction.

over live state is procedural).]}

\subsection{Threat models in recent MTD evaluations}
\label{subsec:recent-threat-models}

Table~\ref{tab:attacker-cross-section} scores recent MTD evaluations
against the eight properties and the fidelity descriptor. The selection
spans the simulator lineage this thesis extends \citep{brown2023,
zhang2023, ho2024, tay2024}, recent IoT-cloud orchestration
\citep{masud2025}, and a recent Cyber Kill Chain-aware MTD framework
deployed on a physical testbed \citep{kim2026}. \emph{[GAP G8 --- the
adverse-sample warrant: these are recent, well-regarded, and in two
cases explicitly ATT\&CK-framed, so they are the works most likely to
model an attacker well; the claim is existence over a favourable
sample, not generalisation from $n = 3$.]} The pattern across the
cross-section is a rhetoric-versus-execution gap: the threat models
encode few of the properties, even where the surrounding framing
suggests otherwise.

Brown et al.'s threat model is two scripted scenarios, opportunistic
(network-wide compromise) and targeted (specific-host compromise),
executed through a finite-state machine inspired by the Cyber Kill
Chain and MITRE ATT\&CK \citep{brown2023}. The attacker's only decision
signal is a priority ordering over scanned exploits by return on attack
(RoA), a cost/impact ratio derived from Common Vulnerability Scoring
System (CVSS) metrics; the simulator's metrics are computed over
outcomes rather than over attacker decisions. Brown et al.\ are candid
about the limitation, noting that ``the exploitation skills are not
configured to distinguish the different skills of adversaries''
\citep[p.~7]{brown2023}.
% [stitch] next sentence (replaces the review's Tay paragraph opener)
The three later works on the same simulator (Table~\ref{tab:mtdsim-lineage})
are defender-side contributions; Zhang adds a time model to the
attacker (per-phase durations and a speed-up on vulnerabilities
exploited before) that parameterises the same scripted progression
\citep{zhang2023}, and the others inherit the attacker unchanged, so its
parametric fidelity carries through. Tay's one attacker-adjacent
experiment varies an intrusion detection system's sensitivity from 0\%
to 100\% and feeds the resulting attacker-action signal to the agent
\citep{tay2024}; the variation is in the defender's
\emph{observability} of the attacker, not in the attacker's
\emph{behaviour}: the attacker remains oblivious to both the IDS and
the RL policy. Masud et al.\ realise the attacker as an exhaustive,
pre-coded traversal of a CVE/CVSS-parameterised attack graph, with no
decision-making agent: scripted fidelity \citep{masud2025}. The framing
claims more than this: the attackers are said to be ``modeled after
techniques in the cyber kill chain and MITRE ATT\&CK''
\citep[p.~7]{masud2025}, but that grounding does not reach the
executed threat model, which carries no technique-level behaviour
beyond the graph it enumerates. Kim et al.'s defender side is genuinely
multi-phase, mapping MTD sub-techniques across the Cyber Kill Chain and
onto corresponding ATT\&CK techniques, and the framing repeatedly
invokes multi-phase MTD against multi-phase cyber-attacks
\citep{kim2026}. The threat model used for evaluation does not match
this depth: the case study is a single path-traversal vulnerability
(CVE-2021-41773) driven by an automated script on a Poisson arrival
schedule, with ATT\&CK invoked taxonomically rather than as behavioural
grounding. The work is itself candid that ``the overlap in time between
each phase is out of scope'' \citep[p.~7]{kim2026}: the multi-phase
attacker is, in execution, a sequential script across collapsed phases.

% [stitch] next sentence
One adjacent work is worth setting beside the table without a row in
it. He et al.'s MTD-AD, a boundary-perturbation defence of an
anomaly-based intrusion detector, formalises an adaptive-knowledge
attacker that knows the defence is deployed and adjusts to it
\citep{he2025}: the only threat model in this survey that responds to
the defence at all. Two qualifiers bound that credit: the response is
design-time configuration rather than runtime decision-making (a single
surrogate-model threshold, swept across fixed values rather than
learned in the loop), and the attack class is detection-evasion of a
machine-learning classifier, a single attack family with no multi-stage
structure. The methodological move toward a defence-aware attacker
transfers; the attack class does not.

Across the cross-section, attacker modelling is consistently secondary
to the defence being proposed: persistence is absent throughout;
adaptivity in the campaign-aware sense is absent; stealth is not
operationalised; and incentive-driven behaviour appears only as partial
operationalisations of the RoA heuristic in the simulator lineage. On
the fidelity descriptor the works cluster at parametric (the lineage)
and scripted (Masud et al., Kim et al.); none reach procedural, let
alone behavioural.

\subsection{The research gap}
\label{subsec:research-gap}

Seen from the attacker's side, the gap sharpens: where the surveyed
works grant the attacker any rationality, it is a defender-computed
heuristic such as RoA \citep{brown2023}, over which the attacker
optimises exploits it cannot sequence, adapt, or remember, choosing the
computationally best move without modelling whether a real attacker
could, or would, make it. The parametric rung, in other words, is
rationality without capability.

The means to close it already exist in MTD-adjacent literatures. Attack
profiling recovers TTP-level behaviour from raw CTI \citep{rodriguez2024,
rahman2025, zhangY2025}, the durable layer the surveyed attacker models
never reach, grounded in documented APT tradecraft rather than a
CVSS-derived heuristic; this supplies the behavioural content, what the
attacker does.
% [stitch] next sentence
The agent to enact it and the engagement data to parameterise it exist
too (Section~\ref{subsec:modelling-traditions}).

The question for L4 is: what can the Petri nets not supply, and how do we
join this to MTDSim? The Petri nets can act as inputs, but
they are like source code: they have no way of running. A Petri net can be run
on its own, but that produces a timeline of what the
attacker did (tracing the token). The timeline is a dead end: it is a
pregenerated sequence, and there is no input from the simulator.
Suppose, for example, the attacker is thwarted by the MTD
mechanism through a mutation. This would lead to a different next
course of action for an attacker in real life, but in this one-way replay
timeline world, where we precompute the attack timelines, the script will
just follow the next tactic. This was not representative of what we thought
the attack model should capture. We had to produce a two-way join.

the action layer. To produce results, we have to join these two layers

\subsubsection{The controller layer}
\label{subsubsec:controller}

The controller layer is the join between the Petri nets and our simulator, and
it carries three things: the dwell times (the stochastic dwell times), the
tactic-to-verb mapping, and the failure matrix.

The first is the dwell times. Each tactic consumes some time in
the simulator, as the previous attack phases did from the action layer. But we
cannot derive the dwell times from anything we have done in
the movement layer itself. The dwell times do not exist in the literature; they
do not exist in CTI vendor reports. Prior papers that have done similar work
describe this as inherently arbitrary: trying to put times on an
attack~\citep{bland2020, mcqueen2006, mendonca2023}.

There is no MITRE tactic mapping to time resource. How
long does reconnaissance take? This is a parameter of the model itself, not an
invariant.

We derived our new dwell times for the tactics from the dwell times of
MTDSim. What we could take from the six original verbs of the action layer,
we used directly.
If that was not sufficient, then we used some multiplier of those values to
produce the tactic dwell times, and if not, we decided what shape fitted
best for this tactic. The declared values are collected in
Table~\ref{tab:dwell-catalogue} and the derivation is in
Appendix~\ref{app:dwell-derivation}: the stealth tactic,
for example, is 45.0 seconds, which is 10 times the exploit shape.
Resource development we deemed zero seconds, because from the
defender's perspective this is off-network and untrackable. Some tactics map to
the same verb, but in reality the tactics, we would assume, do not take the same
amount of time --- there might be more effort, more time, more resources
required --- so different tactics that map to the same verb still provide a
different amount of time.

We tried other mappings: forcing a total mapping was just another input
that did not work. It was running a tightly ordered finite state machine in an
unordered but stochastic manner, and this resulted in poor performance
(Appendix~\ref{app:experiment-one}). We expected the
movement layer to perform the same, or worse, because it is the same thing
in proxy. We also considered using MITRE Caldera~\citep{applebaum2016}, which is also an
operationalisation of the MITRE ATT\&CK framework, but this would introduce too
much overhead, and the results were unclear about the practical implication of
that.

The ceiling of this thesis lies in the action layer that we are adopting from
the simulator: the attacker model that we produce can only be as good
as what we adopt. But it is extendable and modular: our movement layer can be
mapped to anything given an appropriate mapping, or a stronger underlying
attack model can be built that operationalises all of MITRE's tactics, and
that would produce a more useful attacker model. We did not have the time to do
this.

The base transition weights are recurrence values from the earlier levels, and
we assume the observed out-transitions are the complete set of choices open to
the token --- an explicit assumption, since the Attack Flow corpus is all we
have to draw on, and a different corpus would give different transitions and
weightings. But a recurrence value does not reflect an attacker, because an
attacker can succeed or fail, and these reports only capture success --- there
is survivorship bias. These values are necessary, but they are not sufficient,
so we have to supplement them with re-weighting to consider if the
attacker agent fails.
% [rephrase applied: base-weights passage compressed to its consequence + the
%   closed-world assumption, not re-defining the weights (defined at L1/L2).]

One concern was trying to overfit the tactic-to-tactic failure matrix
to the baseline attacker's action layer. This is a
separate layer, independent from the nets and from the action layer: we did not
reverse-engineer any of these values. They can be
justified; they can be defended.

We employed a failure matrix because this is the blind spot of the CTI: the CTI
naturally encodes success, so the failures are what is not encoded, and that is
what we are trying to encode here. We needed a 15-by-14 tactic-to-tactic
failure weight matrix (excluding
self-loops), shaped by two components. The first is the failure rules,
independently decided: each tactic-to-tactic transition was placed into a given
shape (rules A to I in Figure~\ref{fig:failure-weight-matrix}). The second is distance: we used the
literature and overlaid the attack
phases~\citep{hutchins2011, alshamrani2019, mandiant2013, chemat2024}, which
gave the four broad phases of an attack --- preparation, intrusion,
post-intrusion operations, and objective. We assigned a distance value: a
transition within the same phase, or one phase away, is not penalised; two
phases away keeps a quarter of its weight; and the maximum distance is weighted
zero. There is a floor of 0.1: if a distance value falls below this threshold,
it is read as exactly zero at fold-in. It makes no sense for an attacker to go
from reconnaissance directly to impact in the MITRE framework, because they are multiple
steps away from each other, as the literature would say. This can be found in
Appendix~\ref{app:weight-sets}, along with the full set of tactic-to-tactic
failure weights.

\subsubsection{Mechanics and the join to MTDSim}
\label{subsubsec:mechanics-join}

We made all of the actions in MTDSim independent of each other, and produced
the join through the controller layer, so that the movement layer supplies all
the tactic timing of the attacker agent at runtime. The loop runs as follows: the
token selects the next tactic; the tactic has a dwell time and an exponential
draw, which is fed into the discrete-event simulator and consumed as time;
the mapping resolves the tactic to a verb (or to dwell-only); once the time is
consumed, a success or failure signal returns, on failure the failure matrix
re-weights the token's out-transitions, and the next tactic is selected
(Figure~\ref{fig:movement-dataflow}).
% [rephrase applied: your dictated loop spec compressed to one runtime
%   sentence + the figure ref; the action-carve moved here from the preamble.]

This is verdict-conditioned re-weighting. The base proportion on all of the
edges is multiplied by the declared failure matrix and renormalised. On success the
token routes on the base proportions, since the corpus already encodes success;
on failure the declared failure matrix applies, producing a different set of
options for the token to decide from. This is what encodes direction.
% [rephrase applied: the one-arm seam fixed --- success = route on the base
%   proportions (v4_failure_only); "encodes direction" once. The retired
%   success matrix is not mentioned, per your ruling.]

Success or failure at runtime comes from the action layer and is propagated
up.
An action fails if the preconditions of the action itself were missing --- for
example, trying to exploit a vulnerability without having scanned for it:
objects are passed around in the simulator, and if the verbs have not been run,
it fails. The same holds for the moving target defence: if MTD interrupts the
attacker, then whatever verb it is on fails. But if they are on a dwell-only,
there is no verdict, so this is not felt by the token in the Petri net.

We employed a sink-retrace policy, because the token would
frequently hit sinks in the Petri net and terminate the run --- a concession to
the thinness of the corpus; we retrace the edge travelled.
Another characteristic is that the simulator we are inheriting largely models the
confusion and disruption of the attacker through a 20-second confusion penalty
that hits the attacker at certain phases. How the defender thwarts the attacker
is inherently tied to the simulator; it is an invariant of the simulator, so we
maintain that 20-second confusion penalty. Not all the timing is supplied by
the Petri net: the confusion penalty is the exception.
